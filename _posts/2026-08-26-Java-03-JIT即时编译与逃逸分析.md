# JIT 即时编译与逃逸分析（JVM 收官课）
## 1. 执行引擎分层编译

![03-01 执行引擎分层编译]({{ site.baseurl }}/assets/svg/03-01-执行引擎分层编译.svg)

```
字节码 ──加载──> 解释执行 ──热点──> C1 编译 ──更热──> C2 编译
               逐条翻译·启动快    轻优化·短编译      激进优化·极致
               方法计数 ~1.5k 次   循环回边+调用 ~10k 次
```

- **Java"先慢后快"的本质**：JVM 用运行时信息换优化空间，代码越热优化越激进
- 分层编译（`-XX:+TieredCompilation`）JDK 8+ 默认开启，别动
- 触发靠两个计数器：方法调用计数器 + 循环回边计数器（`-XX:CompileThreshold` 分层模式下仅参考）
- **C2 三板斧**：方法内联（一切优化之母）· 逃逸分析 · 锁消除

实战推论：
1. 性能测试别用单次结果下结论——冷代码在解释执行，要先预热
2. getter/setter 不用省（内联后零成本）；该拆的是巨无霸方法——不拆开 C2 看不清方法体

## 2. 逃逸分析：对象到底进不进堆

![03-02 逃逸分析决策路径]({{ site.baseurl }}/assets/svg/03-02-逃逸分析决策路径.svg)

```
new Point(x,y) ──> 逃逸了吗？
   │不逃逸                    │逃逸
   ▼                          ▼
标量替换                     逃逸三途径
对象拆成基本类型放栈帧/寄存器   返回值·存进字段·传给外部方法
堆里根本没有这个对象            赋给静态变量/共享结构
   │                          │
   ▼                          ▼
零 GC 压力                   正常堆分配·走分代流转
```

**关键澄清**：HotSpot 没有真正的"栈上分配"——`-XX:+DoEscapeAnalysis` 的实际手段是**标量替换**：不逃逸的对象被打散成局部变量放进栈帧，对象身份消失，GC 看不见它。

| 写法 | 逃逸？ | 后果 |
|---|---|---|
| 循环里 `new Point()` 算完就扔 | 不逃 | 标量替换，零 GC 压力 |
| `list.add(point)` 再返回 | 逃 | 堆分配，分代流转 |
| 局部 `StringBuffer` 拼完传 logger | 逃 | 堆分配 + synchronized 保留 |
| 临时对象赋给静态字段/缓存 | 线程逃 | 最重：堆分配 + 跨线程 |

- **锁消除**也在这步：不逃逸 → 锁没人争 → synchronized 直接删
- 实战原则：**别为减少对象创建把代码写晦涩**——让 JIT 看得见对象不出方法，比手工抠对象更有效
- 点位解析临时对象不出方法即被消灭；`set` 进响应 DTO 返回前端则进堆

## 3. 直接内存：Netty 网关的隐形战场

![03-03 直接内存与 Netty 池化]({{ site.baseurl }}/assets/svg/03-03-直接内存与Netty池化.svg)

```
业务代码 ──> Netty 池化分配器 ──> OS 直接内存（malloc/mmap）
(Modbus 编解码)  PooledByteBufAllocator     不受 -Xmx 管
                     │
                引用计数 retain(+1)/release(-1)
                计数归零 → 回池复用
               /                          \
        守规矩：try/finally 里 release     漏 release
        内存回池·稳态运行                  DirectMemory 只涨不降
                                          heap dump 看不见它
```

- **池化动机**：高频收发若每次 malloc/free 直接内存，系统调用开销拖垮网关 → 按线程分 Arena 池化复用
- **引用计数纪律**：ByteBuf 不是垃圾，GC 不管它；`SimpleChannelInboundHandler` 自动释放入站消息，自己 retain 过的才手动 release
- 监控三件套：
  - `-XX:MaxDirectMemorySize` 设上限（宁可它报错，别吃光机器内存）
  - NMT：`-XX:NativeMemoryTracking=summary` + `jcmd <pid> VM.native_memory summary`
  - Netty 泄漏检测：`-Dio.netty.leakDetection.level=paranoid`（排查期）
- **诊断口诀**：堆外涨而堆平稳 → 先查 DirectBuffer（Vert.x 网关高频收发全走此链路）

## 4. JVM 三课总结

| 课 | 回答的问题 | 一句话 |
|---|---|---|
| 01 内存与 GC | 数据放哪、GC 何时发生 | 地形图 + 排查入口 |
| 02 G1 与日志 | G1 怎么干活、日志怎么读 | Region 收益模型 + 日志听诊 |
| 03 JIT 与堆外 | 为什么有的对象不进堆 | 逃逸分析消灭临时对象；堆外看 Netty |
