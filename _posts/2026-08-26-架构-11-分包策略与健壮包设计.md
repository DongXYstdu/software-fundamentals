# 分包策略与健壮包设计（L7 结构软实力 · 第三课）
## 1. 包是什么——最小访问控制单元与最小依赖单元

### 1.1 包的两个身份

**身份一：Java 原生的最小访问控制单元。** `private` 管类内部，`public` 对全世界开放，中间那档 `package-private`（不写修饰符的默认可见性）**只对同包可见**。包是 Java 语言里唯一能表达"这组类是一个整体、内部细节不对外"的原生机制。

```java
package com.example.gateway.alarm.rule;

// 同包可见：包内协作自由
class WindowStateTracker { ... }        // 没写 public → 包外根本看不见

// 对外门面：整个包只暴露这一个类
public class AlarmRuleEngine { ... }
```

**身份二：依赖与内聚的最小单元。** 09 课的 Ca/Ce/I/A/D 度量原生粒度就是包；ArchUnit 的 `resideInAPackage` 执法的也是包。**类太细、模块太粗——包正好是"可以画在白板上的最小结构单位"。**

一句话定位：**模块是构建工具给的边界，包是语言给的边界；模块靠 pom 执法，包靠可见性 + 纪律 + 架构测试执法。**

### 1.2 包与模块的执法机制差异

| | Maven 模块（10 课） | 包（本课） |
|---|---|---|
| 边界由什么声明 | pom 的 `<dependency>` | 无显式声明，**靠约定** |
| 越界成本 | 不声明依赖就**编译失败** | `import` 一下就越界，**编译器不拦** |
| 访问控制 | 无 | `package-private` 原生支持 |
| 执法工具 | Enforcer（validate 阶段） | **可见性 + ArchUnit 包级规则** |
| 调整成本 | 改 pom、挪目录、改坐标 | 改 import、挪文件（IDE 一键） |

两个关键推论：

1. **包边界天然是"弱边界"**：没有编译器兜底，包结构更容易腐化——必须补上自动执法，否则等于没有边界
2. **但包有模块没有的武器**：`package-private`——模块之间做不到"只暴露门面、隐藏内部"，包可以

### 1.3 弱边界的生存法则

| 法则 | 含义 | 展开段落 |
|---|---|---|
| **可见性即边界** | 能用 `package-private` 隐藏的，绝不 `public` | 第 4 段 |
| **结构即契约** | 包名和包结构要能读出业务含义 | 第 2、6 段 |
| **测试即执法** | 包间依赖方向、禁环写成 ArchUnit 规则 | 第 7 段 |

### 1.4 现状盘点：告警模块的包长什么样

最常见的初始状态是**按技术分层分包**：

```
com.example.gateway.alarm
├── controller/      ← AlarmController、RuleConfigController
├── service/         ← AlarmService、RuleService、NotifyService（越堆越多）
├── mapper/          ← AlarmRecordMapper、AlarmRuleMapper
├── entity/          ← AlarmRecord、AlarmRule（贫血数据袋）
└── dto/             ← AlarmVO、RuleQueryReq
```

三个先天问题：

1. **"告警"这个业务能力没有对应的包**——代码散在五个技术包里，删掉告警特性要动五个包
2. **`service` 包是包内的"大杂烩"**——规则、通知、确认三类职责混居
3. **所有类都是 `public`**——内部 helper 谁都能调，包内没有秘密

对照 09 课：这个结构的每个包 I 值都说不清（包按技术切，不是按变化轴切），D 值体检无从下手——**包结构不对，度量先失效**。

## 2. package-by-layer vs package-by-feature——删除测试判据

![11-01 按层分包 vs 按特性分包]({{ site.baseurl }}/assets/svg/11-01-按层分包vs按特性分包.svg)

### 2.1 两种分包方式

```
by-layer（第一级是技术层）：        by-feature（第一级是业务能力）：
alarm/                              alarm/
├── controller/                     ├── rule/      ← 评估、配置、窗口状态
├── service/                        ├── notify/    ← 渠道、模板、发送记录
├── mapper/                         ├── confirm/   ← 人工确认、超时升级
├── entity/                         └── record/    ← 持久化、查询
└── dto/
```

一句话区分：**by-layer 的第一级回答"这是什么技术"，by-feature 的第一级回答"这是哪块业务"**——与 10 课横向/纵向模块划分完全同构。

### 2.2 删除测试：删掉一个特性要动几个包

> **假设要将某个业务特性完整移除，需要动多少个包？**

用"移除告警通知功能"演算：

**by-layer**：通知接口（controller）+ NotifyService（service）+ 通知 Mapper（mapper）+ NotifyRecord（entity）+ NotifyVO（dto）= **5 个包全动**，且每个包里通知的类和其他特性的类混居，删除必须逐个甄别。

**by-feature**：整个通知特性在 `notify/` 一个包里，接口、逻辑、持久化自包含，**整包删除即可，其他包无感**。

删除测试的本质：**检验"业务特性的代码是否聚集在一起"**——10 课"变化轴与边界平行"在包粒度的重演。

### 2.3 两种方式的全面对比

| 维度 | package-by-layer | package-by-feature |
|---|---|---|
| 第一级目录 | 技术层 | 业务能力 |
| 加一个特性 | 每个技术包各加一个类，**横穿** | 新建一个特性包，**局部** |
| 删一个特性 | 横穿所有技术包逐个甄别 | 整包删除 |
| 找一个特性的全部代码 | 跨 5 个包拼凑 | 一个包内看全 |
| 包间耦合风险 | 高：`service` 包内部无边界 | 低：特性包间可用 ArchUnit 禁互依 |
| 适用 | 业务极简、单特性的早期项目 | 有 ≥2 个可识别业务特性的模块 |

by-feature **独有**的结构红利：特性包之间可以立规矩（禁互依），而 by-layer 的 `service` 包内部是法外之地。

### 2.4 三个实操要点

**要点 1：特性包粒度 = 两问法降维**——有独立演进节奏或自己的数据 → 独立特性包；都不满足 → 并入相邻包，不为凑数建空包。

**要点 2：特性包内部可以再分层，但层是第二级**

```
rule/                          ← 第一级：业务能力
├── AlarmRuleEngine.java       ← 对外门面（public）
├── internal/                  ← 第二级：包内技术分层（可选）
│   ├── WindowStateTracker.java
│   └── ThresholdEvaluator.java
└── AlarmRule.java
```

**次序铁律：第一级必须是特性，第二级才允许技术**。反过来就退化成 by-layer 套娃。

**要点 3：共享领域模型放模块级 `domain` 包**——判据仍是"三则上提"：两个特性包共用先放其中一方，第三个消费者出现再上提。

### 2.5 by-layer 仍然合理的场景

| 场景 | 理由 |
|---|---|
| 模块只有一个业务能力、类总数 < 20 | 特性分包是空转 |
| 纯技术模块（如 `gateway-common`） | 按工具类别分（`codec/`、`crypto/`）本质还是按变化轴 |

### 2.6 迁移：存量 by-layer 怎么转

```
第一步：不动旧包，新特性一律按 by-feature 建包
第二步：借需求顺手搬——改到哪个特性就搬该特性的类（IDE 一键 Move）
第三步：旧技术包只减不增，搬空后删除
第四步：用 ArchUnit 冻结规则防回潮（第 7 段）
```

核心原则：**迁移跟着需求走，不搞运动式重构**。

## 3. 接口包归属之争——集中式 api 包 vs 消费者所有

![11-02 接口包归属之争]({{ site.baseurl }}/assets/svg/11-02-接口包归属之争.svg)

### 3.1 争论的由来

> **模块内部的接口，放在哪个包里？**

**方案 A：集中式 `api` 包**——所有对外接口堆在一个包里。
**方案 B：消费者所有（Role Interface）**——接口跟着使用它的业务走，谁消费谁拥有。

### 3.2 集中式 `api` 包的诱惑与代价

| 诱惑 | 说法 |
|---|---|
| "一眼看全模块对外能力" | 打开 `api` 包就是能力清单 |
| "依赖方只依赖 api 包" | 看起来依赖最小化 |
| "和很多开源项目一致" | 脚手架默认生成 |

代价（用 09 课尺子量）：

1. **变更磁铁（违反 ISP）**：`AlarmSink` 改签名，`api` 包变了，所有依赖 `api` 的代码都要重新审视——接口物理上挤在一起，变更互相牵连
2. **契约意图丢失**：接口孤零零躺在 `api` 里，无法回答"它是为谁定义的、方法集合为什么恰好是这几个"
3. **诱导过度设计**：有了"坑"就倾向于先挖坑再种萝卜，"第二次变化才抽象"的节奏被破坏

### 3.3 消费者所有：接口跟着使用方走

逻辑链（全部来自 09 课）：

```
ISP：接口按消费者的需要定义
  ↓
DIP：接口所有权归消费者
  ↓
包粒度落地：接口文件放在消费者所在的包里
```

网关实例：

```java
package com.example.gateway.alarm.rule;

// 接口定义在消费者（rule 包）里，方法集合恰好是 rule 需要的
public interface AlarmSink {
    void send(AlarmRecord record);
}

public class AlarmRuleEngine {
    private final AlarmSink sink;   // 依赖自己包里的接口
}
```

```java
package com.example.gateway.alarm.notify;

import com.example.gateway.alarm.rule.AlarmSink;   // 实现方依赖消费者的接口

public class KafkaAlarmSink implements AlarmSink {
    public void send(AlarmRecord record) { /* ... */ }
}
```

依赖方向 **`notify` → `rule`**（实现方指向消费者）——与直觉相反，但正是"倒置"的本义：箭头指向抽象，而抽象归消费者所有。

三个收益：变更局部化、契约意图自解释、天然抑制过度设计。

### 3.4 集中式 `api` 包的适用场景

| 场景 | 理由 |
|---|---|
| **跨模块/跨系统契约**：SDK、OpenFeign 客户端、RPC 接口 | 消费者是外部系统，需要稳定、独立版本的契约包统一发布 |
| **模块对外门面**：少量（3–5 个）门面接口 | 方便其他模块发现；但模块内部特性间的接口不走这里 |

分界线：**对外的契约集中放（发布单元），对内的接口归消费者（协作契约）**。

### 3.5 实操要点

1. **接口放哪，看"谁的方法集合决定它"**——`TagReader` 只有一个 `readTags`，因为领域层只需要读
2. **实现方依赖消费者接口是合法包间依赖，但要受控**——方向稳定、经过接口；两特性包互依具体类 = 环的前兆
3. **命名暴露所有权**：`AlarmSink`、`TagReader`（消费者视角），而不是 `KafkaInterface`、`ScadaApi`。**名字里出现具体技术 = 接口所有权放错了地方**

## 4. package-private 访问控制——用可见性当边界，门面类模式

![11-03 包可见性与稳定抽象放置]({{ site.baseurl }}/assets/svg/11-03-包可见性与稳定抽象放置.svg)

### 4.1 被遗忘的默认可见性

| 可见性 | 谁能访问 | 实际使用率 |
|---|---|---|
| `public` | 全世界 | 滥用 |
| `protected` | 子类 + 同包 | 少用 |
| **（不写）包可见** | **仅同包** | **几乎不用 ← 本课捡起来的武器** |
| `private` | 仅类内 | 正常 |

一个类不写 `public`，包外代码连 `import` 它都做不到——**编译器强制的边界，强度等同模块边界，成本为零**。

### 4.2 全 public 结构的代价

```java
package com.example.gateway.alarm.service;

// 这是 RuleService 的内部 helper，实现细节本不该有人关心
public class WindowStateTracker {          // ❌ public：全世界都能调
    public void touch(String deviceId) { ... }
    public void evictExpired() { ... }     // 内部清理方法也暴露了
}
```

三重代价：

1. **内部细节变成公共契约**：方法签名不能随便改，09 课"变化隔离"被击穿
2. **绕过门面的捷径**：包外嫌流程麻烦直接调内部类抄近路，业务规则被架空
3. **重构恐惧**：改内部类要先全局搜索影响面，代码冻结成"能跑就别碰"

一句话：**全 public 的包没有内部，只有外部**。

### 4.3 门面类模式：一包一门面，其余全包可见

```java
package com.example.gateway.alarm.rule;

// ✅ 门面：整个 rule 包对外的唯一入口
public class AlarmRuleEngine {

    private final WindowStateTracker tracker;   // 内部协作，包外不可见
    private final ThresholdEvaluator evaluator;
    private final AlarmSink sink;

    public AlarmRuleEngine(AlarmSink sink) {
        this.sink = sink;
        this.tracker = new WindowStateTracker();
        this.evaluator = new ThresholdEvaluator();
    }

    // 对外只暴露这一个业务动作
    public List<Alarm> evaluate(DeviceSnapshot snapshot) {
        tracker.touch(snapshot.deviceId());
        return evaluator.check(snapshot, tracker)
                .stream()
                .peek(sink::send)
                .toList();
    }
}

// ✅ 不写 public → 包外根本看不见这两个类
class WindowStateTracker {
    void touch(String deviceId) { ... }
    void evictExpired() { ... }        // 内部清理，想改就改
}

class ThresholdEvaluator {
    List<Alarm> check(DeviceSnapshot s, WindowStateTracker t) { ... }
}
```

| 对比项 | 全 public | 门面模式 |
|---|---|---|
| 包外能调用的类 | 3 个（含内部细节） | **1 个**（只有门面） |
| 内部类重构 | 全项目影响分析 | **包内随便改，编译器保证无人受影响** |
| 抄近路的可能 | 存在 | **编译期封死** |
| 公共契约面积 | 所有 public 方法 | 仅门面方法 |

**"重构自由度"是门面模式最被低估的收益**：编译器已经替你证明了"包外没人用"——不需要搜索、评审、冻结期。

### 4.4 与 Spring 的配合

**注意点 1**：`@Component` 扫描对 package-private 类有效。但更推荐纯粹形态：**内部类不用 `@Component`，由门面类自己 `new` 或持有**——Bean 数量从"每类一个"收敛到"每包一个门面"。

**注意点 2**：测试类放在与被测类**相同的包名**下（`src/test/java` 建同名包），就能直接测 package-private 类——**封装不牺牲可测性**。

### 4.5 实操要点

1. **新类默认不写 `public`**，需要对外时才升级；每次加 `public` 都是"扩大契约面积"的决策
2. **一包原则上一个门面**；要暴露 5 个 public 类，先考虑是不是该拆包
3. **存量渐进收口**：先指定门面，用 ArchUnit 冻结"包外只允许依赖门面"，之后逐个摘内部类的 `public`——**摘掉时编译器立刻报出所有违规调用点，编译器就是影响分析工具**

## 5. 稳定抽象的放置——api/internal 子包约定与主序列投影

### 5.1 包内的"主序列"

| 类型 | 特征 | 主序列坐标 | 例子 |
|---|---|---|---|
| 契约类 | 被广泛依赖、描述"做什么" | I 低 A 高 | `AlarmRecord`、`AlarmSink`、门面 |
| 实现类 | 依赖别人多、描述"怎么做" | I 高 A 低 | `WindowStateTracker`、各 helper |

健康结构：**契约类在上被依赖，实现类在下依赖契约，箭头全部指向稳定侧**——与 10 课模块依赖图同构。

反例："实现类被当契约用"：

```java
// ❌ 别的包直接依赖了实现细节类
import com.example.gateway.alarm.rule.WindowStateTracker;
```

等价于"稳定模块依赖易变模块"的包级翻版。

### 5.2 api / internal 子包约定

```
com.example.gateway.alarm.rule
├── api/                          ← 契约区：稳定、被依赖
│   ├── AlarmRuleEngine.java      ← 门面（public）
│   ├── AlarmSink.java            ← 消费者所有的接口（public）
│   └── AlarmRecord.java          ← 契约模型（public）
└── internal/                     ← 实现区：易变、依赖契约
    ├── WindowStateTracker.java   ← package-private
    ├── ThresholdEvaluator.java   ← package-private
    └── SlidingWindowStore.java   ← package-private
```

三条规则：

1. **`api` 只放 public 契约**：改动需要理由——它们是包的公共承诺
2. **`internal` 全放 package-private 实现**：与门面模式合流，双保险
3. **依赖方向单向**：`internal` 可依赖 `api`，`api` 不得依赖 `internal`（可写成 ArchUnit 规则）

注意与第 3 段术语区分：**这里的 `api` 是特性包内部的"契约区"子包，不是模块级集中式 `api` 大包**。同名不同物，判断标准仍是归属：契约跟着特性走，不集中堆放。

### 5.3 什么时候需要子包

| 包规模 | 建议 |
|---|---|
| ≤ 5 个类 | 不分子包，靠可见性就够 |
| 6–15 个类 | 可选；契约与实现天然分群时加上 |
| > 15 个类 | 先考虑拆包；确实是大特性再上子包 |

**子包是"结构已经存在"时的显式化，不是制造结构的手段。**

### 5.4 稳定性判据：三个问题定位一个类

| 问题 | 答"是"的倾向 |
|---|---|
| 包外代码会依赖它吗？ | → 契约区，且必须 public |
| 方法签名半年内会变吗？ | 会变 → 实现区；稳定 → 契约区 |
| 换实现方式它要跟着变吗？ | 需要 → 实现区；它定义"要做什么" → 契约区 |

### 5.5 同一原则的三个粒度

| 粒度 | 稳定抽象放哪 | 易变实现放哪 | 执法手段 |
|---|---|---|---|
| 模块（10 课） | `domain-core` 模块 | 各业务/基础设施模块 | pom + Enforcer |
| **包（本课）** | **`api` 子包 / 门面** | **`internal` / 包可见类** | **可见性 + ArchUnit** |
| 类（09 课） | 接口、抽象类 | 具体实现类 | DIP + 构造器注入 |

**"层次分明"的工程学定义：每个粒度上，稳定抽象在上、易变实现在下、箭头单向朝上。**

## 6. 命名与结构纪律——包名即文档，结构即防线

### 6.1 包名是写给未来的第一份文档

```
❌ 技术命名：                      ✅ 业务命名：
com.example.gateway.service        com.example.gateway.alarm.rule
com.example.gateway.manager        com.example.gateway.alarm.notify
com.example.gateway.handler        com.example.gateway.device.catalog
com.example.gateway.util2          com.example.gateway.collect.modbus
```

技术命名三病灶：无信息词（看到包名不知是什么业务）、同类词泛滥导致归属模糊（`AlarmManager` 放 manager 还是 service？）、编号后缀是重构的墓碑。

命名铁律：**包名用业务名词，禁用无信息的技术泛词（service/manager/handler 作为业务包名）**。技术泛词只允许出现在纯技术模块里，且按工具类别命名（`codec`/`crypto`）。

### 6.2 深度控制：包层级不超过四层

| 规则 | 说明 |
|---|---|
| 业务路径 ≤ 4 层 | `公司.项目.模块.特性` 足够定位 |
| 每层至少 3 个类 | 单类包这层目录就是噪音 |
| 版本号不进包名 | `v2` 包意味着新旧并存失控 |

**"每层至少 3 个类"是检测过度设计的实用探针**。

### 6.3 防"包内 common"膨胀

模块内会复发同样的病：

```
com.example.gateway.alarm
├── rule/
├── notify/
└── util/          ← ⚠ 模块内的"小 common"
```

治理沿用 10 课四门禁降维执行：

| 门禁 | 模块内版本 |
|---|---|
| 三方共用 | 至少 **3 个特性包**真实使用才进 `util` |
| 稳定 | 不随业务需求变 |
| 无业务语义 | 含业务判断 → 搬回特性包 |
| 零出度 | `util` 不依赖任何特性包 |

补充包粒度特有规则：**优先就近放置**——只有一个特性包在用的工具类直接放那个包里做 package-private。**模块内 `util` 的理想状态是长期接近空**。

### 6.4 包间禁环：模块内的环更隐蔽

模块内的包环没有任何工具自动报警——`rule` 和 `notify` 互相 import，编译完全正常。

典型成因："双向协作没走接口"：

```
rule 包：评估完直接 new 了 notify 的 Notifier
notify 包：发送失败直接调 rule 的 RuleService 回写
→ rule ↔ notify 成环
```

治理手法与 10 课同构：

| 病因 | 包级手法 |
|---|---|
| 抽象缺失 | 接口上提到消费方包或模块 `domain` 包 |
| 边界切错 | 两特性包总一起改 → 合并 |
| 时序耦合 | 改事件：发布 `AlarmTriggeredEvent`，订阅响应 |

执法：ArchUnit 的 `slices().should().beFreeOfCycles()`——**包粒度唯一可靠的自动检测，必须配上**。

### 6.5 网关项目的包命名规范

```
com.example.gateway
├── alarm                          ← 模块根包 = 业务能力名
│   ├── rule                       ← 特性包：业务名词，单数
│   │   ├── api/                   ← 契约区（可选，类多才建）
│   │   └── internal/              ← 实现区（可选）
│   ├── notify
│   ├── confirm
│   └── domain                     ← 模块级共享契约（跨特性模型）
├── device
│   ├── catalog
│   └── domain
└── collect
    ├── modbus                     ← 协议名作特性包名（纯变化轴）
    └── domain
```

五条成文规则：

1. 一级 = 业务能力，禁用技术泛词
2. 二级 = 特性，业务名词、单数形式
3. 三级 = 可选的 api/internal，类少不建
4. 共享契约放 `domain` 包，每模块一个，只进不出
5. util 包默认不建，建了就要接受四门禁审查

## 7. 用 D 值验收分包 + ArchUnit 包级规则

### 7.1 度量与执法的分工

| 工具 | 职责 | 类比 10 课 |
|---|---|---|
| **JDepend** | **度量**：算出每包 Ca/Ce/I/A/D | 体检报告 |
| **ArchUnit** | **执法**：依赖方向、禁环写成测试 | Enforcer 的包级版 |

**09 课的 Ca/Ce/I/A/D 原生就是包粒度度量**——验收分包 = 把 09 课的尺子真正用起来。

### 7.2 告警模块的包体检

| 包 | Ca | Ce | I | A | D | 诊断 |
|---|---|---|---|---|---|---|
| `alarm.domain` | 3 | 0 | 0 | 0.8 | 0.2 | ✅ 主序列左端，稳定锚点 |
| `alarm.rule` | 1 | 1 | 0.5 | 0.5 | 0.0 | ✅ 恰在主序列上 |
| `alarm.notify` | 0 | 2 | 1.0 | 0.1 | 0.1 | ✅ 易变实现区 |
| `alarm.confirm` | 0 | 1 | 1.0 | 0.2 | 0.2 | ✅ 同上 |
| `alarm.util`（若膨胀） | 3 | 2 | 0.6 | 0.05 | **0.45** | ⚠ 滑向痛苦区 |

读数：`domain` 被三方依赖且高抽象（契约区在上做对了）；`notify`/`confirm` 没人依赖可随便重构（by-feature 的红利）；`util` 的 D=0.45 直接指认病灶。

**验收标准：每个特性包落在主序列上（D 接近 0），domain 包在左端，任何 util 包不得偏离主序列。**

### 7.3 ArchUnit 包级规则（可直接抄）

```java
@AnalyzeClasses(packages = "com.example.gateway.alarm")
public class AlarmPackageTest {

    // 规则1：api 契约区不得依赖 internal 实现区（方向单向）
    @ArchTest
    static final ArchRule api不依赖internal =
        noClasses()
            .that().resideInAPackage("..api..")
            .should().dependOnClassesThat()
            .resideInAPackage("..internal..");

    // 规则2：domain 只进不出（模块内 domain-core）
    @ArchTest
    static final ArchRule domain不依赖特性包 =
        noClasses()
            .that().resideInAPackage("..domain..")
            .should().dependOnClassesThat()
            .resideInAnyPackage("..rule..", "..notify..",
                                "..confirm..", "..util..");

    // 规则3：domain 不依赖技术框架（保持契约纯净）
    @ArchTest
    static final ArchRule domain不依赖框架 =
        noClasses()
            .that().resideInAPackage("..domain..")
            .should().dependOnClassesThat()
            .resideInAnyPackage("org.springframework..",
                                "org.apache.ibatis..",
                                "org.apache.kafka..");

    // 规则4：util 零出度（四门禁的代码化）
    @ArchTest
    static final ArchRule util不依赖任何业务包 =
        noClasses()
            .that().resideInAPackage("..util..")
            .should().dependOnClassesThat()
            .resideInAnyPackage("..rule..", "..notify..",
                                "..confirm..", "..domain..");

    // 规则5：特性切片无环（包环唯一可靠检测）
    @ArchTest
    static final ArchRule 特性包无环 =
        slices().matching("com.example.gateway.alarm.(*)..")
            .namingSlices("$1 特性")
            .should().beFreeOfCycles();
}
```

| 规则 | 守护的纪律 | 出处 |
|---|---|---|
| api 不依赖 internal | 契约→实现单向 | 第 5 段 |
| domain 只进不出 | 稳定锚点不被污染 | 第 6 段 |
| domain 不依赖框架 | 契约纯净、可独立测试 | 第 5 段 |
| util 零出度 | 杂物间四门禁 | 第 6 段 |
| 特性包无环 | 包环拦截 | 第 6 段 |

微妙处：`notify → rule`（实现 `AlarmSink`）是单向合法依赖，`beFreeOfCycles` 只拦双向成环，不误伤单向协作。

**"internal 不得被包外访问"不需要 ArchUnit**——`package-private` 已在编译期物理封死。可见性就是最强的执法，**有些边界用语言特性就够了，不必上工具**。

### 7.4 存量项目：冻结 + 增量零容忍

```java
@ArchTest
static final ArchRule domain不依赖特性包_增量 =
    FreezingArchRule.freeze(
        noClasses()
            .that().resideInAPackage("..domain..")
            .should().dependOnClassesThat()
            .resideInAnyPackage("..rule..", "..notify..", "..confirm..")
    );
```

| 场景 | 行为 |
|---|---|
| 首次运行已存在的违规 | 记录进 `archunit_store/`，测试绿 |
| **新增违规** | **测试红** |
| 存量违规被修复 | 自动从记录移除 |

治理节奏：**冻结现状 → 新代码零容忍 → 借需求顺手修存量 → 违规清单只减不增**。

### 7.5 落地要点

| 要点 | 说明 |
|---|---|
| 度量频率 | 每次调整包结构后跑一次 JDepend，对照 D 值前后变化 |
| 执法时机 | 普通单测，`mvn test` 自动带上 |
| 规则数量 | 从 5 条起步，每条对应真实踩过的坑 |
| 不要重复执法 | 可见性已封死的不必再写规则 |
| 度量是诊断仪不是 KPI | 盯趋势：Ca 增长而 A 不动 → 该抽契约了 |

## 8. 落地检查清单与全课收束

### 8.1 分包治理六步操作手册

```
第一步：定结构 —— 第一级按业务能力，第二级才允许技术分层
第二步：定归属 —— 对内接口归消费者包，对外契约才集中放
第三步：收可见性 —— 一包一门面 public，其余全 package-private
第四步：摆稳定 —— 契约放 api（上），实现放 internal（下），箭头单向
第五步：立纪律 —— 业务名词命名、深度 ≤4 层、util 四门禁、特性禁环
第六步：验收执法 —— JDepend 跑 D 值 + ArchUnit 五规则 + 存量冻结
```

### 8.2 评审现场速查表

| 场景 | 检查项 |
|---|---|
| 新建一个包 | 包名是业务名词吗？第一级是特性吗？ |
| 新建一个类 | 默认 package-private 了吗？ |
| 新建一个接口 | 消费者是谁？放消费者包里了吗？ |
| 想往 util 扔东西 | 四门禁过了吗？能不能就近放特性包？ |
| 包外要调某类内部方法 | 该走门面吗？还是这个类该 public？ |
| 两特性包互相 import | 单向协作（合法）还是双向成环（必拆）？ |
| 分包完成后 | JDepend 跑一遍，D 值是否都接近 0？ |

### 8.3 一句话记住本课

> **包是语言给的弱边界，用三件套补强：可见性封内部（门面模式）、结构摆稳定（api/internal）、测试守方向（ArchUnit）。**

对"如何分包对系统更健壮、层次分明"的完整回答：

- **健壮**来自变化隔离：by-feature 让变化落在一个包内（删除测试），package-private 让包内重构有编译器保证，D 值验收确保每包落在主序列
- **层次分明**来自三个粒度的同一把尺子：契约在上、实现在下、箭头单向——类内（09 课）、包内（本课）、模块间（10 课）全部同构
