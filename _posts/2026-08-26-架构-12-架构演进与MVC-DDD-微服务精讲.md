# 架构演进与MVC-DDD-微服务精讲
---

## 一条主线：每次演进，都是"把一个堵住的问题拆出去"

![12-01 架构演进主线总览]({{ site.baseurl }}/assets/svg/12-01-架构演进主线总览.svg)

架构不是越分越好，而是"当一个问题开始堵住增长时才拆"。四步演进的每一步，都有明确的堵点与判据：

| 演进 | 解决什么 | 堵点信号 | 拆刀依据 |
|---|---|---|---|
| 单体分层（MVC） | 让代码"够用"、分层好维护 | 代码膨胀、改动牵一发 | 技术横切 |
| 模块化单体 | 让代码"按业务切" | 层与层粘连、上帝 Service | 业务纵切 |
| DDD 收编 | 让切刀"切得对" | 模块边界靠拍脑袋、内聚被切开 | BC / 聚合 |
| 微服务 | 让边界"独立成部署单元" | 需要独立伸缩 / 团队 / 故障域 | 独立演进判据 |

---

## 第 1 段：单体分层（MVC）——为什么先"够用"

![12-02 单体分层 MVC 的得与失]({{ site.baseurl }}/assets/svg/12-02-单体分层MVC得与失.svg)

**分层的价值（为什么几乎所有项目都以 3 层起步）**：

- 依赖单向：Web → 业务 → 数据，好测、好替换
- 关注点分离：改接口不影响存储，换库不动业务
- 团队分工：前端 / 后端 / 数据各管一层，早期完全够用
- 入门成本低：一个 Controller 就能起一个功能

**技术分层的祸根（横向截断业务）**：

- 一个业务"点表下发"被拆到 4 个层，改需求要跨 4 处
- Service 层越滚越胖 → "上帝 Service"，所有人的业务都塞进去
- 层间只见技术不见业务：Controller / Mapper 代码量超过真正的领域逻辑
- 模块无边界：谁都 import 谁，改一个 Service 牵动全应用

**演进触发信号**：一次需求改动要跨 3+ 层、测试全回归、部署全量。

**分水岭**：技术分层是"横切"，业务模块是"纵切"。演进不是推翻分层，而是把分层**下沉到每个业务模块内部**。

> 你的网关对照：`PointController / PointService / PointMapper` 应聚成一个"点位"纵向模块，而非散落的横向切片。

## 第 2 段：模块化单体——切刀方向决定生死

![12-03 模块化单体与依赖治理]({{ site.baseurl }}/assets/svg/12-03-模块化单体与依赖治理.svg)

**错误的切法：横向切成 4 个大分层包**——`controller 包 / service 包 / mapper 包 / common 包`。这换汤不换药：只是把"包"改成"模块"，依赖依旧无界，service 层依然是上帝类。判据：**按删除测试失败**——删了一个模块，别的全红。

**正确的切法：纵向按业务特性切**——`point 模块 / device 模块 / alarm 模块`，每个模块内部自含 controller → service → mapper。分层保留但"下沉"到模块内部；模块之间只见接口不见实现。判据：删整个 point 模块，其余模块不受牵连（删除测试通过）。

**依赖方向由原则约束**：复用笔记 10（ADP / SDP / SAP）与笔记 11（D 值度量 + ArchUnit 执法），让"模块边界 = 编译期依赖 + 运行期审计"。

**模块化单体的自洽闭环（为何仍不是终局）**：

- 代价小：仍是单进程单库，事务、调用、部署照旧——**绝大多数团队止步于此且正确**
- 剩余堵点：① 切刀靠经验未必正确，可能把强内聚业务切开 ② 模块间仍共享 DB 与事务
- 由此引出 DDD：BC / 聚合告诉你"边界到底划在哪"，让切刀从拍脑袋变成有依据

> 一句话：模块化是"切"的动作，DDD 是"切对"的依据。

## 第 3 段：DDD 收编——给切刀装一套判据

![12-04 DDD 收编边界切分工具]({{ site.baseurl }}/assets/svg/12-04-DDD收编边界切分工具.svg)

**战略设计：BC 限界上下文（切成几个模块的依据）**：

- 一个领域内的自治语言与一致性范围
- 判定：同一术语在不同上下文含义不同 → 必须拆 BC（你网关的"站点上报" vs 运维的"站点"就不同）
- 切分判据：语言边界 + 一致性边界 + 团队边界 → 每个 BC 就是"模块化"那个模块的内核

**战术设计：聚合与聚合根（模块内切得对不对的最小单元）**：

- 聚合 = 一组"必须一起变"的对象，统一入口 = 聚合根
- 一致性边界：聚合内事务内完成，跨聚合只靠最终一致
- 判定原子性：改 A 不改 B 会出问题 → A/B 同一聚合

**一致性边界 ↔ 事务**：聚合边界 = 事务边界，一次请求改一个聚合根；跨聚合写不要硬塞大事务，用最终一致。**这是 DDD 与 L2 事务课的链接点**。

**落地组件（模块内部再纵切）**：

| 层 | 职责 | 依赖方向 |
|---|---|---|
| interface / API | 对外契约（防腐层） | 最外层 |
| application | 用例编排 / 事务 | 向内调用 domain |
| domain | 实体 / 值对象 / 领域服务 | 核心，最稳定 |
| infra | Mapper / 外部依赖 | 实现 domain 声明的接口 |

- 依赖方向固定向内：API/App → domain → infra，由 domain 定义接口、infra 实现（依赖倒置，接笔记 09 的 DIP）
- **仓储（Repository）**：domain 与 infra 的桥。domain 只声明"我要存什么"，实现交 infra → 换库不动领域
- **防腐层（Anti-Corruption）**：隔离外部系统，上游变化不污染你的 domain 语言（对接 TDengine / 第三方走它）

## 第 4 段：推演——从领域边界到服务边界

![12-05 领域边界到服务边界推演]({{ site.baseurl }}/assets/svg/12-05-领域边界到服务边界推演.svg)

**第 1 步 · 找候选服务**：每个 BC = 一个候选服务（语言自治）。你网关候选：采集服务 / rule 规则服务 / config 点位配置服务 / alarm 告警服务（每个都是独立 BC）。

**第 2 步 · 独立演进判据**：这个 BC 的改动频率是否独立于其他？是否要独立团队 / 独立部署 / 独立扩展？

**第 3 步 · 拆与不拆的判据（核心）**：

- 不拆的信号：改动联动、强数据耦合
- 拆的信号：独立伸缩、独立部署、独立故障域
- 反模式：为技术炫技而拆；拆完互相调用频繁

**常见拆错，都是没守住判据**：

1. "按代码体积拆"：把大 Service 从中间一刀切 → 切成两个互相频繁调用的服务，网络延迟代替方法调用
2. "共享同一张表拆成服务"：两个 BC 强共库 → 拆开后事务与一致性更糟
3. "为了微服务而微服务"：单机就能扛住，纯增成本
4. 正确样板：采集服务（高吞吐、需水平伸缩）拆出；config 服务（低频、需强一致）留单体，各自独立演进

> 一句话：BC 提供"切分边界"，判据决定"切不切"。边界清晰 ≠ 一定要拆，独立演进才是拆的理由。

## 第 5 段：拆分后的代价 → 保障体系补位

（架构决策部分，不用图中展开 L4 中间件实现细节，此处收敛到"拆完缺什么、补什么"的清单）

![12-06 拆分保障与网关演进落地]({{ site.baseurl }}/assets/svg/12-06-拆分保障与网关演进落地.svg)

一旦拆成多服务，失去的单体内建要逐项补位：

| 缺失的单体内建 | 补位手段 | 状态 |
|---|---|---|
| 本地事务 | L4 分布式事务 | 点到为止（你暂不看） |
| 直接调用 | 服务发现 / 网关 / 超时熔断 | L4 中间件，暂不展开 |
| 调用链 | 可观测性三支柱 | ✅ 已学（复用笔记 07） |
| 接口契约 | API 契约 / 防腐层版本管理 | 本课已讲外层契约 |
| 部署与故障域 | 容器化编排 / 独立限流隔离 | 架构决策层面理解即可 |

> 结论：每拆一步，必须先把"拆完缺什么"补上，否则只徒增复杂度。

## 第 6 段：你的网关——单体到多实例的最短路径

![12-06 拆分保障与网关演进落地]({{ site.baseurl }}/assets/svg/12-06-拆分保障与网关演进落地.svg)（图同第 5 段）

**阶段 A · 先模块化（今天就能做）**：Vert.x 单体按 BC 拆模块，`point / device / alarm` 各自成模块，依赖下移 + ArchUnit 执法。成本低、立即可回。

**阶段 B · 再独立伸缩（看需求触发）**：把"采集"这个高吞吐 BC 拆为独立服务，多实例水平扩展；低频强一致 BC（config）保持单体。

**阶段 C · 保障先行（贯穿）**：任何一步拆分，都先铺可观测性三支柱，再用 L4 中间件补事务 / 发现 / 限流。

**判据重温**：采集服务"改动频率独立 + 需伸缩" → 可拆；config 服务"强一致 + 低频" → 留在单体最合适。你网关的合理终态很可能是：**单体优先，个别 BC 弹性外拆**。

## 全课小结：一条决策链

① 单体分层 → 够用但业务横切
② 模块化 → 按业务纵切，依赖用原则 + 度量执法
③ DDD → BC/聚合给出"切对"判据，仓储/防腐层隔离内外
④ 推演 → BC 定位候选服务，"独立演进"判据决定拆不拆
⑤ 保障 → 拆完缺什么补什么，可观测性/契约先行
⑥ 你网关 → 单体优先 + 采集 BC 弹性外拆
