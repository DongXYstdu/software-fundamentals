# 模块划分与依赖治理（L7 结构软实力 · 第二课）
## 1. 模块是什么——粒度光谱与"边界强制力"

### 1.1 模块的定义

> **模块 = 一个有明确边界的单元，内部细节对外隐藏，对外只暴露契约。**

这个定义和 09 课讲类、讲接口时用的是同一套语言——"边界、隐藏、契约"。**模块划分就是 SRP 在更大粒度上的应用**，09 课的尺子（变化轴、Ca/Ce、主序列）在本课全部继续有效。

### 1.2 粒度光谱：从类到微服务

```
类/接口 ──> 包 ──> Maven 模块 ──> 部署单元(jar/war) ──> 微服务
  │          │          │                │                 │
 访问修饰符  包可见性   编译期依赖声明    进程内整体部署     网络+独立进程
 （最弱）                                    （最强）
```

| 粒度 | 强制机制 | 越界的难度 | 划错的代价 | 调整边界的成本 |
|---|---|---|---|---|
| 类 | `private`/`public` | 低 | 低 | 极低 |
| 包 | `package-private` 可见性 | 低（import 就能越界） | 低 | 低 |
| **Maven 模块** | **编译期依赖声明** | **中（不声明依赖就编译不过）** | **中** | **中** |
| 部署单元 | 进程内整体启动 | — | 中 | 中 |
| 微服务 | 网络 + 独立进程 + 独立数据源 | 高 | **高** | **极高** |

### 1.3 核心洞察：强制力越强的边界越可信，但也越贵

- **包边界是"君子协定"**：`package-private` 挡不住决心越界的人，把类改成 `public` 就能跨包调用。只靠包隔离的 DDD 四层，"领域层不依赖基础设施层"随时可能被悄悄破坏
- **Maven 模块边界是"编译期执法"**：模块 A 想调用模块 B 的类，必须先在 pom 里声明依赖，否则编译直接失败。依赖方向、禁止循环可以交给构建工具强制执行
- **微服务边界是"物理执法"**：进程隔离 + 网络调用，想绕过都难。但一次方法调用变成网络请求，本地事务变成分布式事务

选型经验：

> **能用编译期边界（Maven 模块）解决的隔离问题，不要升级到进程边界（微服务）。**

### 1.4 模块化单体：网关项目的甜蜜点

```
┌─────────────── 一个部署单元（单进程，部署简单）───────────────┐
│                                                              │
│   ┌────────┐   ┌────────┐   ┌────────┐   ┌────────────┐    │
│   │设备模块 │   │告警模块 │   │能耗模块 │   │ 采集驱动模块 │    │
│   └───┬────┘   └───┬────┘   └───┬────┘   └──────┬─────┘    │
│       │            │            │               │            │
│       └────────────┴─────┬──────┴───────────────┘            │
│                          ▼                                   │
│                 ┌─────────────────┐                          │
│                 │  领域核心模块     │  ← 被依赖最多，最稳定     │
│                 │（模型+接口契约）  │    （09 课主序列左端）     │
│                 └─────────────────┘                          │
└──────────────────────────────────────────────────────────────┘
```

- **单体的好处**：一个进程部署、本地方法调用、本地事务、断点调试——客户现场运维友好
- **模块化的好处**：编译期边界强制依赖方向；**将来真要拆微服务，模块边界就是现成的切割线**（14 课展开）

"单模块 + 包混乱"的项目直接跳微服务 = 把混乱复制成 N 份分布式混乱——**先模块化，再谈服务化**。

### 1.5 起点判断：三种常见起点

| 现状 | 诊断 | 路径 |
|---|---|---|
| 单模块，包按 controller/service/dao 分层，业务代码互相穿插 | 边界只有"层"，没有"业务能力" | 先做 11 课：包内按业务能力重组 |
| 单模块，包已按业务分，但包间调用随意 | 业务能力边界有了，但没有执法 | **本课主战场**：稳定包边界升级为 Maven 模块 + 工具执法 |
| 已多模块，但循环依赖、common 大杂烩 | 有模块没治理 | 直接进三原则 + 拆环 + 工具执法 |

关键次序：**包边界没理顺就拆模块，等于把混乱固化进编译期结构**。11 课（分包）逻辑上是本课的前置侦察。

## 2. 横向划分 vs 纵向划分——刀往哪个方向切

![10-01 横向划分 vs 纵向划分]({{ site.baseurl }}/assets/svg/10-01-横向划分vs纵向划分.svg)

### 2.1 两种切法

**横向划分（按技术层切）**：

```
gateway-web（所有 Controller）/ gateway-service（所有业务）
/ gateway-dao（所有 Mapper）/ gateway-common（所有公共类）
每个模块内部：设备、告警、能耗的代码混在一起
```

**纵向划分（按业务能力切）**：

```
设备模块 / 告警模块 / 能耗模块（各自含 API+逻辑+持久化）
              ↓ 都依赖
      领域核心（共享契约）
```

一句话区分：**横向切出来的是"技术同乡会"，纵向切出来的是"业务独立团"**。

### 2.2 评判标准：一个需求动几个模块

需求：**"给空压机加一条告警规则——排气温度连续 3 分钟超 80℃ 触发高温告警"**。

**横向划分下的改动路径**：

| 步骤 | 改动位置 | 所属模块 |
|---|---|---|
| 1 | 新增规则配置接口 | `gateway-web` |
| 2 | 规则判断逻辑 + 3 分钟窗口状态 | `gateway-service` |
| 3 | 规则持久化 Mapper | `gateway-dao` |
| 4 | 告警常量 | `gateway-common` |

**4 个模块全动**。更糟的是：这条告警规则的代码和设备的、能耗的代码在同一个模块里继续混居。

**纵向划分下的改动路径**：

| 步骤 | 改动位置 | 所属模块 |
|---|---|---|
| 1–3 | 接口 + 逻辑 + 持久化 | `alarm` 模块 |
| 4 | （只读）从领域核心拿 `DeviceSnapshot` 契约 | 只依赖，不修改 |

**只动 1 个模块**。设备、能耗模块的开发者完全无感，甚至不用重新编译。

### 2.3 横向划分为什么流行又有害

| 横向的诱惑 | 真相 |
|---|---|
| "同类代码放一起，好找" | 好找的是技术同类，但需求从来不是按技术层来的 |
| "和三层架构教科书一致" | 三层是**模块内部**的分层，不是模块之间的划分依据 |
| "分工清晰" | 现代团队按业务域分工，不按技术层分工 |
| "拆起来简单" | 省掉的思考会在每次需求里加倍偿还 |

结构性危害（用 09 课尺子诊断）：

1. **变化轴被切断**：一条业务需求的变化轴被硬切成三段落在三个模块——SRP 反其道而行
2. **模块边界与需求边界垂直相交**：每个需求横穿所有层模块，边界成了每次改动的必经收费站
3. **common 必然膨胀**：跨层共享的模型无处安放——09 课痛苦区的标准成因

### 2.4 纵向划分为什么对：边界与变化轴平行

```
横向划分：需求的变化轴 ⟂ 模块边界  → 每次需求横穿所有模块
纵向划分：需求的变化轴 ∥ 模块边界  → 每次需求落在单个模块
```

领域核心模块只放**多个业务能力都依赖、且变化频率低**的东西（`DeviceSnapshot`、`AlarmRecord` 等契约模型和跨模块接口）。按 09 课主序列必须高抽象、高稳定（Ca 大 → I 低 → A 高）。

### 2.5 横向划分的合法场景

| 场景 | 理由 |
|---|---|
| **纯技术组件**：common（工具类）、starter（自动装配）、驱动适配层 | 变化轴本来就是技术性的，按技术切正好平行于变化轴 |
| **业务极简的早期项目**：只有一个业务域 | 没有多条业务能力可切；一旦长出第二条业务能力就该转纵向 |

口诀：**切模块时问"这一刀切的是变化轴还是横断面？"——切变化轴（纵向）是对的，切横断面（横向）只留给技术组件。**

### 2.6 折中陷阱：混合划分

```
gateway-web / gateway-service / gateway-dao   ← 横向三层
gateway-alarm                                  ← 纵向一个告警模块
```

最坏的组合：两套边界互相打架，没有任何一套能完整描述系统。通常是"拆了一半停下来"的遗迹，治理第一步就是收敛成一种。

## 3. 边界怎么画——业务能力识别与共享模块准入

### 3.1 识别业务能力：两问法

> **问题 1（变化轴问）**：它有没有独立的"变化原因"——独立的需求来源方、独立的演进节奏？
> **问题 2（数据问）**：它有没有自己独占的数据——**只有它写、别人只读**？

| 问题 1 | 问题 2 | 结论 |
|---|---|---|
| ✅ | ✅ | **独立成模块** |
| ✅ | ❌ | 模块内的独立组件 |
| ❌ | ✅ | 数据托管给相邻模块，逻辑并入 |
| ❌ | ❌ | 并入最相关的模块，或进技术公共层 |

问题 2 的关键词是"**独占写**"——一个能力如果连自己的数据都没有，它的"独立"只是逻辑上的幻觉。

### 3.2 实战推演：网关候选能力过筛

| 候选能力 | 问题 1 | 问题 2 | 结论 |
|---|---|---|---|
| 设备管理 | ✅ | ✅ 设备台账只有它写 | **模块** |
| 采集驱动 | ✅ 协议变化频繁 | ⚠ 只产出快照不落地 | **模块**（特例） |
| 告警 | ✅ | ✅ 规则表+告警记录 | **模块** |
| 控制下发 | ✅ | ✅ 指令队列/控制日志 | **模块** |
| 能耗统计 | ✅ | ✅ 统计结果 | **模块** |
| 用户权限 | ❌ | ✅ | 并入平台基础模块 |
| 日志审计 | ❌ | ❌ | 技术公共层 |

**采集驱动的特例**：过不了问题 2，但问题 1 极强——协议适配是全系统变化最频繁的轴。按口诀裁决：**它本身就是一条纯变化轴，必须隔离**。定位是"易变实现区"（主序列右端，I 高 A 低），允许频繁变动，只要不污染别人。

### 3.3 边界争议裁决：三条规则依次用

**规则 1：单一写入者原则（Single Writer）**——一张表、一个聚合，只允许一个模块写。谁写谁拥有。

```
争议："设备在线状态"归设备模块还是采集模块？
裁决：在线状态写入设备表 → 设备模块拥有
      采集发现失联 → 通过契约接口通知设备模块更新（不直接写设备表）
```

**规则 2：变化频率归属**——两边都不写（纯读取/计算），归变化更频繁的一侧。

```
争议："告警级别字典"归告警模块还是领域核心？
裁决：级别会随业务扩展 → 归告警模块；领域核心只保留最小契约
```

**规则 3：稳定侧托管**——前两条裁决不了，放更稳定的一侧，以只读契约暴露。宁可放错到稳定侧，不可放错到易变侧。

### 3.4 共享模块准入：common 的四条门槛

| 门禁 | 规则 | 反例 |
|---|---|---|
| 1. 三方共用 | 至少 **3 个**模块真实依赖它 | 只有两个模块用的工具 → 先放其中一方 |
| 2. 稳定 | 可预见不随业务需求变化 | "告警级别常量"进 common ❌ |
| 3. 无业务语义 | 纯技术：字符串、加解密、协议帧工具 | `DeviceUtils`（带业务判断）❌ |
| 4. 零出度 | common 不依赖任何业务模块（Ce = 0） | common 里引用告警枚举 ❌ |

门禁 1 即**"三则上提"**：两个模块想共享代码时先复制一份各自留着；第三个消费者出现再上提。复制的短期成本远低于错误共享的长期耦合成本——与 09 课"第二次变化才抽象"同节奏。

### 3.5 关键区分：common ≠ 领域核心

| | `common`（技术公共层） | `domain-core`（领域核心） |
|---|---|---|
| 内容 | 无业务语义的工具、基类、协议帧解析 | **有**业务语义的契约：模型 + 跨模块接口 |
| 变化原因 | 技术升级 | 业务模型演进（频率低） |
| 09 课坐标 | A 低、I 低——允许（没有业务逻辑） | **A 高、I 低**——主序列左端，全系统稳定锚点 |
| 准入门槛 | 四条门禁 | 只有"≥2 个业务模块依赖的模型/接口"能进 |

记忆锚点：**common 装"怎么实现"的公共件，domain-core 装"业务是什么"的公共契约**。前者越薄越好，后者是全系统的脊椎。

### 3.6 粒度体检：两个信号

| 信号 | 诊断 | 动作 |
|---|---|---|
| 两个模块**总是一起改** | 边界切在了变化轴中间 | 合并 |
| 一个模块内部有两拨需求**互不相干地改** | 内部还藏着没拆开的轴 | 继续拆 |

**边界不是一次画对的，是靠需求反馈迭代收敛的**——第一版画七八成，跑三个月需求，用信号修正。

## 4. 依赖方向三原则——ADP / SDP / SAP

![10-02 依赖方向三原则]({{ site.baseurl }}/assets/svg/10-02-依赖方向三原则.svg)

三条原则回答三个递进的问题：**能不能成环 → 箭头指向谁 → 被指向的模块长什么样**。

### 4.1 ADP：无环依赖原则

> **模块依赖图中不允许出现环。**

一票否决，没有商量余地。环的三个连锁后果：

1. **编译耦合**：改一方，另一方必须重新编译 → 两个模块焊成一个
2. **发布耦合**：互为构建前提，谁都无法单独发布
3. **理解耦合**：读任何一边都必须同时理解另一边

环的本质是**两个模块互相需要对方的"现在"**，而健康依赖应该是"我依赖你的**稳定契约**"。发现环，先拆环，其他治理都往后排。

### 4.2 SDP：稳定依赖原则

> **依赖箭头必须指向更稳定的模块。**

用 09 课的 I 值定义"稳定"：I 越低越稳定。

```
依赖方向：不稳定模块 ──────> 稳定模块
              （I 高）          （I 低）
```

用"改动波及"推一遍：

- 让"随便变的"依赖"少变的"：易变方天天改，稳定方纹丝不动，**改动被吸收在末端**
- 反过来：易变方一改，稳定方跟着改，再波及稳定方的所有下游——**改动被放大到全系统**

网关依赖图：

```
   采集驱动（I≈1，天天变协议）
        │
        ▼
   告警（I≈0.7）──┐
   能耗（I≈0.7）──┼──> 设备管理（I≈0.4）──> domain-core（I=0，最稳定）
   控制（I≈0.7）──┘
```

箭头全部**从易变指向稳定**，domain-core 是全图汇点（sink），没有任何箭头从它出发。

**实操推论**：发现一个模块想依赖比自己更不稳定的模块时，几乎总是边界画错的信号——回去重画，而不是硬连。

### 4.3 SAP：稳定抽象原则

> **模块越稳定，越应该由抽象构成。**

逻辑链：

1. 稳定模块被广泛依赖 → 必须少变
2. 具体实现最容易变 → 稳定模块里不能放具体实现
3. 接口/抽象类描述"做什么"而非"怎么做" → 天然少变
4. 所以：**稳定模块 = 接口 + 契约模型，具体实现全部下沉到不稳定模块**

这正是 09 课 DIP 在模块粒度的投影：`domain-core` 放 `TagReader`、`AlarmSink`、`DeviceSnapshot`，`KafkaAlarmSink`、`ModbusPoller` 住在 I≈1 的末端模块。

**实操推论**：被三个模块依赖却 A≈0 的模块，要么抽接口，要么降级它的被依赖数。

### 4.4 三原则的因果链

```
ADP（底线）：先保证图里无环
     │ 无环，图才有"方向"可言
     ▼
SDP（方向）：让箭头从不稳定指向稳定
     │ 有了方向，才知道谁"被依赖"
     ▼
SAP（内容）：被依赖的模块必须高抽象
     │ 抽象才能真稳定，方向才站得住
     ▼
  回到 09 课主序列：每个模块都落在 A + I = 1 上
```

**ADP 保结构、SDP 定方向、SAP 定内容**——三者合起来就是主序列在模块图上的完整表达。

### 4.5 体检

| 检查项 | 方法 | 网关示例结论 |
|---|---|---|
| ADP | 拓扑排序，排不出序 = 有环 | 采集→告警若互调即成环 |
| SDP | 每个箭头检查：起点 I > 终点 I？ | 能耗→domain-core ✓（0.7→0） |
| SAP | 入度高的模块查 A 值 | domain-core A≈0.8 ✓ |

## 5. 循环依赖专题——三种拆环手法

![10-03 循环依赖三种解法]({{ site.baseurl }}/assets/svg/10-03-循环依赖三种解法.svg)

### 5.1 环是"症状"，不是"病"

| 病因 | 表现 | 对症手法 |
|---|---|---|
| 抽象缺失 | 两模块确实要协作，但直接调用对方具体类 | 手法一：上提抽象 |
| 边界画错 | 两模块本就是一回事，被硬切成两块 | 手法二：合并模块 |
| 时序耦合 | 一方要在"事后"通知另一方，却用了同步直调 | 手法三：事件解耦 |

拆环的正确姿势不是"随便砍一条边"，而是**先诊断病因，再选手法**。

### 5.2 一个真实的环：采集 ↔ 告警

```
        ┌────────────────────────────┐
        │                            │
        ▼                            │
   ┌─────────┐    推送快照     ┌─────────┐
   │ 采集模块 │ ─────────────> │ 告警模块 │
   └─────────┘                └─────────┘
        ▲                            │
        └────────────────────────────┘
             告警触发后要求加密采集
```

### 5.3 手法一：上提抽象（DIP 拆环）——最常用

**适用病因：抽象缺失。** 把"被需要的那个能力"抽成接口，放进稳定层。

```java
// domain-core：定义"采集频率控制"的抽象
public interface PollingRateController {
    void increaseRate(String deviceId);
    void restoreRate(String deviceId);
}

// 采集模块：实现这个接口
public class ModbusPollingRateController implements PollingRateController {
    public void increaseRate(String deviceId) { /* 调快该设备轮询 */ }
    public void restoreRate(String deviceId)  { /* 恢复正常频率 */ }
}

// 告警模块：只依赖 domain-core 里的接口，不认识采集模块
public class HighTempAlarmHandler {
    private final PollingRateController rateController;   // ← 注入接口

    public HighTempAlarmHandler(PollingRateController rateController) {
        this.rateController = rateController;
    }

    public void onTrigger(String deviceId) {
        rateController.increaseRate(deviceId);   // 只调抽象
    }
}
```

拆完后：`采集 ──实现──> PollingRateController <──依赖── 告警`，无环，箭头都指向稳定层。环被拆成"两个模块都依赖一个更稳定的第三方"。

### 5.4 手法二：合并模块（边界纠错）——最容易被忽略

**适用病因：边界画错。** 双向、高频、细粒度的互相依赖说明它们根本不是两个模块。

判断"该合并"的信号：

| 信号 | 说明 |
|---|---|
| 两模块总是一起改 | 每次需求都同时动它们 |
| 互相调用点多且杂 | 抽一两个接口根本兜不住 |
| 共享大量内部数据结构 | 不是契约模型，是实现细节 |

案例：如果"告警规则引擎"和"告警通知"被拆成两个模块，却互相高频调用、共享内部状态——合并成一个 `alarm` 模块，内部用包分层（`alarm.rule` / `alarm.notify`）。

> **记忆锚点**：抽接口能解决的环是"协作问题"，抽不动的环是"边界问题"。后者合并比硬拆更诚实。

### 5.5 手法三：事件解耦（异步替代同步）——治时序耦合

**适用病因：时序耦合。** 把同步调用改成**领域事件**——发布者发完即忘。

```java
// domain-core：定义事件（契约）
public record AlarmTriggeredEvent(String deviceId, String alarmType, Instant at) {}

// 告警模块：只发布事件，不认识采集模块
public class AlarmEvaluator {
    private final EventPublisher publisher;

    public void evaluate(DeviceSnapshot snapshot) {
        if (isHighTemp(snapshot)) {
            publisher.publish(new AlarmTriggeredEvent(
                snapshot.deviceId(), "HIGH_TEMP", Instant.now()));
        }
    }
}

// 采集模块：订阅事件，自己决定怎么响应
public class AlarmReactionListener {
    @EventListener
    public void on(AlarmTriggeredEvent event) {
        if ("HIGH_TEMP".equals(event.alarmType())) {
            pollingController.increaseRate(event.deviceId());
        }
    }
}
```

与手法一的本质区别：

| | 手法一（接口） | 手法三（事件） |
|---|---|---|
| 耦合残留 | 仍依赖"能力的抽象" | 连抽象都不依赖，只依赖事件契约 |
| 调用语义 | 同步、可能要返回值 | 异步、发完即忘 |
| 适用 | "我需要你为我做件事" | "我发生了件事，谁关心谁来" |
| 代价 | 低 | 中（需事件总线，调试链路变长） |

**选型口诀**：需要**确定性响应**（要结果、要顺序）→ 接口；只是**广播事实** → 事件。08 课"跨聚合协作用领域事件"正是此手法的业务版。

### 5.6 选择决策树

```
发现循环依赖
     │
     ├─ 互相调用点多、总一起改、共享内部结构？
     │        │ 是 ──> 手法二：合并模块（边界画错了）
     │        │ 否
     │        ▼
     ├─ 需要确定性响应（要结果/要顺序）？
     │        │ 是 ──> 手法一：上提抽象（DIP）
     │        │ 否
     │        ▼
     └─ 只是"事后广播"，多个潜在响应者？
              │ 是 ──> 手法三：事件解耦
```

三种手法不互斥，复杂系统常常**混用**。

## 6. ArchUnit 实战——把依赖规则写成单测

### 6.1 为什么需要"架构测试"

文档约束靠自觉，编译约束靠工具。Maven 模块边界只能管到模块粒度——模块**内部**的包之间、"谁该依赖谁"的方向性规则，编译器管不了。ArchUnit 让你**把架构规则写成 JUnit 测试**——规则被违反时 `mvn test` 直接红。架构规则从此是"跑出来的"，不是"说出来的"。

### 6.2 快速上手

```xml
<dependency>
    <groupId>com.tngtech.archunit</groupId>
    <artifactId>archunit-junit5</artifactId>
    <version>1.3.0</version>
    <scope>test</scope>
</dependency>
```

```java
@AnalyzeClasses(packages = "com.example.gateway")
public class ArchitectureTest {

    @ArchTest
    static final ArchRule 领域层不得依赖基础设施层 =
        noClasses()
            .that().resideInAPackage("..domain..")
            .should().dependOnClassesThat()
            .resideInAPackage("..infrastructure..");
}
```

一旦有人在领域层写了 `import ...infrastructure.KafkaAlarmSink`，测试立刻失败，并报告具体哪个类、哪一行违规。

### 6.3 网关项目的五条规则

包结构假设：`com.example.gateway.{domain, collect, alarm, energy, common, infrastructure}`。

**规则 1：领域层不依赖任何外层（DIP 执法）**

```java
@ArchTest
static final ArchRule domain_is_the_core =
    noClasses()
        .that().resideInAPackage("..domain..")
        .should().dependOnClassesThat()
        .resideInAnyPackage("..collect..", "..alarm..",
                            "..energy..", "..infrastructure..");
// domain-core 是全图汇点：只进不出（SDP）
```

**规则 2：业务模块之间不得直接依赖（边界执法）**

```java
@ArchTest
static final ArchRule 业务模块只能通过domain协作 =
    slices().matching("com.example.gateway.(*)..")
        .namingSlices("$1 模块")
        .should().notDependOnEachOther()
        .ignoreDependency(resideInAPackage("..domain.."), anyClass())
        .ignoreDependency(anyClass(), resideInAPackage("..common.."));
```

**规则 3：模块间无环（ADP 执法）**

```java
@ArchTest
static final ArchRule 模块依赖图无环 =
    slices().matching("com.example.gateway.(*)..")
        .should().beFreeOfCycles();
```

**规则 4：common 零出度（门禁 4 执法）**

```java
@ArchTest
static final ArchRule common不得依赖任何业务模块 =
    noClasses()
        .that().resideInAPackage("..common..")
        .should().dependOnClassesThat()
        .resideInAnyPackage("..domain..", "..collect..",
                            "..alarm..", "..energy..");
```

**规则 5：分层注解归位**

```java
@ArchTest
static final ArchRule REST接口只能出现在接入层 =
    classes()
        .that().areAnnotatedWith(RestController.class)
        .should().resideInAPackage("..api..");

@ArchTest
static final ArchRule MyBatis的Mapper只能出现在基础设施层 =
    classes()
        .that().areAnnotatedWith(Mapper.class)
        .should().resideInAPackage("..infrastructure..");
```

五条规则合起来：**边界（规则 2）、方向（规则 1）、无环（规则 3）、common 门禁（规则 4）、层内归位（规则 5）**。

### 6.4 存量项目：FreezingArchRule 增量治理

```java
@ArchTest
static final ArchRule 领域层不得依赖基础设施层_增量 =
    FreezingArchRule.freeze(
        noClasses()
            .that().resideInAPackage("..domain..")
            .should().dependOnClassesThat()
            .resideInAPackage("..infrastructure..")
    );
```

| 场景 | 普通规则 | 冻结规则 |
|---|---|---|
| 存量违规（首次运行时已存在） | ❌ 测试红 | ✅ 记录进 `archunit_store/`，测试绿 |
| **新增违规** | ❌ 测试红 | ❌ **测试红** |
| 存量违规被修复 | ✅ 绿 | ✅ 自动从记录中移除 |

治理节奏：**先冻结 → 新代码零容忍 → 存量违规随需求顺手修 → 记录文件只减不增**。`archunit_store/` 提交进 Git，消减进度肉眼可见。

### 6.5 落地要点

| 要点 | 说明 |
|---|---|
| 跑在哪 | 普通单测，`mvn test` 自动带上；CI 天然拦截 |
| 规则放哪 | 单模块放 `src/test/java`；多模块建议建 `architecture-tests` 模块 |
| 规则数量 | 从 3–5 条起步，**每条对应一个真实踩过的坑** |
| 命名 | 变量名直接用中文描述，报告可读性第一 |
| 与 Enforcer 分工 | ArchUnit 管类/包级方向；Enforcer 管模块级构建约束 |

## 7. Maven 工程执法——Enforcer 与多模块骨架

### 7.1 分工

| | ArchUnit | Maven Enforcer |
|---|---|---|
| 执法粒度 | 类、包、注解 | **Maven 模块、依赖坐标** |
| 执法时机 | `mvn test` | `mvn validate`（**构建最早期**） |
| 典型规则 | 领域层不依赖基础设施 | 模块间无环、版本收敛、禁 SNAPSHOT |
| 违规成本 | 测试红 | **构建直接失败，连编译都不开始** |

**在多模块项目里，pom.xml 的 `<dependency>` 声明就是依赖图的成文化**。

### 7.2 网关多模块骨架

```
gateway-parent/                    ← 父 pom（packaging=pom）
├── gateway-domain-core            ← 领域核心（全图汇点，I=0）
├── gateway-common                 ← 技术公共层（四门禁把守）
├── gateway-collect                ← 采集驱动（易变实现区）
├── gateway-alarm                  ← 告警
├── gateway-energy                 ← 能耗
├── gateway-infrastructure         ← 基础设施：Kafka/MyBatis 实现
├── gateway-app                    ← 装配模块（组合根）
└── architecture-tests             ← ArchUnit 规则
```

**`gateway-app` 是组合根（Composition Root）**：全工程唯一允许依赖所有模块的地方。Spring Boot 启动类和 Bean 装配都在这里——`AlarmService` 注入 `KafkaAlarmSink` 的"接线"动作全部发生在此。呼应 09 课 DIP：**业务模块互相不认识，由组合根负责接起来**。也是唯一打可执行 jar 的模块。

### 7.3 父 pom：dependencyManagement 统一版本

```xml
<!-- gateway-parent/pom.xml -->
<packaging>pom</packaging>

<modules>
    <module>gateway-domain-core</module>
    <module>gateway-common</module>
    <module>gateway-collect</module>
    <module>gateway-alarm</module>
    <module>gateway-energy</module>
    <module>gateway-infrastructure</module>
    <module>gateway-app</module>
    <module>architecture-tests</module>
</modules>

<dependencyManagement>
    <dependencies>
        <dependency>
            <groupId>com.example</groupId>
            <artifactId>gateway-domain-core</artifactId>
            <version>${revision}</version>
        </dependency>
        <dependency>
            <groupId>com.alibaba.fastjson2</groupId>
            <artifactId>fastjson2</artifactId>
            <version>2.0.52</version>
        </dependency>
    </dependencies>
</dependencyManagement>
```

```xml
<!-- gateway-alarm/pom.xml：子模块引依赖不写版本 -->
<dependencies>
    <dependency>
        <groupId>com.example</groupId>
        <artifactId>gateway-domain-core</artifactId>
        <!-- 无 version：由父 pom 管理 -->
    </dependency>
</dependencies>
```

**版本只在父 pom 声明一次**——"谁用了什么版本"从考古问题变成一眼可见。

### 7.4 Enforcer 三条规则

```xml
<plugin>
    <groupId>org.apache.maven.plugins</groupId>
    <artifactId>maven-enforcer-plugin</artifactId>
    <version>3.5.0</version>
    <dependencies>
        <dependency>
            <groupId>org.codehaus.mojo</groupId>
            <artifactId>extra-enforcer-rules</artifactId>
            <version>1.8.0</version>
        </dependency>
    </dependencies>
    <executions>
        <execution>
            <id>enforce-module-rules</id>
            <goals><goal>enforce</goal></goals>
            <configuration>
                <rules>
                    <!-- 规则1：模块依赖图无环（ADP 执法） -->
                    <banCircularDependencies/>
                    <!-- 规则2：依赖版本收敛 -->
                    <dependencyConvergence/>
                    <!-- 规则3：发布构建禁止依赖 SNAPSHOT -->
                    <requireReleaseDeps>
                        <onlyWhenRelease>true</onlyWhenRelease>
                    </requireReleaseDeps>
                </rules>
                <fail>true</fail>
            </configuration>
        </execution>
    </executions>
</plugin>
```

| 规则 | 治理目标 | 违规场景 |
|---|---|---|
| `banCircularDependencies` | **ADP 一票否决** | collect 和 alarm 的 pom 互相依赖 → `mvn validate` 失败并打印环路径 |
| `dependencyConvergence` | 版本漂移 | 两个模块引不同版本 fastjson → 要求收敛 |
| `requireReleaseDeps` | 发布卫生 | 给客户的版本混入 SNAPSHOT → 拒绝出包 |

Enforcer 绑在 `validate` 阶段，**比编译还早**。

### 7.5 模块 pom 的依赖声明纪律

| 纪律 | 对应原则 | 示例 |
|---|---|---|
| 业务模块只声明对 `domain-core`（和 `common`）的依赖 | SDP | `gateway-alarm` 的 pom 里不允许出现 `gateway-collect` |
| 实现模块依赖 `domain-core`，反向不成立 | SAP/DIP | `gateway-infrastructure` 依赖 `domain-core`，反之禁止 |
| 只有 `gateway-app` 可以依赖全部模块 | 组合根唯一性 | 其他模块出现 `gateway-app` 依赖 = 违规 |

双层执法：**Enforcer 拦结构性错误，ArchUnit 拦代码级越界**——pom 里没声明依赖，代码里想 import 也编译不过。

## 8. 落地检查清单与全课收束

### 8.1 模块治理七步操作手册

```
第一步：定粒度 —— 判断起点落在光谱哪一档
第二步：定刀向 —— 业务模块纵向切，横向只留给技术组件
第三步：画边界 —— 两问法过筛 + 三规则裁决 + common 四门禁
第四步：定方向 —— ADP 无环 → SDP 指向稳定 → SAP 稳定者高抽象
第五步：拆环   —— 诊断病因：抽象缺失→接口；边界切错→合并；时序耦合→事件
第六步：立执法 —— ArchUnit 五规则（存量冻结）+ Enforcer 三规则 + 版本收敛
第七步：持续体检 —— "总一起改"→合并；"内部互不相干地改"→再拆；季度看 Ca 趋势
```

### 8.2 评审现场速查表

| 场景 | 检查项 |
|---|---|
| 新建模块提案 | 两问法过不过？（独立变化轴 + 独占写数据） |
| 新加模块间依赖 | 箭头是否从 I 高指向 I 低？会不会成环？ |
| 有类想进 common | 四门禁全过？ |
| 发现两模块互调 | 先诊断病因，别急着砍边 |
| pom 里加依赖 | 业务模块是否只依赖 domain-core？ |
| 架构测试红了 | 真违规还是冻结存量？存量随需求顺手修 |

### 8.3 一句话记住本课

> **模块边界与变化轴平行（纵向切），依赖箭头指向稳定与抽象（SDP+SAP），然后用构建工具把规则变成执法（ArchUnit + Enforcer）。**

三个关键词：**切对**（设计）、**指对**（纪律）、**守住**（工程）——三者缺一，模块划分就只是 PPT 上的框图。
