# IoC 容器与 Bean 生命周期
---

## 第 1 段：IoC 容器本质

![09-01 IoC 容器本质]({{ site.baseurl }}/assets/svg/09-01-IoC容器本质.svg)

### 1.1 IoC 反转了什么

- 传统写法：业务代码自己 `new` 依赖——**创建权 + 组装权在业务代码手里**
- IoC：两项权力移交给容器；业务代码只声明"我需要什么"
- **IoC（控制反转）** = 设计思想；**DI（依赖注入）** = 落地手段（构造器 / setter / 字段注入，首选构造器）

### 1.2 容器管理的是蓝图，不是对象

四步流水线：**配置源 → BeanDefinition（蓝图）→ 注册表 → 单例池**

- 配置源：`@ComponentScan` / `@Import` / `@Bean` 方法 / XML
- BeanDefinition = 元数据蓝图：类名、作用域、懒加载、构造参数、依赖关系
- **先管蓝图、后造对象**——蓝图层给了容器三个操作空间：条件过滤、作用域决策、依赖排序

### 1.3 @Conditional 的生效时刻（回填 08-03）

- 条件评估发生在 **②→③ 之间**（注册阶段）
- 条件不满足 → **蓝图直接丢弃，Bean 从未被创建**（不是创建后销毁）
- `--debug` 条件报告里 matched / not matched 判定的就是这个时刻
- 你 Starter 的 `@ConditionalOnProperty(matchIfMissing=true)`、`@ConditionalOnMissingBean` 都在这里评估

### 1.4 BeanFactory vs ApplicationContext

| 维度 | BeanFactory | ApplicationContext |
|---|---|---|
| 定位 | 最小 IoC 容器（地基） | 继承并扩展（精装房） |
| 实例化时机 | getBean() 时才创建（懒加载） | refresh() 预实例化所有非懒加载单例 |
| 额外能力 | 无 | 事件发布、国际化、资源加载、Environment |
| 场景 | 资源受限 | yudao / 网关实际使用 |

预实例化的生产价值：**配置错误启动期暴露**，而非运行期。

## 第 2 段：Bean 生命周期

![09-02 Bean 生命周期流水线]({{ site.baseurl }}/assets/svg/09-02-Bean生命周期流水线.svg)

### 2.1 实例化 ≠ 初始化（高频辨析）

- **实例化**：构造器创建裸对象，字段全 null，不能干活
- **初始化**：填充依赖 + 执行回调，能干活
- 循环依赖的解法正利用"实例化后、初始化完成前"的**半成品窗口期**

### 2.2 六阶段流水线

```
① 实例化（构造器裸对象）
② 属性注入（@Autowired / 构造器依赖）
③ Aware 回调（BeanNameAware 等）
④ 初始化（前置钩子 → InitializingBean/init-method → 后置钩子）
⑤ 就绪使用（放入单例池）
⑥ 销毁（@PreDestroy → DisposableBean）
```

### 2.3 四个干预点

| 干预点 | 位置 | 典型用途 |
|---|---|---|
| 实例化后 | ①→② | 三级缓存提前暴露半成品 |
| 注入后 | ②→③ | 属性加工 |
| **初始化前后** | ④ 内两个钩子 | @PostConstruct、AOP 代理、@Async |
| 销毁前 | ⑥ 前 | @PreDestroy 资源释放 |

**BeanPostProcessor** 是容器级扩展点，对所有 Bean 初始化前后各插一次手：
- `@PostConstruct` → CommonAnnotationBeanPostProcessor，**前置钩子**触发
- **AOP 代理** → AbstractAutoProxyCreator，**后置钩子**替换原对象
- `@Async` → 同理，后置钩子包代理

### 2.4 @PostConstruct 为什么能拿到注入完成的依赖

时序：② 属性注入完成 → ④ 前置钩子触发 @PostConstruct → 依赖已就绪，安全使用。

**推论（第 4 段伏笔）**：AOP 代理在后置钩子才生成，@PostConstruct 里自调用本类 @Transactional 方法**不走代理**（this 是原始对象）。

## 第 3 段：三级缓存解循环依赖

![09-03 三级缓存解循环依赖]({{ site.baseurl }}/assets/svg/09-03-三级缓存解循环依赖.svg)

### 3.1 三级缓存结构

| 级别 | 名称 | 存的内容 | 作用 |
|---|---|---|---|
| 一级 | singletonObjects | 成品（初始化完成） | getBean() 最终取用处 |
| 二级 | earlySingletonObjects | 早期对象（半成品，可能已是代理） | 保证工厂只调一次、引用唯一 |
| 三级 | singletonFactories | **ObjectFactory（工厂，不是对象）** | 把"要不要代理"的决策延迟 |

查询顺序：一级 → 二级 → 三级，命中即升级（三级命中 → 调工厂 → 结果放二级 → 删三级）。

### 3.2 A↔B 推演关键节点

1. A 实例化 → 包装成 ObjectFactory 放三级（半成品已可被引用）
2. A 注入发现需要 B → 去创建 B，A 挂起
3. B 实例化 → B 注入发现需要 A（循环闭合）
4. **三级命中 A 的工厂** → 调工厂：若 A 需要代理**此刻提前生成** → 放二级删三级
5. B 拿 A 早期引用完成初始化 → B 进一级，解救 A
6. A 拿成品 B 完成注入；若 ④ 已提前生成代理，后置钩子**直接复用**不包第二次
7. A 进一级删二级 → 循环依赖解除，B 持有的 A 与池中 A 是同一引用

### 3.3 为什么是三级不是二级（核心问题）

若只有两级，A 实例化后必须**立刻决定**早期池放原始对象还是代理：
- 放原始 → 需要代理时引用不一致
- 放代理 → 违背"代理在初始化后生成"的生命周期设计，且多数 Bean 无循环依赖，白白提前生成

三级的解法：**放工厂**。工厂不产生对象，只承诺"被调用时给出正确对象（原始或代理）"：
- 无循环依赖（多数）→ 工厂永不被调用，代理照常后置钩子生成，零开销
- 有循环依赖 → 工厂被调用那一刻才决定要不要代理，二级保证只调一次

**一句话**：三级缓存 = 半成品窗口期提前暴露引用 + 工厂把代理决策**延迟到必要时刻**（懒加载思想）。

### 3.4 两种无解情况

| 情况 | 原因 |
|---|---|
| 构造器循环依赖 | 实例化未完成，没东西可提前暴露 → 直接报错 |
| prototype 作用域 | 原型 Bean 不进缓存 → 无解 |

（字段 / setter 循环依赖可解：实例化与注入分两步，有窗口期。）

### 3.5 著名陷阱：@Async + 循环依赖

- @Async 代理**不参与**三级缓存提前暴露（不走 getEarlyBeanReference），只在后置钩子生成
- 循环依赖时 B 从工厂拿到**原始 A**，A 初始化后池里是**代理 A** → 引用不一致 → **启动报错**
- 解法：消除循环依赖（首选，本身是设计坏味道），或 @Lazy 延迟注入
