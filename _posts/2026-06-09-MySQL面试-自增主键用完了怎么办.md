<code>INT</code> 和 <code>BIGINT</code> 的区别。</p> </li> <li> <p><strong>系统设计思维</strong> ：考察你是否具备前瞻性的系统设计能力，能否在表设计阶段就考虑到数据量增长的问题。</p> </li> <li> <p><strong>分布式 ID 方案</strong> ：当单机自增主键不够用时，是否了解分布式 ID 生成方案（雪花算法、UUID 等），这是高并发系统的必备知识。</p> </li> </ol> <H2>核心答案</H2> <p><strong>自增主键用完的后果</strong> ：当自增 ID 达到数据类型的最大值后，再次插入数据会报错 <code>Duplicate entry 'xxx' for key 'PRIMARY'</code> ，新的数据无法写入。</p> <p><strong>各整数类型的主键容量</strong> ：</p> <table> <thead> <tr> <th>数据类型</th> <th>字节数</th> <th>最大值</th> <th>容量级</th> </tr> </thead> <tbody> <tr> <td><code>TINYINT</code></td> <td>1</td> <td>127（有符号）/ 255（无符号）</td> <td>百级</td> </tr> <tr> <td><code>SMALLINT</code></td> <td>2</td> <td>32767 / 65535</td> <td>万级</td> </tr> <tr> <td><code>MEDIUMINT</code></td> <td>3</td> <td>8388607 / 16777215</td> <td>百万级</td> </tr> <tr> <td><code>INT</code></td> <td>4</td> <td>2147483647 / 4294967295</td> <td><strong>21 亿 / 42 亿</strong></td> </tr> <tr> <td><code>BIGINT</code></td> <td>8</td> <td>9223372036854775807 /...</td> <td><strong>922 亿亿</strong></td> </tr> </tbody> </table> <p><strong>一句话总结</strong> ：主键用完会导致插入失败，解决方案有 <strong>改用更大的类型（BIGINT）</strong> 或 <strong>使用分布式 ID（雪花算法）</strong> 。</p> <H2>深度解析</H2> <H3>一、自增主键用完会发生什么？</H3> <p>当自增 ID 达到上限后，MySQL 的行为如下：</p>   <p>上图展示了自增主键用完后的情况。关键点说明：</p> <ul> <li><strong>自增到最大值</strong> ：当 <code>AUTO_INCREMENT</code> 达到数据类型的上限时，无法继续递增</li> <li><strong>插入失败</strong> ：MySQL 尝试使用最大值插入，但该值已存在，导致主键冲突</li> <li><strong>删除不回退</strong> ：即使删除了中间的记录， <code>AUTO_INCREMENT</code> 值也不会变小</li> <li><strong>影响范围</strong> ：所有依赖自增主键的插入操作都会失败</li> </ul> <H3>二、解决方案一：改用更大的数据类型</H3> <p><strong>最简单直接的方案</strong> ：将 <code>INT</code> 改为 <code>BIGINT</code> 。</p> <pre><code class="language-sql" data-lang="sql">-- 修改前：INT 最大约 21 亿（有符号）或 42 亿（无符号）
CREATE TABLE orders (
    id INT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    order_no VARCHAR(32)
);

-- 修改后：BIGINT 最大约 922 亿亿
ALTER TABLE orders MODIFY id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY;</code></pre> <p><strong>BIGINT 有多大？</strong></p>   <p><strong>注意事项</strong> ：</p> <ul> <li>修改字段类型会锁表，大表操作需要谨慎（使用 <code>pt-online-schema-change</code> 等工具）</li> <li>建议新表设计时就直接使用 <code>BIGINT</code> ，省去后续迁移的麻烦</li> </ul> <H3>三、解决方案二：使用分布式 ID —— 雪花算法（Snowflake）</H3> <p>对于分布式系统，单机自增主键不够用或存在冲突风险，推荐使用 <strong>雪花算法</strong> 生成分布式 ID。</p>   <p>上图展示了雪花算法的 ID 结构。核心优势在于：</p> <ul> <li><strong>全局唯一</strong> ：通过机器 ID 区分不同节点，保证分布式环境下的唯一性</li> <li><strong>趋势递增</strong> ：基于时间戳生成，ID 大致按时间递增，利于索引</li> <li><strong>高性能</strong> ：本地生成，不依赖数据库，单机每秒可生成 400 万个 ID</li> <li><strong>无需协调</strong> ：各节点独立生成，不需要分布式锁或中心化服务</li> </ul> <p><strong>Java 实现示例</strong> ：</p> <pre><code class="language-java" data-lang="java">public class SnowflakeIdGenerator {
    // 起始时间戳（2024-01-01）
    private final long twepoch = 1704038400000L;

    // 机器 ID 所占位数
    private final long workerIdBits = 5L;
    private final long datacenterIdBits = 5L;

    // 序列号所占位数
    private final long sequenceBits = 12L;

    // 机器 ID 最大值：31
    private final long maxWorkerId = ~(-1L &lt;&lt; workerIdBits);

    // 序列号最大值：4095
    private final long sequenceMask = ~(-1L &lt;&lt; sequenceBits);

    // 机器 ID 左移位数
    private final long workerIdShift = sequenceBits;

    // 时间戳左移位数
    private final long timestampLeftShift = sequenceBits + workerIdBits + datacenterIdBits;

    private final long workerId;
    private long sequence = 0L;
    private long lastTimestamp = -1L;

    public SnowflakeIdGenerator(long workerId) {
        if (workerId &gt; maxWorkerId || workerId &lt; 0) {
            throw new IllegalArgumentException("worker Id error");
        }
        this.workerId = workerId;
    }

    public synchronized long nextId() {
        long timestamp = System.currentTimeMillis();

        // 时钟回拨检测
        if (timestamp &lt; lastTimestamp) {
            throw new RuntimeException("Clock moved backwards!");
        }

        // 同一毫秒内，序列号递增
        if (lastTimestamp == timestamp) {
            sequence = (sequence + 1) &amp; sequenceMask;
            if (sequence == 0) {
                // 序列号溢出，等待下一毫秒
                timestamp = tilNextMillis(lastTimestamp);
            }
        } else {
            sequence = 0L;
        }

        lastTimestamp = timestamp;

        // 组装 ID
        return ((timestamp - twepoch) &lt;&lt; timestampLeftShift)
                | (workerId &lt;&lt; workerIdShift)
                | sequence;
    }

    private long tilNextMillis(long lastTimestamp) {
        long timestamp = System.currentTimeMillis();
        while (timestamp &lt;= lastTimestamp) {
            timestamp = System.currentTimeMillis();
        }
        return timestamp;
    }
}</code></pre> <H3>四、各种 ID 生成方案对比</H3>   <p><strong>为什么 UUID 不推荐作为主键？</strong></p> <ul> <li><strong>页分裂问题</strong> ：UUID 是无序的，插入时会导致 B+ 树频繁分裂</li> <li><strong>存储空间大</strong> ：36 字符 vs 8 字节的 BIGINT</li> <li><strong>索引效率低</strong> ：无序 ID 导致缓存命中率下降</li> </ul> <H3>五、最佳实践建议</H3> <p><strong>1. 新表设计直接用 BIGINT</strong></p> <pre><code class="language-sql" data-lang="sql">-- 推荐写法
CREATE TABLE orders (
    id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
    -- 其他字段...
) ENGINE=InnoDB;</code></pre> <p><strong>2. 分布式系统用雪花算法</strong></p> <pre><code class="language-java" data-lang="java">// 使用成熟的开源实现
// 如：Mybatis-Plus 的 IdWorker、百度 UidGenerator、美团 Leaf
@IdType(type = IdType.ASSIGN_ID)  // Mybatis-Plus 雪花算法
private Long id;</code></pre> <p><strong>3. 设置合理的自增起始值和步长</strong></p> <pre><code class="language-sql" data-lang="sql">-- 多主架构下，避免 ID 冲突
-- 服务器 1：起始值 1，步长 2（生成 1, 3, 5, ...）
SET GLOBAL auto_increment_offset = 1;
SET GLOBAL auto_increment_increment = 2;

-- 服务器 2：起始值 2，步长 2（生成 2, 4, 6, ...）
SET GLOBAL auto_increment_offset = 2;
SET GLOBAL auto_increment_increment = 2;</code></pre> <H2>面试高频追问</H2> <ol> <li> <p><strong>追问一</strong> ：为什么 UUID 不适合做主键？</p> <ul> <li>答：UUID 无序会导致 B+ 树频繁页分裂，影响插入性能；同时占用空间大（36 字符 vs 8 字节），降低索引效率。</li> </ul> </li> <li> <p><strong>追问二</strong> ：雪花算法有什么缺点？</p> <ul> <li>答：依赖服务器时钟，时钟回拨会导致 ID 重复或异常；需要处理机器 ID 的分配问题（可通过 ZooKeeper/Redis 统一管理）。</li> </ul> </li> <li> <p><strong>追问三</strong> ：INT 和 BIGINT 对性能有影响吗？</p> <ul> <li>答：影响很小。主键索引的查找时间复杂度是 O(log n)，与主键大小关系不大；但 BIGINT 占用更多存储空间，可能影响内存中的缓存效率。</li> </ul> </li> </ol> <H2>常见面试变体</H2> <ul> <li>"MySQL 主键用完了会怎么样？"</li> <li>"为什么推荐用 BIGINT 做主键？"</li> <li>"分布式 ID 生成方案有哪些？"</li> <li>"雪花算法的原理是什么？"</li> </ul> <H2>记忆口诀</H2> <p><strong>主键 ID 方案选择</strong> ：</p> <ol> <li><strong>单机用 BIGINT</strong> ：容量够大，简单可靠</li> <li><strong>分布式用雪花</strong> ：全局唯一，趋势递增</li> <li><strong>远离 UUID</strong> ：无序导致页分裂</li> </ol> <H2>总结</H2> <p>自增主键用完会导致插入失败，解决方案有两种： <strong>单机场景改用 BIGINT</strong> （约 922 亿亿容量，足够使用）； <strong>分布式场景使用雪花算法</strong> 生成全局唯一、趋势递增的 ID。新表设计建议直接用 <code>BIGINT UNSIGNED</code> ，避免后续迁移成本。</p> </div></main>
