## 一条 SQL 是如何执行的？

想象你走进一家餐厅点餐：

1. 你对服务员说"给我来一份宫保鸡丁"——这就是你的 SQL
2. 服务员确认你是本店会员，把菜单记下来——这是连接器和分析器
3. 厨师长看了一眼菜谱说"这道菜做过，直接上"——这是查询缓存
4. 厨师长决定先炒鸡丁还是先备调料——这是优化器
5. 厨师按流程炒菜——这是执行器
6. 菜端上桌——结果返回给你

MySQL 的执行过程，和餐厅的运作一模一样。

```mermaid
flowchart LR
    A["客户端"] --> B["连接器"]
    B --> C["查询缓存"]
    C --> D["分析器"]
    D --> E["优化器"]
    E --> F["执行器"]
    F --> G["存储引擎"]
    G --> H["磁盘"]

    style A fill:#4a90d9,color:#fff
    style G fill:#f5a623,color:#fff
    style H fill:#e74c3c,color:#fff
```

> 💡 **核心认知**：MySQL 分为 **Server 层**（连接器、缓存、分析器、优化器、执行器）和 **存储引擎层**（InnoDB、MyISAM 等）。Server 层做逻辑处理，存储引擎负责数据读写。
{: .prompt-tip }

## 连接器：先确认你是谁

当你执行 `mysql -u root -p` 时，第一步就是**建立连接**。

### 连接器做了什么？

1. **TCP 握手**：客户端和 MySQL 建立网络连接
2. **身份认证**：验证用户名密码是否正确
3. **权限检查**：你这个账号能查哪些表、能做什么操作

```
客户端 ── 握手 ──▶ MySQL
               ├─ 用户名密码验证 ✅
               └─ 读取权限表，记住你是谁
```

### 连接池：反复建立连接很浪费

每次建立连接都要做 TCP 握手、身份验证、权限读取，开销很大。所以生产环境通常用**连接池**——提前建好一批连接，谁用就借给谁，用完还回来。

| 概念 | 类比 | 作用 |
|:---:|:---:|:---:|
| **长连接** | 包月会员，一直用 | 减少连接开销，适合频繁查询 |
| **短连接** | 临时顾客，用完就走 | 适合偶尔用一次 |
| **连接池** | 餐厅预留座位 | 控制并发，管理连接生命周期 |

> ⚠️ **注意**：长连接虽然省资源，但长时间不关闭可能导致 MySQL 内存占用越来越大（连接内存不会释放）。建议定期断开重连，或者用 `mysql_reset_connection` 重置连接状态。
{: .prompt-warning }

## 查询缓存：直接端上来

连接建立后，MySQL 收到你的 SQL，先做一件事——**看看这道菜之前做过没**。

### 缓存如何工作？

```
SQL: SELECT * FROM users WHERE id = 1
        ↓
    对 SQL 做哈希（计算一个"指纹"）
        ↓
    查缓存表：这个指纹有没有对应的结果？
        ├─ 有 ✅ → 直接返回结果（超快！）
        └─ 没有 ❌ → 继续后面的流程
```

### 缓存的致命问题：太容易失效了

**只要表有任何改动（INSERT/UPDATE/DELETE），这张表的所有缓存全部失效**。

想象一下：你存了 1000 条缓存记录，都关联 `users` 表。现在有一个用户改了昵称——1000 条缓存瞬间全部作废。

| 场景 | 缓存是否好用？ | 原因 |
|:---:|:---:|:---:|
| 静态数据（配置表、字典表） | ✅ 非常好用 | 很少改动 |
| 读写均衡的业务表 | ❌ 不要用 | 写操作会频繁清空缓存 |
| 写入频繁的表 | ❌ 绝对不用 | 缓存几乎永远是空的 |

> 💡 **MySQL 8.0 已经移除了查询缓存功能**，因为实践证明弊大于利。现代应用通常用 Redis 等外部缓存替代。
{: .prompt-tip }

## 分析器：你到底想做什么

缓存没命中，MySQL 开始**理解你的 SQL**。

### 第一步：词法分析

把你的 SQL 拆成一个个"词"：

```
SELECT   name, age   FROM   users   WHERE   id = 1
   ↓        ↓          ↓      ↓        ↓      ↓
关键字   字段列表     关键字   表名    关键字  条件
```

就像你说"给我一份宫保鸡丁，不要辣"——服务员要拆出"宫保鸡丁"是菜名，"不要辣"是特殊要求。

### 第二步：语法分析

按照 MySQL 的语法规则，把这些词组装成一棵**语法树**：

```mermaid
graph TD
    A["SELECT语句"] --> B["字段列表"]
    A --> C["来源表"]
    A --> D["过滤条件"]

    B --> B1["name"]
    B --> B2["age"]
    C --> C1["users"]
    D --> D1["id = 1"]

    style A fill:#4a90d9,color:#fff
```

### 第三步：语义分析

检查语法树合不合理：

- `users` 表存在吗？
- `name`、`age`、`id` 字段在 `users` 表里吗？
- 你有权限查这些字段吗？

> 📖 **总结**：分析器 = 拆解 SQL + 检查语法 + 验证语义。如果 SQL 写错了（比如把 `SELECT` 拼写成 `SELET`），就是在这一步报错。
{: .prompt-info }

## 优化器：怎么走最划算

分析器告诉 MySQL "用户想查什么"，但**怎么查最快**——这是优化器的工作。

### 优化器在选择什么？

一条 SQL 可能有很多种执行方式，优化器要选成本最低的：

| 决策类型 | 例子 |
|:---:|:---|
| **走哪个索引** | 查 `WHERE name='小明' AND age=18`，是用 name 索引还是 age 索引？ |
| **表连接顺序** | 多表 JOIN 时，先查 A 表还是先查 B 表？小表先查通常更快 |
| **全表扫还是走索引** | 如果要查的数据占了表的一半，全表扫描可能比索引还快 |
| **排序方式** | `ORDER BY` 是走索引排序，还是临时文件排序？ |

### 理解"成本"

MySQL 的优化器基于**成本模型**（Cost Model）决策，主要考虑：

- **IO 成本**：从磁盘读数据页的开销（最昂贵）
- **CPU 成本**：在内存中比较、计算、排序的开销

```
总成本 ≈ IO成本 × 权重 + CPU成本 × 权重
```

> 💡 **类比**：从北京去上海，有三种选择：<br>① 坐飞机（贵但快 = 走索引）<br>② 坐高铁（中等 = 覆盖索引）<br>③ 走路去（免费但极慢 = 全表扫描）<br><br>优化器会估算每种方式的"成本"，选它认为最便宜的。
{: .prompt-tip }

### EXPLAIN：看优化器的决策

你可以用 `EXPLAIN` 查看优化器的选择：

```sql
EXPLAIN SELECT * FROM users WHERE id = 1;
```

关键信息：

| 字段 | 含义 | 关注点 |
|:---:|:---:|:---:|
| `type` | 访问类型 | `system` > `const` > `eq_ref` > `ref` > `range` > `index` > `ALL`（越靠左越快） |
| `key` | 实际用的索引 | 是否用了你期望的索引？ |
| `rows` | 预估扫描行数 | 越少越好 |
| `Extra` | 额外信息 | 是否出现了 `Using filesort`、`Using temporary`？ |

> ⚠️ **优化器不是神**。它基于统计信息估算，有时会选错（比如统计信息不准、索引选错）。这时候可以用 `FORCE INDEX` 强制指定索引。
{: .prompt-warning }

## 执行器：真正去执行

优化器确定了执行计划，**执行器**负责按照计划去取数据。

### 执行流程

以 `SELECT name FROM users WHERE age > 18` 为例：

```
1. 检查权限：你能查 users 表吗？
2. 打开表，调用存储引擎的接口
3. 取第一条数据：age > 18 吗？
   ├─ 是 → 留下 name，放入结果集
   └─ 否 → 跳过
4. 取下一条，重复步骤 3
5. 所有数据扫描完，返回结果集给客户端
```

### 执行器和存储引擎的配合

```mermaid
sequenceDiagram
    participant 执行器
    participant 存储引擎 as InnoDB

    执行器->>存储引擎: "给我 users 表第一条数据"
    存储引擎->>执行器: 返回数据行
    执行器->>执行器: 检查 age > 18？
    执行器->>存储引擎: "给我下一条"
    存储引擎->>执行器: 返回数据行
    执行器->>执行器: 检查 age > 18？
    Note right of 执行器: 循环直到数据取完
```

> 📖 **核心设计**：执行器只关心"取数据、判断、返回"，**数据具体怎么存、怎么取**交给存储引擎。这种分层设计让 MySQL 可以支持多种存储引擎（InnoDB、MyISAM、Memory 等）。
{: .prompt-info }

## 存储引擎：真正管数据的人

MySQL 最经典的设计就是**插件式存储引擎**——Server 层负责逻辑，存储引擎负责数据的存和取。

### 三大存储引擎对比

| 特性 | InnoDB（默认） | MyISAM | Memory |
|:---:|:---:|:---:|:---:|
| **事务** | ✅ 支持 | ❌ 不支持 | ❌ 不支持 |
| **行锁** | ✅ 支持 | ❌ 只有表锁 | ✅ 支持 |
| **崩溃恢复** | ✅ 可以 | ❌ 可能丢数据 | ❌ 重启就没了 |
| **存储位置** | 磁盘 | 磁盘 | 内存 |
| **适用场景** | 大多数业务系统 | 只读、日志类 | 临时表、缓存 |

### InnoDB 为什么是默认？

```mermaid
flowchart TB
    A["InnoDB"] --> B["事务安全 ACID"]
    A --> C["行级锁 + MVCC"]
    A --> D["B+树索引"]
    A --> E["崩溃恢复能力"]
    A --> F["外键支持"]

    style A fill:#4a90d9,color:#fff
```

> 💡 **一句话总结**：MyISAM 跑得快但不安全（不支持事务、不支持行锁），InnoDB 是最均衡的选择——现代 MySQL 应用 99% 用 InnoDB。
{: .prompt-tip }

## 完整执行流程回顾

把一个 `SELECT` 从头到尾再过一遍：

```mermaid
flowchart LR
    A["1. 建立连接<br/>TCP握手+认证"] --> B["2. 查询缓存<br/>命中则直接返回"]
    B --> C["3. 分析器<br/>词法+语法+语义分析"]
    C --> D["4. 优化器<br/>选择执行计划"]
    D --> E["5. 执行器<br/>调用存储引擎取数据"]
    E --> F["6. 存储引擎<br/>从磁盘/Buffer Pool取数据"]
    F --> G["7. 返回结果<br/>给客户端"]

    style A fill:#4a90d9,color:#fff
    style G fill:#f5a623,color:#fff
```

### 更新语句的特殊之处

如果是 `UPDATE/INSERT/DELETE`，多了两个关键步骤：

```
执行器修改数据
        ↓
    写 undo log（回滚日志——万一出错可以回滚）
        ↓
    更新内存中的数据页
        ↓
    写 redo log（重做日志——崩溃后可以恢复）
        ↓
    写 binlog（归档日志——主从同步用）
        ↓
    后台刷盘（把内存中的改动写回磁盘）
```

> 📖 **WAL（Write-Ahead Logging）**：先写日志，再写数据。这是数据库的核心设计——**任何修改先记日志，再应用到数据**。好处是：即使数据库突然挂了，重启后可以根据日志恢复。
{: .prompt-info }

## 小结

MySQL 的架构设计体现了计算机系统最经典的思想——**分层 + 各司其职**：

- **连接器**：认证 + 权限 + 连接管理
- **查询缓存**：快道（但弊大于利，MySQL 8.0 已移除）
- **分析器**：理解 SQL 说什么
- **优化器**：决定怎么走最快
- **执行器**：按照计划执行
- **存储引擎**：真正读写数据（InnoDB 是默认）

理解这条执行链路，你就不是"只会写 SQL"的初级开发者了——你能看懂 EXPLAIN、理解索引为什么快、诊断查询慢的原因。
