<code>LIMIT 1000000, 10</code> 会慢？MySQL 到底在做什么？</p> </li> <li> <p><strong>原理理解深度</strong> ：考察你是否理解 MySQL 的 <code>LIMIT offset, size</code> 执行机制——它需要扫描 offset + size 条记录再丢弃前面的，而不是"直接跳到第 offset 条"。</p> </li> <li> <p><strong>方案选型思维</strong> ：深度分页有多种优化方案，考察你能否根据业务场景（是否允许用户跳页、是否有连续自增主键等）选择最合适的方案。</p> </li> </ol> <H2>核心答案</H2> <p><strong>深度分页问题</strong> ：当使用 <code>LIMIT offset, size</code> 且 <code>offset</code> 值很大时，MySQL 需要扫描 <code>offset + size</code> 条记录后丢弃前面的 <code>offset</code> 条，性能急剧下降。</p> <p><strong>优化方案对比</strong> ：</p> <table> <thead> <tr> <th>方案</th> <th>核心思路</th> <th>适用场景</th> <th>性能提升</th> </tr> </thead> <tbody> <tr> <td>子查询优化</td> <td>先查主键 ID，再回表查数据</td> <td>有自增主键索引</td> <td>⭐⭐⭐⭐</td> </tr> <tr> <td>INNER JOIN</td> <td>同上，写法不同</td> <td>有自增主键索引</td> <td>⭐⭐⭐⭐</td> </tr> <tr> <td>游标分页</td> <td>记录上次最大 ID，下次从该 ID 开始</td> <td>连续翻页、不支持跳页</td> <td>⭐⭐⭐⭐⭐</td> </tr> <tr> <td>BETWEEN 范围查询</td> <td>用 ID 范围替代 LIMIT offset</td> <td>ID 连续、无断层</td> <td>⭐⭐⭐⭐⭐</td> </tr> <tr> <td>业务限制</td> <td>限制最大页数，禁止深度跳页</td> <td>搜索引擎类场景</td> <td>⭐⭐⭐</td> </tr> </tbody> </table> <p><strong>一句话总结</strong> ：深度分页的本质是 <code>offset</code> 导致的全表扫描，优化核心是 <strong>"利用索引直接定位起始点，避免扫描后丢弃"</strong> 。</p> <H2>深度解析</H2> <H3>一、问题本质：为什么深度分页会慢？</H3> <p>先看一个典型的深度分页 SQL：</p> <pre><code class="language-sql" data-lang="sql">SELECT * FROM orders ORDER BY id LIMIT 1000000, 10;</code></pre> <p><strong>很多人的误解</strong> ：MySQL 会"直接跳到第 100 万条记录"，然后取 10 条。</p> <p><strong>实际情况</strong> ：MySQL 的执行流程是：</p>   <p>上图展示了 <code>LIMIT 1000000, 10</code> 的执行过程。关键问题在于：</p> <ul> <li><strong>扫描量大</strong> ：MySQL 需要扫描 <code>1000000 + 10 = 1000010</code> 条记录，而不是只扫描 10 条</li> <li><strong>丢弃浪费</strong> ：前 100 万条记录全部被扫描后丢弃，做了无用功</li> <li><strong>回表开销</strong> ：如果查询的是 <code>SELECT *</code> ，每条记录都要回表获取完整数据，代价更大</li> <li><strong>时间复杂度</strong> ：O(offset + size)，offset 越大，性能越差</li> </ul> <p>这就是为什么 <code>LIMIT 100, 10</code> 很快，但 <code>LIMIT 1000000, 10</code> 会慢几个数量级。</p> <H3>二、方案一：子查询优化</H3> <p><strong>核心思想</strong> ：先通过子查询利用覆盖索引快速定位起始 ID，再回表查数据，避免大量无意义的回表操作。</p> <pre><code class="language-sql" data-lang="sql">-- 原始慢查询（假设执行时间：5 秒）
SELECT * FROM orders ORDER BY id LIMIT 1000000, 10;

-- 优化后（假设执行时间：0.1 秒）
SELECT * FROM orders o
INNER JOIN (
    SELECT id FROM orders ORDER BY id LIMIT 1000000, 10
) t ON o.id = t.id;</code></pre> <p><strong>为什么更快？</strong></p>   <p>上图展示了子查询优化的核心原理。关键优化点在于：</p> <ul> <li><strong>覆盖索引</strong> ：子查询只查 <code>id</code> 字段，可以直接在索引上完成，无需回表</li> <li><strong>减少回表</strong> ：子查询阶段扫描 100 万条时不需要回表，只有最终的 10 条才回表</li> <li><strong>性能对比</strong> ：原始查询回表 100 万次，优化后只回表 10 次</li> </ul> <H3>三、方案二：游标分页（Cursor-based Pagination）—— 性能最优</H3> <p><strong>核心思想</strong> ：记录上一页最后一条记录的 ID，下次查询时直接从该 ID 之后开始，完全避开 <code>offset</code> 。</p> <pre><code class="language-sql" data-lang="sql">-- 第一页
SELECT * FROM orders ORDER BY id LIMIT 10;

-- 假设第一页最后一条记录的 id = 10
-- 第二页（传统方式：LIMIT 10, 10）
-- 第二页（游标方式：记住上一页最后的 id）
SELECT * FROM orders WHERE id &gt; 10 ORDER BY id LIMIT 10;

-- 第 N 页：假设上一页最后的 id = 1000000
SELECT * FROM orders WHERE id &gt; 1000000 ORDER BY id LIMIT 10;</code></pre>   <p>上图对比了传统分页和游标分页的性能差异。关键优势在于：</p> <ul> <li><strong>稳定性能</strong> ：无论翻到第几页，每次都只扫描 <code>size</code> 条记录，性能恒定</li> <li><strong>索引定位</strong> ： <code>WHERE id &gt; last_id</code> 可以直接利用主键索引定位到起始位置</li> <li><strong>无丢弃浪费</strong> ：不存在"扫描后丢弃"的问题</li> </ul> <p><strong>游标分页的局限性</strong> ：</p> <ul> <li><strong>不支持跳页</strong> ：用户只能"上一页/下一页"，不能直接跳到第 N 页</li> <li><strong>需要连续 ID</strong> ：如果 ID 不连续或有删除，可能导致某些记录被跳过或重复</li> <li><strong>前端需要记住游标</strong> ：需要保存上一页最后的 ID 值</li> </ul> <H3>四、方案三：BETWEEN 范围查询</H3> <p>如果 ID 连续且业务允许，可以用 ID 范围替代 <code>LIMIT offset</code> ：</p> <pre><code class="language-sql" data-lang="sql">-- 假设每页 10 条，要查第 100001 页
-- 起始 ID = (100001 - 1) * 10 + 1 = 1000001
-- 结束 ID = 1000001 + 9 = 1000010

SELECT * FROM orders
WHERE id BETWEEN 1000001 AND 1000010;</code></pre> <p><strong>适用条件</strong> ：</p> <ul> <li>ID 必须连续（没有断层）</li> <li>需要知道 ID 的分布规律</li> </ul> <H3>五、方案四：业务层面限制 —— 最实用的方案</H3> <p>很多大厂的做法： <strong>直接限制用户只能翻到前 N 页</strong> 。</p>   <p><strong>实现方式</strong> ：</p> <pre><code class="language-java" data-lang="java">// 后端校验
public PageResult&lt;Order&gt; listOrders(int pageNum, int pageSize) {
    // 限制最大页数
    int maxPage = 100;
    if (pageNum &gt; maxPage) {
        throw new BusinessException("最多只能查看前 " + maxPage + " 页");
    }
    // 正常查询
    return orderMapper.selectPage(pageNum, pageSize);
}</code></pre> <H3>六、实际性能对比（100 万条数据测试）</H3> <table> <thead> <tr> <th>查询方式</th> <th>SQL</th> <th>执行时间</th> </tr> </thead> <tbody> <tr> <td>原始查询</td> <td><code>SELECT * FROM orders LIMIT 1000000, 10</code></td> <td>~5s</td> </tr> <tr> <td>子查询优化</td> <td><code>SELECT * FROM orders o INNER JOIN (SELECT id FROM orders LIMIT 1000000, 10) t ON o.id = t.id</code></td> <td>~0.1s</td> </tr> <tr> <td>游标分页</td> <td><code>SELECT * FROM orders WHERE id &gt; 1000000 LIMIT 10</code></td> <td>~0.01s</td> </tr> </tbody> </table> <H2>面试高频追问</H2> <ol> <li> <p><strong>追问一</strong> ：游标分页有什么缺点？什么场景不适合用？</p> <ul> <li>答：不支持跳页、需要前端保存游标状态、ID 不连续时可能漏数据。电商搜索结果页适合，但后台管理系统需要跳页就不适合。</li> </ul> </li> <li> <p><strong>追问二</strong> ：如果排序字段不是主键 ID，而是 <code>create_time</code> ，怎么优化？</p> <ul> <li>答：可以用联合索引 <code>(create_time, id)</code> ，子查询改为 <code>SELECT id FROM orders ORDER BY create_time, id LIMIT offset, size</code> ，游标分页改为 <code>WHERE (create_time, id) &gt; (last_time, last_id)</code> 。</li> </ul> </li> <li> <p><strong>追问三</strong> ：为什么子查询只查 <code>id</code> 就能提升性能？</p> <ul> <li>答：因为只查主键/索引列时，MySQL 可以使用"覆盖索引"，直接在索引树上获取数据，不需要回表去聚簇索引查完整记录。</li> </ul> </li> </ol> <H2>常见面试变体</H2> <ul> <li>"为什么 <code>LIMIT 1000000, 10</code> 会很慢？"</li> <li>"MySQL 分页查询怎么优化？"</li> <li>"百万级数据分页怎么处理？"</li> <li>"介绍几种分页优化方案及其适用场景"</li> </ul> <H2>记忆口诀</H2> <p><strong>深度分页优化三句话</strong> ：</p> <ol> <li><strong>子查询先查 id</strong> ：覆盖索引省回表</li> <li><strong>游标记住 last_id</strong> ：直接定位无扫描</li> <li><strong>业务限制最大页</strong> ：性价比高最实用</li> </ol> <H2>总结</H2> <p>深度分页的性能问题本质是 <code>offset</code> 导致的大量无效扫描。优化核心是 <strong>"用索引直接定位，避免扫描后丢弃"</strong> ：生产环境推荐 <strong>子查询 + JOIN</strong> （兼容跳页）或 <strong>游标分页</strong> （性能最优），同时配合 <strong>业务层限制最大页数</strong> ，这是最经济实用的方案。</p> </div></main>
