# 可观测性：三支柱 + 链路追踪 + 指标方法论（L6 第一课）
## 1. 三支柱：缺一不可

![07-01 可观测性三支柱]({{ site.baseurl }}/assets/svg/07-01-可观测性三支柱.svg)

```
        Metrics 指标
        聚合数值·健康度
        CPU·QPS·GC
            │
            ▼
Tracing ────► 完整 ◄──── Logging
链路追踪      可观测性      日志
单请求贯穿   （三合一）    离散事件
慢在哪·错在哪              结构化+trace_id
```

三者互补：
- **Metrics** 看曲线但不知哪次请求
- **Tracing** 看一次但不知整体
- **Logging** 知发生了什么但难聚合

实战排查流程（接口偶发超时）：
1. 看 Metrics：确认 P99 飙高是延迟问题不是流量
2. 拿 Tracing：点那条慢 Trace，定位 Span C "写 TDengine 1.8s"
3. 翻 Logging：用 trace_id 检索日志，看到 TDengine 报 "out of memory"

**关键：日志必须带 trace_id**，否则第三步搜不到那次请求的相关日志。

## 2. 链路追踪：Span 树

![07-02 链路追踪 Span 树]({{ site.baseurl }}/assets/svg/07-02-链路追踪Span树.svg)

```
Trace Root: HTTP /iot/data
   ├── Span A 网关解码
   ├── Span B 解析寄存器
   │     └── Span D 更新 Redis
   └── Span C ⚠ 写 TDengine 1.8s
         └── Span E 告警判定
```

核心概念：
- **trace_id** 全链唯一——一次请求所有 Span 共享
- **span_id / parent_span_id**——子 Span 通过 parent_id 找父，串成树
- **SpanContext 传播**：跨进程靠 HTTP Header（W3C `traceparent` / B3 / Jaeger）；跨线程靠 MDC + 线程上下文
- **线程池里任务必须用 ContextUtil.wrap() 包装**——否则 trace_id 在子线程丢失
- **采样**：
  - Head-based（入口决定，简单但抓不到错误）
  - Tail-based（出口按结果，能保证错误必采，成本高）
  - 生产常配 1~10% 全量采样 + 错误必采
- **OpenTelemetry 是当下唯一推荐**——统一了 Zipkin/Jaeger 各家客户端标准

## 3. 指标方法论：看什么、怎么看

![07-03 指标方法论 RED 与 USE]({{ site.baseurl }}/assets/svg/07-03-指标方法论RED与USE.svg)

| 方法 | 视角 | 四要素 |
|---|---|---|
| RED | 服务 | Rate · Errors · Duration |
| USE | 资源 | Utilization · Saturation · Errors |
| 四金信号 | Google SRE | 延迟 · 流量 · 错误 · 饱和度 |

- **RED** 看服务对外表现：QPS、错误率、P99 延迟
- **USE** 看资源内部健康：CPU/内存/磁盘利用率、队列饱和、错误
- **四金信号** 是 Google SRE 综合：四个金指标都稳=系统稳

### 网关场景应用
- QPS = 流量（Rate）
- Modbus 错误率 = 错误（Errors）
- 响应 P99 = 延迟（Duration / Latency）
- TDengine 写入队列长度 = 饱和度（Saturation）

## 4. 生产场景对照

| 场景 | 对应可观测性短板 |
|---|---|
| bat 启动 stdout 缓冲、日志不打印 | Logging 支柱没立起来——日志要先能稳定输出 |
| application-prod 抑制高频日志 | 日志成本治理——但不是砍掉，是要带 trace_id 后才能少而准 |
| 网关 Modbus 高频轮询 → 大屏超时 | 缺 Tracing，无法定位是哪个环节慢 |
| TDengine 双写偶发失败 | 缺 Metrics，看不到错误率与饱和度趋势 |
| Jimu 多接口慢查询 | Tracing 串联多个 service 后才能定位瓶颈接口 |

## 5. 推荐技术栈（生产可落地）

| 支柱 | 选型 | 说明 |
|---|---|---|
| Metrics | Prometheus + Grafana | 拉模式、时序库、告警 AlertManager |
| Tracing | OpenTelemetry + Tempo/Jaeger | OTel 统一采集，后端任选 |
| Logging | Loki + Grafana（轻量）/ ELK（重） | Loki 与 Grafana 同 UI，轻量首选 |
| APM 一体 | SkyWalking / 阿里 Arthas（仅排查） | 国产、对 Spring 生态友好 |

**关键提醒**：你 Windows Server 生产（10.10.50.2）跑 Grafana/Prometheus 没问题，但 Loki/ES 较重，建议先上 Prometheus + Grafana + 轻量日志（带 trace_id 的结构化日志写文件 + Grafana Loki 远程查）。
