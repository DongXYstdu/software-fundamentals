# SOLID 实战与耦合度量（结构软实力 · 地基课）
## 1. 为什么 SOLID 是结构软实力的地基

模块划分、分包健壮、层次分明、模式进来不乱——本质都在回答同一个问题：

> **当需求变化时，改动会被限制在局部，还是沿着依赖链扩散到全系统？**

SOLID 五原则看似五条独立规则，其实只在做一件事：**把"变化"隔离在尽可能小的范围内**。

| 原则 | 隔离的是什么变化 |
|---|---|
| SRP | 隔离"多个变化原因"挤在一个类里 |
| OCP | 隔离"新增类型"对已有代码的修改 |
| LSP | 隔离"替换实现"带来的行为意外 |
| ISP | 隔离"客户端不用的方法"变更的波及 |
| DIP | 隔离"底层实现更换"对高层的影响 |

统一视角：后面模块划分、分包、守层、模式安放的所有技巧，都是这五条在不同粒度上的应用——**类内 → 包内 → 层间 → 模块间**。

判断标准很朴素：做完一次重构/引入一个模式后，问自己——**"下次同类变化，我需要改几个地方？"** 改的地方越少、越集中，结构就越好。

## 2. SRP 单一职责——职责是"变化的轴"，不是"方法少"

### 2.1 最常见的误读

"把大类拆成小类，每个类方法少一点"——这不是 SRP。经典定义：

> **一个模块应当只有一个引起它变化的原因（One reason to change）。**

"变化原因"= 使用这个模块的**利益相关方**。谁在要求你改代码，谁就是一个变化轴。

### 2.2 反例：网关里的"上帝服务"

```java
// ❌ 反例：一个类背着三条变化轴
public class DeviceService {

    // 轴1：采集协议变化 —— 协议工程师要求改
    public Map<String, Object> pollDevice(String deviceId) {
        // Modbus 读寄存器、大小端处理、协议版本兼容...
    }

    // 轴2：告警规则变化 —— 运维/业务方要求改
    public void checkAlarm(Map<String, Object> data) {
        if ((double) data.get("t_001") > 80) { /* 触发告警 */ }
        // 规则越加越多：阈值、持续时间、组合条件...
    }

    // 轴3：存储方案变化 —— 架构师要求改（换时序库/加压缩）
    public void save(Map<String, Object> data) {
        // 写 MySQL / 写 TDengine / 批量攒批...
    }
}
```

三条轴纠缠的代价：

1. **改动互相踩**：改告警阈值误伤采集逻辑，测试必须三块全回归
2. **合并冲突**：三个需求方向的人同时改这一个文件
3. **无法独立演进**：想换时序库，却被迫重新理解采集和告警代码

### 2.3 正例：按变化轴拆开

```java
// ✅ 每条轴一个类，各有一个变化原因
public class ModbusPoller {          // 轴1：协议变 → 只改这里
    public DeviceSnapshot poll(String deviceId) { ... }
}

public class AlarmRuleEngine {       // 轴2：规则变 → 只改这里
    public List<Alarm> evaluate(DeviceSnapshot snapshot) { ... }
}

public class TimeSeriesWriter {      // 轴3：存储变 → 只改这里
    public void write(DeviceSnapshot snapshot) { ... }
}
```

三者之间用**稳定的数据结构** `DeviceSnapshot` 传递，谁也不依赖谁的内部实现。

### 2.4 两个实操判断法

**判断法 1：用"谁要求你改"来拆**
对类里每个方法问：这个方法变更时，是哪个角色（协议方/业务方/架构方）提的需求？出现 ≥2 个角色 → 违反 SRP。

**判断法 2：用"一句话描述"来测**
描述这个类时必须用"和"字连接两件不相干的事（"采集**和**告警**和**存储"）→ 大概率违反 SRP。

### 2.5 边界提醒：SRP 不是无限拆

- 三个轴目前都只有一行逻辑、且确定永远简单 → 可以先不拆，**等第二条轴真的开始频繁变化时再拆**
- 拆分的依据是**已观察到的变化**，不是想象中的变化

### 2.6 衔接

SRP 在类粒度上拆变化轴；模块划分、package-by-feature 就是在**包/模块粒度**上做同一件事——按业务能力（变化轴）而不是按技术层切分。

## 3. OCP 开闭原则——对扩展开放，对修改关闭

![09-02 OCP 扩展点对比]({{ site.baseurl }}/assets/svg/09-02-OCP扩展点对比.svg)

### 3.1 定义与本质

> **软件实体应当对扩展开放，对修改关闭。**

直白翻译：**新增一种情况时，应该写新代码，而不是改老代码**。老代码是已测试、已上线、被多处依赖的——动它就要全量回归。OCP 的实现手段只有一个：**抽象 + 注入**。

### 3.2 反例：新增设备型号，if/else 硬编码

```java
// ❌ 每来一个型号，改一次这个"核心类"
public class ModbusParser {

    public DeviceSnapshot parse(String model, byte[] frame) {
        if ("KHE-100".equals(model)) {
            // 老型号：温度在寄存器 0，压力在寄存器 1
            return new DeviceSnapshot(
                readShort(frame, 0), readShort(frame, 1));

        } else if ("KHE-200".equals(model)) {
            // 新型号：顺序反了，还要乘缩放系数
            return new DeviceSnapshot(
                readShort(frame, 1) * 0.1, readShort(frame, 0) * 0.1);

        } else if ("KHE-300".equals(model)) {
            // 又新型号：32 位浮点编码...
            return new DeviceSnapshot(
                readFloat(frame, 0), readFloat(frame, 2));
        }
        throw new IllegalArgumentException("未知型号: " + model);
    }
}
```

问题清单：

1. **每加一个型号都要改这个类** → 每次都要重新测试所有已有型号
2. **合并冲突热点**：所有型号需求都挤在同一个文件
3. **违反 SRP**：这个类的变化原因 = 型号数量，型号无限增长
4. **无法独立发布**：新型号解析有 bug，回滚会连带所有型号

### 3.3 正例：抽象 + 注册表扩展点

```java
// ✅ 第一步：抽出"型号解析器"接口 —— 这就是扩展点
public interface ModelParser {
    String supportedModel();                 // 我负责哪个型号
    DeviceSnapshot parse(byte[] frame);      // 怎么解析
}

// ✅ 第二步：每个型号一个实现类 —— 新增型号 = 新增文件
public class Khe100Parser implements ModelParser {
    public String supportedModel() { return "KHE-100"; }
    public DeviceSnapshot parse(byte[] frame) {
        return new DeviceSnapshot(readShort(frame, 0), readShort(frame, 1));
    }
}

public class Khe200Parser implements ModelParser {
    public String supportedModel() { return "KHE-200"; }
    public DeviceSnapshot parse(byte[] frame) {
        return new DeviceSnapshot(
            readShort(frame, 1) * 0.1, readShort(frame, 0) * 0.1);
    }
}

// ✅ 第三步：注册表按型号路由 —— 这个类写好后永远不用改
public class ParserRegistry {
    private final Map<String, ModelParser> parsers = new HashMap<>();

    public void register(ModelParser parser) {
        parsers.put(parser.supportedModel(), parser);
    }

    public DeviceSnapshot parse(String model, byte[] frame) {
        ModelParser parser = parsers.get(model);
        if (parser == null) throw new IllegalArgumentException("未知型号: " + model);
        return parser.parse(frame);
    }
}
```

Spring 环境下第三步可以更省事——所有 `ModelParser` 实现自动注入成 List，启动时建表：

```java
@Component
public class ParserRegistry {
    private final Map<String, ModelParser> parsers;

    // Spring 自动收集所有 ModelParser 实现
    public ParserRegistry(List<ModelParser> parserList) {
        this.parsers = parserList.stream()
            .collect(Collectors.toMap(ModelParser::supportedModel, p -> p));
    }
}
```

此时新增 KHE-300：**只新建 `Khe300Parser.java` 一个文件，零行老代码修改**。

### 3.4 三个实操要点

**要点 1：扩展点是"第二次变化"时抽出来的**

| 阶段 | 做法 |
|---|---|
| 只有 1 个型号 | 直接写死，不抽象 |
| 第 2 个型号出现 | 出现 if/else → **此时**抽接口建注册表 |
| 第 N 个型号 | 只加实现类 |

**变化出现第二次，就是抽象的信号**。

**要点 2：OCP 有作用域，不可能全系统封闭**

注册表对"新型号"封闭了，但对"协议从 Modbus 换成 OPC-UA"并不封闭。只能针对**最可能发生的那类变化**设防；判断依据：历史需求记录里哪类变化最频繁。

**要点 3：OCP 的常见实现形态**（13 课讲与分层的安放关系）

| 形态 | 机制 | 典型场景 |
|---|---|---|
| 策略 + 注册表 | 接口 + 多实现 + 路由 | 多型号解析 |
| 模板方法 | 父类定骨架，子类填空 | 采集流程固定、步骤不同 |
| 责任链 | 处理器串联，可插拔 | 数据清洗管道 |
| 事件监听 | 发布者不感知订阅者 | 告警通知多渠道 |

### 3.5 衔接

- 上承 SRP：`ModbusParser` 反例同时违反两条——SRP 说"它背了太多变化轴"，OCP 说"怎么改才能不再每次修改它"
- 下启 DIP：注册表能成立，是因为调用方依赖 `ModelParser` **接口**而不是具体实现类

## 4. LSP 里氏替换原则——继承的"行为契约"

### 4.1 定义与本质

> **所有引用基类的地方，必须能透明地使用其子类的对象，而程序行为不变。**

编译通过 ≠ 满足 LSP。LSP 约束的不是类型系统，而是**行为契约**：子类在继承父类能力的同时，也继承了父类对调用方的所有承诺（前置条件、后置条件、不变式）。**子类只能加强承诺，不能违背或削弱承诺**。

一句话记忆：**调用方不应该、也不需要知道自己拿到的是父类还是哪个子类。**

### 4.2 反例：只读设备继承可写设备

```java
// 父类：通用设备，承诺"可读可写"
public class Device {
    protected String id;

    public DeviceSnapshot read() { /* 读寄存器 */ }

    // 父类契约：写入后，下次 read 能读到新值
    public void write(String tag, Object value) { /* 写寄存器 */ }
}

// ❌ 子类：只读探头，"继承"了 write 却兑现不了契约
public class ReadOnlyProbe extends Device {
    @Override
    public void write(String tag, Object value) {
        throw new UnsupportedOperationException("只读设备不支持写入");
    }
}
```

爆炸点在调用方：

```java
// 这段代码对 Device 完全合法
public void setAndVerify(Device device, String tag, Object value) {
    device.write(tag, value);
    Object actual = device.read().get(tag);
    // ...
}

// 传入 ReadOnlyProbe → 运行时抛异常 💥
```

调用方写的是 `Device`，行为却取决于**运行时具体是哪个子类**——透明替换失败。更隐蔽的代价：调用方被迫"防御"：

```java
// ❌ 调用方被迫识别具体类型 —— 多态的意义完全丧失
if (!(device instanceof ReadOnlyProbe)) {
    device.write(tag, value);
}
```

代码里一旦出现 `instanceof` + 分支处理子类，就是 LSP 违规的现场证据。

### 4.3 契约违规的三种典型形态

| 形态 | 表现 | 网关中的例子 |
|---|---|---|
| 违背后置条件 | 父类承诺的结果，子类给不了 | `write()` 承诺"写后读一致"，只读设备做不到 |
| 加强前置条件 | 父类不要求的限制，子类额外要求 | 父类 `connect()` 无前提，子类要求"必须先 `calibrate()`" |
| 抛出意外异常 | 父类签名里没有的异常，子类抛出来 | `UnsupportedOperationException`、空实现静默吞掉 |

第三种最常见也最危险——**空方法体比抛异常更坏**，它让调用方以为操作成功了。

### 4.4 正例：把"能力"抽成接口，而不是硬塞进继承树

问题根源是建模错误："只读设备"**本来就不是**"可写设备"的一种，is-a 不成立。正确做法把能力拆开：

```java
// ✅ 读是所有设备的能力
public interface Readable {
    DeviceSnapshot read();
}

// ✅ 写是部分设备的能力，单独成接口
public interface Writable {
    // 契约：写入成功后，下次 read 可读到新值
    void write(String tag, Object value);
}

public class ModbusDevice implements Readable, Writable {
    public DeviceSnapshot read() { /* ... */ }
    public void write(String tag, Object value) { /* ... */ }
}

public class ReadOnlyProbe implements Readable {
    public DeviceSnapshot read() { /* ... */ }
    // 没有 write —— 类型系统直接禁止，而不是运行时抛异常
}
```

调用方按能力声明依赖：

```java
// 只需要读的地方，声明 Readable —— 只读设备可以安全传入
public void collect(Readable device) { device.read(); }

// 需要写的地方，声明 Writable —— 只读设备在编译期就被挡在外面
public void control(Writable device, String tag, Object value) {
    device.write(tag, value);
}
```

违规时是**运行时炸弹**，修正后是**编译期拦截**——这就是健壮性的差别。

### 4.5 三个实操要点

**要点 1：继承前先问"契约能否全部兑现"**
判断 is-a 是否成立，不看名字像不像，看父类每条行为承诺子类能否兑现。兑现不了 → 不要继承，改用组合或拆接口。经典反例"正方形继承矩形"同理：矩形承诺"宽高可独立修改"，正方形兑现不了。

**要点 2：优先接口继承，慎用类继承**
`implements` 只继承契约，自由度高；`extends` 连实现一起继承，父类一改子类全受牵连。经验法则：**对外暴露用接口，类继承只留给"模板方法"这种确需复用骨架的场景**。

**要点 3：两个静态检测信号**

| 信号 | 说明 |
|---|---|
| 子类出现空实现 / 抛 `UnsupportedOperationException` | 契约兑现不了，is-a 不成立 |
| 调用方出现 `instanceof` 分支 | 多态失效，契约已被破坏 |

### 4.6 衔接

- 上承 OCP：`ParserRegistry` 能安全运转，前提是每个 `ModelParser` 实现都遵守同一契约。**LSP 是 OCP 扩展机制不出事的地基**——一个违约的实现类就能让注册表模式崩盘
- 下启 ISP："把写能力拆出去"正是接口隔离的手法；DIP 要求依赖接口，而接口契约靠 LSP 保证

## 5. ISP 接口隔离原则——别逼别人依赖他不用的东西

### 5.1 定义与本质

> **客户端不应该被迫依赖它不使用的方法。**

主语是**客户端**（接口使用方），但胖接口的伤害是双向的：

- **实现方**被迫写空方法 / 抛异常 → 就是第 4 节的 LSP 违规
- **使用方**被迫依赖一堆用不到的方法 → 这才是 ISP 违规

ISP 和 LSP 是同一个病根（胖接口）的两个视角。记忆锚点：**接口应该按"使用者的角色"来切，而不是按"提供者的能力总和"来堆**。

### 5.2 反例：一个 `DeviceManager` 塞进所有能力

```java
// ❌ 胖接口：六类能力全塞一起
public interface DeviceManager {
    DeviceSnapshot read();                          // 采集
    void write(String tag, Object value);           // 控制
    void configure(Map<String, String> params);     // 参数配置
    void upgradeFirmware(byte[] image);             // 固件升级
    DiagnosticsReport diagnose();                   // 自诊断
    void reboot();                                  // 远程重启
}
```

**伤害 1：实现方被迫造假**

```java
// 一个只读温度探头，被迫实现 6 个方法，5 个是假的
public class SimpleProbe implements DeviceManager {
    public DeviceSnapshot read() { /* 真实逻辑 */ }
    public void write(String tag, Object value) { throw new UnsupportedOperationException(); }
    public void configure(Map<String, String> params) { /* 空实现 */ }
    public void upgradeFirmware(byte[] image) { /* 空实现 */ }
    public DiagnosticsReport diagnose() { return DiagnosticsReport.EMPTY; }
    public void reboot() { /* 空实现 */ }
}
```

5 个假方法就是 5 颗 LSP 地雷。

**伤害 2：使用方被无关变更波及**

```java
// 告警引擎只需要 read()，却声明依赖整个 DeviceManager
public class AlarmRuleEngine {
    private final DeviceManager device;   // ❌ 依赖面过大

    public List<Alarm> evaluate() {
        return rules.check(device.read());   // 实际只用了 1/6 的能力
    }
}
```

| 代价 | 说明 |
|---|---|
| 接口成为变更磁铁 | 给 `DeviceManager` 加第 7 个方法，**所有实现类**被迫改动，哪怕告警引擎根本不关心 |
| 测试成本放大 | 给 `AlarmRuleEngine` 写单测，要 mock 一个 6 方法的接口，实际只用 1 个 |
| 复用被堵死 | 想换"只读数据源"（如 CSV 回放历史数据做告警回归测试），它实现不了 `upgradeFirmware`，进不来 |

### 5.3 正例：按客户端角色切分接口

切分方法：**先枚举客户端，看各自用哪些方法**：

| 客户端 | 用到的方法 |
|---|---|
| 告警引擎、存储写入 | `read()` |
| 控制下发 | `read()` + `write()` |
| 配置管理页 | `configure()` |
| 运维工具 | `upgradeFirmware()` + `diagnose()` + `reboot()` |

按这张表切：

```java
// ✅ 每个接口对应一组"总是一起被使用"的方法
public interface Readable {
    DeviceSnapshot read();
}

public interface Writable {
    void write(String tag, Object value);
}

public interface Configurable {
    void configure(Map<String, String> params);
}

public interface Maintainable {                    // 运维三件套总是一起用
    void upgradeFirmware(byte[] image);
    DiagnosticsReport diagnose();
    void reboot();
}
```

实现方各取所需，**一个假方法都不用写**：

```java
public class ModbusDevice implements Readable, Writable, Configurable, Maintainable {
    // 6 个方法全是真实逻辑
}

public class SimpleProbe implements Readable {
    public DeviceSnapshot read() { /* 仅此一个，干净 */ }
}
```

使用方声明**最小依赖**：

```java
public class AlarmRuleEngine {
    private final Readable device;   // ✅ 只依赖需要的能力

    public AlarmRuleEngine(Readable device) { this.device = device; }
}
```

三件好事同时发生：
1. 接口新增 `exportLog()` 与告警引擎无关——它依赖的是 `Readable`，纹丝不动
2. 单测只需 mock 一个单方法接口
3. CSV 回放数据源 `implements Readable` 即可接入告警回归测试——**复用路径被打开了**

### 5.4 三个实操要点

**要点 1：切分依据是"是否总是一起被使用"，不是方法数量**
`Maintainable` 把三个方法放一起，因为运维工具总是同时需要它们；强行拆成三个单方法接口，运维工具就要声明三个依赖，反而啰嗦。反方向的极端（每接口一方法）同样是过度设计——**除非它是函数式接口场景**（`Predicate`、`Function` 这类是语言特性，不算胖也不碎）。

**要点 2：两个静态检测信号**

| 信号 | 诊断 |
|---|---|
| 实现类出现空实现 / `UnsupportedOperationException` | 实现方视角的胖接口（与 LSP 信号重合） |
| 客户端持有大接口却只调用其中 1–2 个方法 | 使用方视角的胖接口 |

评审时看到第二条，直接问："这个类真正需要的是哪个能力切片？"

**要点 3：`default` 方法是缓解药，不是根治药**

```java
public interface DeviceManager {
    // ...
    default void exportLog() { /* 默认空实现 */ }   // 实现类不用改了
}
```

它只是把"编译错误"压下去，客户端依赖面过大、测试难 mock 的问题一个没解决。**接口该切还是要切**，`default` 留给"接口演进时向后兼容"的过渡期。

### 5.5 实战对照：防腐层就是 ISP 的放大应用

回看 08 课 KingSCADA 场景：SDK 暴露几十个方法，但 IoT 领域只需要"读标签值"。防腐层的正确姿势不是原样转发，而是**只暴露领域需要的那一切**：

```java
// 领域层看到的只有这个最小接口
public interface TagReader {
    Map<String, Object> readTags(List<String> tagIds);
}

// 适配器内部持有庞大的 SDK 客户端，但对外只露一个方法
public class KingScadaAdapter implements TagReader {
    private final KingScadaSdk sdk;   // 胖东西被关在适配器里
    // ...翻译 Val_xxx → DeviceTag
}
```

胖接口被锁在适配器内部，领域层永远面对最小契约——**防腐层在接口粒度上的理论依据就是 ISP**。

### 5.6 衔接

- 上承 LSP：第 4 节把 `Writable` 拆出去治好了只读设备的 LSP 病；本节给出通用方法论——按客户端角色切接口，一次治愈 LSP + ISP 两个病
- 下启 DIP：DIP 决定依赖方向，ISP 决定依赖的"宽度"——依赖**最小的**抽象

## 6. DIP 依赖倒置原则——高层定契约，低层来实现

### 6.1 定义与"倒置"到底倒的是什么

> 1. **高层模块不应该依赖低层模块，两者都应该依赖抽象。**
> 2. **抽象不应该依赖细节，细节应该依赖抽象。**

传统依赖方向顺直觉——业务逻辑（高层）直接用 MySQL、Kafka、Modbus 驱动（低层）：

```
传统方向（高层 → 低层）：

  AlarmService ──────> KafkaTemplate
  （告警业务）          （Kafka 客户端）

  换消息中间件 = 改业务代码 💥
```

DIP 把箭头**倒过来**：接口由高层按自己的需要定义，低层去实现它：

```
倒置后（都指向抽象，抽象归高层所有）：

  AlarmService ──────> AlarmSink <────── KafkaAlarmSink
  （定义契约）          （抽象）          （来实现契约）

  换消息中间件 = 新增一个实现类，业务代码零修改 ✓
```

"倒置"的准确含义：**接口的所有权从低层（工具提供方）转移到了高层（业务使用方）**。这是 DIP 与"面向接口编程"口号式理解的分水岭——不是"写个接口就行"，而是**接口归谁定义、放在哪个包里**的问题。这一点直接决定分包时"接口包放哪"。

### 6.2 反例：告警服务焊死在 Kafka 上

```java
// ❌ 高层直接依赖低层细节
@Service
public class AlarmService {

    private final KafkaTemplate<String, String> kafka;   // 焊死 Kafka

    public AlarmService(KafkaTemplate<String, String> kafka) {
        this.kafka = kafka;
    }

    public void onAlarm(Alarm alarm) {
        AlarmRecord record = enrich(alarm);
        // 业务逻辑里混着传输细节：topic 名、序列化、分区键
        kafka.send("iot-alarm", alarm.getDeviceId(), toJson(record));
    }
}
```

| 代价 | 场景 |
|---|---|
| 换不动 | 客户要求告警改走短信网关 / MQTT → 改 `AlarmService` 本体，全量回归 |
| 测不了 | 单测 `onAlarm` 的业务规则，必须起 Kafka（或 mock 一个重客户端） |
| 漏细节 | topic 命名、序列化格式这些**传输细节**渗进了业务类 |
| 方向错 | 最稳定的业务规则，依赖了最易变的传输配置 |

### 6.3 正例：高层定义 `AlarmSink`，低层排队实现

```java
// ✅ 第一步：接口定义在业务侧（domain/alarm 包），只描述"我要什么"
public interface AlarmSink {
    void send(AlarmRecord record);
}

// ✅ 第二步：业务类只依赖抽象，不知道消息去了哪
@Service
public class AlarmService {

    private final AlarmSink sink;

    public AlarmService(AlarmSink sink) {   // 构造器注入
        this.sink = sink;
    }

    public void onAlarm(Alarm alarm) {
        sink.send(enrich(alarm));           // 业务逻辑，无传输细节
    }
}

// ✅ 第三步：实现类放在基础设施包（infrastructure/alarm）
@Component
public class KafkaAlarmSink implements AlarmSink {
    private final KafkaTemplate<String, String> kafka;

    public KafkaAlarmSink(KafkaTemplate<String, String> kafka) {
        this.kafka = kafka;
    }

    public void send(AlarmRecord record) {
        kafka.send("iot-alarm", record.getDeviceId(), toJson(record));
    }
}

// 客户要求加短信通道？新增一个实现，AlarmService 零修改（OCP 兑现）
@Component
public class SmsAlarmSink implements AlarmSink {
    public void send(AlarmRecord record) { /* 调短信网关 */ }
}
```

四件好事：换通道只动基础设施包；单测传一个 `record -> captured.add(record)` 的 lambda 即可；传输细节被锁在 Sink 实现里；依赖方向与稳定方向一致。

### 6.4 依赖注入三形式：为什么首选构造器注入

DIP 是**原则**（依赖谁），DI 是**机制**（怎么把依赖递进来），两者不要混为一谈。

| 形式 | 写法 | 评价 |
|---|---|---|
| **构造器注入** | `public AlarmService(AlarmSink sink)` | ✅ 首选：依赖不可变（final）、缺失则启动即失败、单测无需容器 |
| Setter 注入 | `setSink(...)` | 可选依赖才用；对象可能处于"半初始化"状态 |
| 字段注入 | `@Autowired private AlarmSink sink;` | ❌ 避免：无法声明 final、单测必须靠反射或容器、隐藏依赖清单 |

字段注入最隐蔽的坏处：**看构造器签名就能知道一个类依赖什么**，字段注入把这份清单藏起来了。构造器参数超过 5 个会"硌手"，这个硌手感恰恰是"该类违反 SRP"的早期警报。

### 6.5 三个实操要点

**要点 1：接口归消费者所有（Role Interface）**
`AlarmSink` 只有一个 `send` 方法，因为它按**消费者**（`AlarmService`）的需要定义，而不是按 Kafka 的能力总和定义——这正是 ISP"按客户端角色切接口"在跨层场景的应用。推论：**接口应该和消费者放在同一个包/模块里**，而不是集中堆在一个 `api` 大包里（集中式接口包会让所有消费者互相牵连，11 课展开）。

**要点 2：不是所有类都值得抽接口**

| 该抽 | 不必抽 |
|---|---|
| 有 ≥2 个可预见实现（Kafka/短信/Mock） | 纯内部工具类、值对象 |
| 需要单测隔离（依赖外部资源） | 稳定且无外部依赖的领域逻辑 |
| 跨层/跨模块边界 | 同包内的协作细节 |

给每个类配一个 `IXxx` 接口是仪式性编程，只增加导航成本，不产生解耦收益。

**要点 3：依赖方向 = 编译期依赖方向，与运行时调用方向无关**
运行时永远是 `AlarmService` 调用 `KafkaAlarmSink`（数据从业务流向基础设施）；但**编译期** `AlarmService` 源码里不出现任何 Kafka 类型，依赖箭头指向 `AlarmSink` 接口。模块治理（10 课）与六边形架构（12 课）反转的都是这个编译期方向。

### 6.6 实战对照：Repository 是最典型的 DIP 应用

08 课 DDD 四层里"领域层定义 Repository 接口、基础设施层实现"就是 DIP 的标准姿势：

```java
// domain 包：领域层只认识这个
public interface AlarmRecordRepository {
    void save(AlarmRecord record);
    List<AlarmRecord> findUnacknowledged(String deviceId);
}

// infrastructure 包：MyBatis/JPA 细节全被关在这里
@Repository
public class MyBatisAlarmRecordRepository implements AlarmRecordRepository {
    private final AlarmRecordMapper mapper;   // MyBatis 类型不出本包
    // ...
}
```

收益：领域层单测用内存实现 `InMemoryAlarmRecordRepository`（一个 HashMap）即可跑，**测试速度从秒级降到毫秒级**；将来从 MySQL 换到时序库，领域层零改动。

### 6.7 五原则收束：一张关系图

![09-01 SOLID 五原则指向变化隔离]({{ site.baseurl }}/assets/svg/09-01-SOLID五原则指向变化隔离.svg)

```
              SRP：找到变化的轴（拆类）
                │
        ┌───────┴───────┐
        ▼               ▼
      OCP：为变化       ISP：接口按消费者
      预留扩展点        切到最小
        │               │
        └───────┬───────┘
                ▼
      LSP：保证每个实现都守约
                │
                ▼
      DIP：让依赖箭头全部指向这些抽象
```

- SRP 回答"**拆什么**"（变化轴）
- OCP 回答"**为什么拆**"（扩展不改老代码）
- ISP 回答"**接口切多细**"（按消费者）
- LSP 回答"**怎么保证不出事**"（行为契约）
- DIP 回答"**箭头往哪指**"（全部指向抽象）

五条原则最终交付同一个东西：**一组稳定的、最小的、被遵守的抽象**——这正是耦合度量要量化的对象。

## 7. 耦合度量——用数字回答"这个包拆得好不好"

### 7.1 为什么需要度量

前五节给了定性原则，但评审现场的争论往往是："我觉得该合并。" "我觉得不该。"——两边都是感觉。SOLID 之后还差一块拼图：**一组可以算出来的数字**，让"拆得好不好"从观点变成事实。这是 Robert C. Martin 提出的**包内聚与耦合度量**。

### 7.2 四个基础量：Ca / Ce / I

| 指标 | 全称 | 含义 | 记忆 |
|---|---|---|---|
| **Ca** | Afferent Couplings（传入耦合） | **有多少个别的包依赖我** | 我"被需要"的程度 |
| **Ce** | Efferent Couplings（传出耦合） | **我依赖多少个别的包** | 我"需要别人"的程度 |

由此定义**不稳定度**：

```
        Ce
I = ─────────     取值 0 ~ 1
     Ca + Ce
```

- **I = 0**：只有人依赖我，我不依赖任何人 → 极稳定（改我一次，下游全回归）
- **I = 1**：我只依赖别人，没人依赖我 → 极不稳定（我可以随便改，没人受影响）

直觉校准：**被依赖越多的包，越应该稳定；越稳定的包，越应该由抽象构成**。

### 7.3 抽象度 A 与主序列

![09-03 主序列与痛苦区]({{ site.baseurl }}/assets/svg/09-03-主序列与痛苦区.svg)

```
        抽象类 + 接口数量
A = ─────────────────────     取值 0 ~ 1
          类的总数
```

把每个包画在 **I（横轴）— A（纵轴）** 平面上，健康的包落在对角线上：

```
A
1 ┤ ●─────────────────────●  主序列 Main Sequence
  │  抽象且稳定              抽象但不稳定
  │  （领域接口包）           （少见，警惕）
  │        ╱
  │      ╱
  │    ╱
  │  ╱
0 ┤ ●─────────────────────●
  │  具体且稳定              具体且不稳定
  │  ⚠ 痛苦区                ✓ 易变实现区
  └───────────────────────── I
  0                         1
```

**主序列方程：A + I = 1**。含义：

- 横轴左端（I→0，被广泛依赖）→ 纵轴必须高（A→1）：**越被依赖，越要用抽象构成**
- 横轴右端（I→1，依赖很多别人）→ 纵轴必须低（A→0）：**干脏活累活的包就该是具体实现**，允许它频繁变动

这正是前五节的数字化表达：DIP 说"箭头指向抽象"，主序列说"被箭头指向的地方（低 I）必须是高 A"。

### 7.4 距离 D 与两个危险区

```
D = | A + I − 1 |     到主序列的垂直距离，0 最好，越大越糟
```

**痛苦区（Zone of Pain）：左下，I 低 + A 低**

```
特征：被很多人依赖，却全是具体类
后果：改一行，全系统回归 —— "痛苦"名不虚传
```

网关真实案例：`common-utils` 或 `device-core` 这类包，塞满具体的协议常量、报文工具类、全局配置类，全项目 20 个包都 import 它。**这是"大而全公共包"反模式的度量学诊断**。

**无用区（Zone of Uselessness）：右上，I 高 + A 高**

```
特征：一堆接口，却没人依赖它们（它们反而依赖别人）
后果：抽象的仪式感，零解耦收益 —— 为接口而接口
```

真实案例：给每个类配 `IXxx` 接口、接口和唯一实现放在同一个包里且从不替换——"仪式性编程"在度量上就落在无用区。

### 7.5 实战演算：网关四个包的健康体检

依赖关系：采集→领域、告警→领域、存储→领域、领域→无。

| 包 | Ca（谁依赖我） | Ce（我依赖谁） | I | A | D | 诊断 |
|---|---|---|---|---|---|---|
| `domain`（接口+领域模型） | 3（采集/告警/存储） | 0 | 0 | 0.8 | 0.2 | ✅ 近主序列左端，健康 |
| `collect`（Modbus 采集实现） | 0 | 1（domain） | 1.0 | 0.1 | 0.1 | ✅ 右端，易变实现区，正常 |
| `alarm`（告警规则实现） | 0 | 1（domain） | 1.0 | 0.2 | 0.2 | ✅ 同上 |
| `common`（大杂烩工具包） | 3 | 2 | 0.6 | 0.05 | **0.45** | ⚠ 偏离主序列，滑向痛苦区 |

读数结论：
1. `domain` 被三方依赖（Ca=3）且高度抽象（A=0.8）→ DIP 做对了
2. `collect`/`alarm` 没人依赖（Ca=0），可以随便重构 → SRP 拆轴的红利：**变化被关在 I=1 的包里**
3. `common` 的 D=0.45 全场最差——被广泛依赖却几乎无抽象，**数字直接指认了重构对象**

### 7.6 三个实操要点

**要点 1：度量用在包/模块粒度，不用在类粒度**
Ca/Ce 数的是"包间依赖"。单个类的"被依赖数"用 IDE 的 Find Usages 看就够了。这些数字是给"模块划分、分包"决策用的。

**要点 2：工具化，别手算**

| 工具 | 用法 |
|---|---|
| **JDepend** | 老牌，Maven 插件直接出 Ca/Ce/I/A/D 报表 |
| **ArchUnit** | 把依赖规则写成单测（10 课主力工具），违规即测试红 |
| **SonarQube** | 持续跟踪耦合类指标，看趋势 |
| **IDE 依赖矩阵** | IDEA Diagrams → Show Dependencies，肉眼找循环 |

节奏：**每次调整包结构/模块边界时跑一次**，作为重构前后的对照证据。

**要点 3：指标是诊断仪，不是 KPI**

- D 不是越小越好到强迫症程度：纯 DTO 包天然低 A，只要没人重度依赖它（Ca 小），偏离主序列也无妨
- 真正要盯的是**趋势**：某包 Ca 持续增长而 A 纹丝不动 → 正在滑向痛苦区，该抽接口了
- **循环依赖（A 依赖 B，B 依赖 A）比任何 D 值都严重**——它让两个包焊死成一个，发现即修（10 课讲 Enforcer 自动拦截）

## 8. 落地检查清单与全课收束

### 8.1 评审现场的五原则速查表

| 原则 | 违规信号（看到即查） | 修正动作 |
|---|---|---|
| SRP | 类描述要用"和"连接两件不相干的事；一个类被三个方向的需求反复修改 | 按变化轴拆类，用稳定数据结构衔接 |
| OCP | 新增一种情况要改老类的 if/else / switch | 抽接口建注册表；记住"第二次变化才抽象" |
| LSP | 子类空实现、抛 `UnsupportedOperationException`；调用方 `instanceof` 分支 | 拆能力接口，把假方法消灭在编译期 |
| ISP | 实现类有假方法；客户端持大接口只用 1–2 个方法 | 按"总是一起被使用"切接口，客户端声明最小依赖 |
| DIP | 业务类源码里出现 Kafka/MyBatis/HTTP 客户端类型 | 高层定义接口，实现下沉到基础设施包，构造器注入 |

### 8.2 重构决策三步流程

```
第一步：闻到味道
   上帝类 / if-else 膨胀 / 假方法 / 换不动底层
        │
第二步：度量定位
   数 Ca/Ce → 算 I/A/D → 找偏离主序列的包
   （循环依赖一票否决，发现即修）
        │
第三步：选原则动刀
   拆轴用 SRP，留扩展点用 OCP，
   拆能力用 LSP+ISP，倒箭头用 DIP
        │
验收：下次同类变化，需要改几个地方？
   改得越少越集中，重构越成功
```

### 8.3 一句话记住本课

> **SOLID 五原则只在做一件事——把变化隔离；Ca/Ce/I/A/D 只在做一件事——量化隔离得好不好。**

五条原则交付"一组稳定的、最小的、被遵守的抽象"，五个指标验证这些抽象是否放在了正确的位置。
