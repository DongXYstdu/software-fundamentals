# 分层架构深入：六边形与洋葱（L7 结构软实力 · 第四课）
## 1. 三层为什么会烂——贫血模型的病灶

### 1.1 先为三层说句公道话

controller → service → dao 三层的原始意图没有错：controller 管协议适配、service 管业务逻辑、dao 管持久化。**问题不在分层，在于实践中几乎所有团队都把它写成了同一副样子：贫血模型 + 事务脚本。** 本段解剖这个退化过程——它是理解六边形"为什么长这样"的必要铺垫。

### 1.2 贫血模型的标准长相

```java
// entity 层：纯数据袋，没有行为
public class AlarmRule {
    private Long id;
    private String deviceId;
    private Double threshold;      // 阈值
    private Integer windowMinutes; // 持续窗口
    private Boolean enabled;
    // getter/setter × 10 个，完
}

// service 层：所有逻辑都在这里
@Service
public class AlarmService {

    public void checkAlarm(Long deviceId, Double value) {
        // 规则加载
        List<AlarmRule> rules = ruleMapper.selectByDeviceId(deviceId);
        // 规则过滤：enabled 且超阈值 —— 业务规则裸奔在 Service 里
        for (AlarmRule rule : rules) {
            if (rule.getEnabled() && value > rule.getThreshold()) {
                // 窗口判断：查历史记录判断持续时长 —— 还是业务规则
                int count = recordMapper.countRecentOverrun(
                        deviceId, rule.getThreshold(), rule.getWindowMinutes());
                if (count >= rule.getWindowMinutes()) {
                    // 告警生成：去重、级别映射 —— 又是业务规则
                    if (recordMapper.existsActiveAlarm(deviceId, rule.getId()) == 0) {
                        AlarmRecord record = new AlarmRecord();
                        record.setDeviceId(deviceId);
                        record.setLevel(mapLevel(rule, value));   // 级别映射逻辑
                        record.setStatus("ACTIVE");
                        recordMapper.insert(record);
                        notifyService.send(record);               // 直接调另一个 Service
                    }
                }
            }
        }
    }
}
```

**`AlarmRule` 明明是"告警规则"这个业务概念，却不知道怎么判断自己是否被触发**——`value > threshold` 这条规则的本体住在 `AlarmService` 里。Martin Fowler 称之为**贫血模型（Anemic Domain Model）**：名义面向对象，实际是"数据结构 + 过程脚本"。

### 1.3 病灶清单：四条连锁反应

**病灶 1：Service 成为业务逻辑的黑洞。** 业务规则无家可归（实体是哑巴），只能全堆进 Service——09 课的"上帝服务"反例在三层架构里是**必然产物**：结构本身没给业务逻辑留位置。

**病灶 2：Service 互调成网，层次名存实亡。** `AlarmService` 调 `NotifyService`，`NotifyService` 调 `DeviceService`，`DeviceService` 回头调 `AlarmService`（设备上线清除告警）——"service 层"内部没有任何边界，一层里塞了一张任意连线的网。名义三层，实际"上薄下薄中间一坨"。

**病灶 3：业务规则不可复用、不可测试。** "超阈值持续 N 分钟"的判断和 Mapper 查询、去重、通知耦合在一个方法里，抠不出来；单测要 mock 两个 Mapper 再 mock NotifyService——**测的是过程，不是规则**。

**病灶 4：换技术 = 全层穿越。** "查历史记录判断持续时长"这条业务规则是用 SQL 写的（`countRecentOverrun`），换库 = 业务规则重写——技术选型的变化穿透三层，因为业务和技术从一开始就没分开。

### 1.4 关键区分："有层次" ≠ "层次分明"

| | 有层次 | 层次分明 |
|---|---|---|
| 判据 | 目录里有 controller/service/dao 三个包 | 每层知道**能依赖谁、不能依赖谁，且被强制执行** |
| 依赖方向 | service 层内部任意互调（网状） | 单向、可画在一张图上、ArchUnit 守着 |
| 业务与技术 | 搅在一起 | 业务规则有独立的家，技术只是替它打工 |
| 变化隔离 | 业务变动 Service；技术变穿三层 | 业务变只动领域；技术变只动适配器 |

**"层次分明"不是把类分进三个目录，而是——业务逻辑有唯一的家，依赖箭头全部单向可预期，变化被隔离在它所属的那一层。**

### 1.5 用前三课的尺子诊断三层

| 尺子 | 三层现状的诊断 |
|---|---|
| 09 SRP | 业务规则、流程编排、持久化查询搅在一个 Service 方法里 |
| 09 DIP | Service 直接依赖 Mapper 具体实现，箭头指向技术细节 |
| 09 主序列 | 巨型 service 包：被大量依赖（Ca 大）却全是具体类（A≈0）——痛苦区 |
| 10 模块治理 | service 层内部无边界 = "service 大杂烩" |
| 11 包结构 | controller/service/dao 是 by-layer 分包——删除测试必横穿 |

**结论：贫血三层不是"写错了"，而是结构上就没有给业务逻辑留位置。**

## 2. 六边形架构——端口与适配器全景

![从三层到六边形演进]({{ site.baseurl }}/assets/svg/12-01-从三层到六边形演进.svg)

### 2.1 名字的真相：重点不是"六"，是"内外"

六边形架构由 Alistair Cockburn 于 2005 年提出，正式名称**端口与适配器（Ports and Adapters）**。**"六"没有任何含义**——Cockburn 本人说过，画六边形只是因为边数够多、每条边都能挂适配器。唯一重要的是那条内外分界线：**应用内核在里面，技术在外面。** 读图盯两样：内核在哪、箭头往哪指。

### 2.2 全景图

![六边形端口与适配器全景]({{ site.baseurl }}/assets/svg/12-02-六边形端口适配器全景.svg)

```
        驱动侧（左）                                  被驱动侧（右）
   谁在"敲应用的门"                              应用让谁"替它打工"

  REST 配置台     MQTT 指令          MySQL 库      Kafka 集群
      │              │                ▲              ▲
      ▼              ▼                │              │
 [RestAdapter]  [MqttCmdAdapter]  [MyBatisRepo]  [KafkaSink]
      │              │                │              │
      ▼              ▼                │              │
 ───►端口          ───►端口        端口◄────────  端口◄───
 ┌─────────────────────────────────────────────────────────┐
 │                      应 用 内 核                          │
 │  应用层：用例编排（薄）—— 定义端口、组织流程、事务边界     │
 │  领域层：业务规则（纯）—— 实体、领域服务、规则判断         │
 │              所有依赖箭头，无一例外，指向内核               │
 └─────────────────────────────────────────────────────────┘
```

| 构件 | 是什么 | 前三课的对应物 |
|---|---|---|
| **端口 Port** | 内核定义的接口，与外界协作的唯一契约 | 09 课 DIP"高层定义的接口"、11 课 `api` 契约区 |
| **适配器 Adapter** | 端口的实现/调用者，住在内核外 | 11 课 `internal` 实现、08 课防腐层 |
| **应用层** | 用例编排：组织流程、开事务、调端口 | 10 课组合根装配的对象之一 |
| **领域层** | 纯业务规则，不知道谁在调它、数据去哪 | 10 课 `domain-core`（稳定锚点） |

### 2.3 驱动侧 vs 被驱动侧：判据只有一个——谁发起

> **外界发起、打进内核 → 驱动侧；内核发起、打出去 → 被驱动侧。**

| | 驱动侧（Driving） | 被驱动侧（Driven） |
|---|---|---|
| 别名 | 左侧、primary、入口 | 右侧、secondary、出口 |
| 发起方 | 外部 actor | 内核 |
| 端口形态 | 用例接口（"我能做什么"） | 能力接口（"我需要什么"） |
| 端口被谁实现/调用 | 适配器**调用**端口 | 适配器**实现**端口 |
| 网关实例 | REST 配置台、平台 MQTT 指令、**采集定时器** | MySQL 仓储、Kafka 告警出口、**Modbus 设备访问** |

易错点：**同一技术可同时出现在两侧**——MQTT 收指令是驱动侧（平台发起），MQTT 发遥测是被驱动侧（内核发起）；Modbus 被拆成定时器（左）+ 协议访问（右）。判据永远是"谁发起"，不是"什么技术"。

### 2.4 内核的两层：领域层纯，应用层薄

**领域层——业务规则的唯一的家。** 铁律：不依赖 Spring、MyBatis、Kafka，连应用层都不依赖。`AlarmRule` 在这里学会自己的行为：

```java
// 领域层：规则知道怎么判断自己是否被触发 —— 贫血实体活了
public class AlarmRule {
    public boolean triggeredBy(DeviceSnapshot snapshot, OverrunWindow window) {
        return enabled && snapshot.exceeds(tag, threshold) && window.lasted(windowMinutes);
    }
}
```

**应用层——用例编排。** 一个用例 = 一次完整业务动作。它很薄：加载领域对象 → 调领域规则 → 通过端口读写外部 → 落事务。**不写业务规则（领域层的事），不碰技术细节（适配器的事），只做组织。**

```java
@Service
public class EvaluateAlarmUseCase {

    private final DeviceAccessPort deviceAccess;    // 被驱动端口：读设备
    private final AlarmSink alarmSink;              // 被驱动端口：发告警

    @Transactional
    public void evaluate(Long deviceId) {
        DeviceSnapshot snapshot = deviceAccess.read(deviceId);   // 通过端口
        alarmRules.matching(deviceId).stream()
                  .filter(rule -> rule.triggeredBy(snapshot, ...))  // 规则归领域
                  .map(Alarm::from)
                  .forEach(alarmSink::send);                      // 通过端口
    }
}
```

对照 1.2 的 `AlarmService.checkAlarm`：规则判断回到 `AlarmRule`，SQL 查询变成端口调用，通知变成端口调用——**Service 从"规则黑洞"降格为"流程编排"，这就是贫血→分明的结构性修复。**

### 2.5 核心法则：依赖箭头全部指向内

```
适配器 ──► 端口 ◄── 应用层 ──► 领域层
   （内核不知道适配器存在）
```

这是 09 课 DIP 的**空间化**：把所有抽象（端口）画在几何中心，把所有技术（适配器）推到外围——箭头想指错方向都画不出来。用 10 课 SDP 验证：内核最稳定（业务规则变得慢），适配器最易变（换库换协议）——易变者依赖稳定者，方向完全一致。四课在此汇合。

### 2.6 网关端口清单推演

**列出所有外部 actor 和技术 → 每个问"谁发起" → 发起的挂左边配驱动端口，被调的挂右边配被驱动端口。** 清单本身是验收材料：内核里除端口外的任何包名出现技术名词（kafka/modbus/mysql），就是漏网之鱼。

## 3. 洋葱与整洁架构——同一思想的同心圆画法

![洋葱与整洁架构同心圆]({{ site.baseurl }}/assets/svg/12-03-洋葱与整洁架构同心圆.svg)

### 3.1 谱系

```
2005 六边形架构（Ports & Adapters）  Alistair Cockburn
   ↓ 继承"依赖指向内核"
2008 洋葱架构（Onion Architecture）  Jeffrey Palermo
   ↓ 继承"同心圆分层"
2012 整洁架构（Clean Architecture）  Robert C. Martin
```

**三者的核心是同一句话：业务在中心，依赖箭头全部指向中心。**

### 3.2 洋葱架构：一层一层剥

```
Infrastructure（基础设施：DB/消息/UI）        ← 最外圈：全是易变技术
   Application Services（应用服务）            ← 用例编排（薄）
      Domain Services（领域服务）              ← 跨实体业务规则
         Domain Model（业务概念的唯一的家）     ← 圆心
```

洋葱对六边形的两点发展：**内核内部显式分层**（领域模型 → 领域服务 → 应用服务，多出"领域服务"承载跨实体规则，如告警升级策略）；**基础设施整个推到最外圈**（连 UI 都只是外圈）。一句话：**洋葱 = 六边形 + 内核分层 + 基础设施全部外置**。

### 3.3 整洁架构：四圈与"依赖规则"

```
Frameworks & Drivers（框架与驱动：Spring/DB/UI）
   Interface Adapters（接口适配器：Controller/Repository 实现/网关）
      Use Cases（用例：应用特定业务规则）
         Entities（实体：企业级业务规则）
依赖规则：源代码依赖只能由外向内，无一例外
```

两点发展：**把"接口适配器"独立成显式一圈**；**区分 Entities（企业级规则，换应用还在，如"超温必告警"）与 Use Cases（应用级规则，如"每秒轮询后评估"）**。另有一个精妙机制（DIP 动态版）：**控制流与依赖流可以反向交叉**——用例调数据库（控制流向外），但通过依赖倒置，依赖流仍向内："调用出去、依赖进来"。

### 3.4 三架构词汇对照表

| 本课统一用词 | 六边形 | 洋葱 | 整洁 | 10/11 课对应物 |
|---|---|---|---|---|
| **领域层** | 内核-领域 | Domain Model + Services | Entities | `domain-core` / `domain` 包 |
| **应用层** | 内核-应用 | Application Services | Use Cases | 用例服务（11 课门面） |
| **端口** | Port | 隐含在内部接口中 | Use Case 输入/输出边界 | 11 课 `api` 契约区 |
| **适配器** | Adapter | Infrastructure 实现 | Interface Adapters | 11 课 `internal` / 08 课防腐层 |
| **技术设施** | 外部世界 | 最外圈 Infrastructure | Frameworks & Drivers | 10 课 infrastructure 模块 |
| **核心法则** | 箭头指向内核 | 箭头指向圆心 | 依赖规则向内 | SDP + DIP |

**四列说的是同一栋房子，只是户型图画法不同。**

### 3.5 实操建议：选一种词汇，贯穿到底

三种架构工程上可互换，**真正有害的是混用词汇**。网关项目选六边形词汇（actor 对称性极强：设备/MQTT/REST/定时器都可作为驱动方，驱动/被驱动之分对南北向流量分类不可替代）。检验团队是否真掌握：能不能一句话说清"哪个目录是内核、哪些是适配器、端口在哪定义"——答不上来的，画了六边形也是三层换皮。

### 3.6 与 08 课 DDD 的关系

**DDD 提供领域层内部的设计方法（实体/值对象/聚合/领域事件怎么建模），六边形/洋葱/整洁提供领域层与外界的边界协议（依赖如何反转、端口如何定义）**——一个管内核的"内容"，一个管内核的"围墙"。两者组合才是完整答案。

## 4. 端口设计——粒度、归属与命名

### 4.1 驱动端口与被驱动端口是两种不同的动物

| | 驱动端口（左） | 被驱动端口（右） |
|---|---|---|
| 本质 | **用例接口**："我能做什么" | **能力接口**："我需要什么" |
| 定义者 | 应用层 | 应用层 |
| 实现者 | **应用层自己** | **适配器** |
| 调用者 | 驱动适配器 | 应用层用例 |
| 命名风格 | 业务动词（`pollAll`） | 能力名词（`AlarmSink`） |

最常见理解偏差：以为两种端口都由适配器"实现"。**驱动端口的实现者是应用层**（REST 适配器只是把 HTTP 翻译成对它的调用）；只有被驱动端口才由外部适配器实现。

### 4.2 粒度：两条不同的切分规则

**驱动端口按 actor 切（ISP 的 actor 版）**——一个外部 actor 一个端口，绝不共享：

```java
// ❌ 三个 actor 共享一个"大用例接口" —— 给配置页加方法，定时器和 MQTT 适配器被动跟着动
public interface GatewayUseCase { ... }

// ✅ 一个 actor 一个端口
public interface PollDevicesUseCase { void pollAll(); }
public interface RuleConfigUseCase  { Result configure(RuleCmd); }
public interface ControlUseCase     { void execute(CtrlCmd); }
```

**被驱动端口按消费场景切（09 课 ISP 直接升维）**：

```java
// ❌ 胖端口
public interface DeviceAccessPort {
    DeviceSnapshot read(Long deviceId);
    void write(Long deviceId, String tag, Object value);
    DiagnosticsReport diagnose(Long deviceId);
    void reboot(Long deviceId);
}

// ✅ 按消费场景切开
public interface DeviceSnapshotReader { DeviceSnapshot read(Long deviceId); }
public interface ControlValueWriter   { void write(Long deviceId, String tag, Object value); }
public interface DeviceMaintainer     { DiagnosticsReport diagnose(Long deviceId); void reboot(Long deviceId); }
```

结构红利：**Modbus 适配器可以实现多个窄端口，但端口本身按消费者切分——实现方合住没关系，接口必须分家。**

### 4.3 归属：端口必须定义在内核

| 端口放在哪 | 依赖方向 | 后果 |
|---|---|---|
| **内核的应用层包**（正确） | 适配器 → 内核 | 换掉 Kafka，内核零改动 |
| 适配器模块（错误） | 内核 → 适配器 | **依赖反转当场失败**，六边形退回三层 |

11 课"接口归消费者所有"的架构级重演：消费者明确为应用层用例——端口住在应用层，适配器反向依赖进来。**端口在 domain-core 里定义，infrastructure 模块依赖并实现，SDP 自动满足。**

### 4.4 命名：技术中立，违者即泄漏

| ❌ 泄漏命名 | ✅ 中立命名 | 泄漏了什么 |
|---|---|---|
| `KafkaPublisher` | `AlarmSink` | 焊死"告警发 Kafka" |
| `ModbusPort.readHoldingRegisters(addr, count)` | `DeviceSnapshotReader.read(deviceId)` | 寄存器语义印在端口上 |
| `MyBatisAlarmRepo` | `AlarmRecordRepository` | 换 ORM = 改内核 |

最隐蔽的陷阱是**端口模仿底层 API 的形状**——照抄 Modbus SDK 的 `readHoldingRegisters(slaveId, startAddr, quantity)` 等于把协议细节引进内核，防腐层形同虚设。正确做法：端口说业务语言，适配器去翻译。

```java
// ✅ 端口说业务语言
public interface DeviceSnapshotReader {
    DeviceSnapshot read(Long deviceId);   // "给我这台设备的快照"
}

// 翻译留给适配器：deviceId → 点表 → 从站/地址 → byte[] → 业务快照
public class ModbusDeviceAdapter implements DeviceSnapshotReader {
    public DeviceSnapshot read(Long deviceId) {
        PointTable table = pointTables.of(deviceId);      // 点表：deviceId→地址映射
        byte[] raw = modbusClient.readHoldingRegisters(   // SDK 术语止步于此
            table.slaveId(), table.startAddr(), table.quantity());
        return table.decode(raw);
    }
}
```

**判据：内核开发者写代码时，需不需要知道"寄存器"这个词？需要 = 端口设计失败。**

### 4.5 网关端口清单：最终设计版

| 侧 | actor / 技术 | 端口 | 方法（最小集） |
|---|---|---|---|
| 驱动 | 采集定时器 | `PollDevicesUseCase` | `pollAll()` |
| 驱动 | 配置管理页 | `RuleConfigUseCase` | `configure(cmd)`、`listRules(query)` |
| 驱动 | 平台 MQTT | `ControlUseCase` | `execute(CtrlCmd)` |
| 被驱动 | Modbus/OPC-UA | `DeviceSnapshotReader` | `read(deviceId)` |
| 被驱动 | Modbus/OPC-UA | `ControlValueWriter` | `write(deviceId, tag, value)` |
| 被驱动 | MySQL | `DeviceRepository` | `save(device)`、`findBy(id)` |
| 被驱动 | TDengine | `TimeSeriesWriter` | `write(snapshot)` |
| 被驱动 | Kafka | `AlarmSink` | `send(alarmRecord)` |

每条一个回合检验：谁是 actor（驱动）或谁消费（被驱动）、名字有没有技术词、方法是不是业务语言。

### 4.6 事务边界注记

**事务是用例的属性，不是端口的属性**：`@Transactional` 标在应用层用例方法上（用例 = 一次完整业务动作 = 自然事务边界），被驱动端口保持纯粹。适配器若需特殊语义（事务提交后发送），在适配器内部用事务同步机制解决，不污染端口签名。

## 5. 适配器实现——南北向流量全图 + Modbus 轮询归驱动侧

### 5.1 适配器只有一种职责：翻译

> **适配器只做翻译，不含业务规则。** 一旦在适配器里发现 if 判断业务条件、计算业务数值——立刻搬进内核。

### 5.2 本课亮点：为什么 Modbus 轮询在驱动侧

**Web 思维的直觉**：外部系统是被访问的资源，Modbus 设备 = 数据库的等价物，自然归被驱动侧。**这个直觉对 Modbus 是错的。**

**追问"谁发起"**：Modbus 是主从协议——**设备永远不会主动说话，必须网关去问**。"读设备"这个动作的发起者不是人、不是平台、不是内核，而是——**时间到了**。定时器每秒触发，这个"时间事件"打进了应用，驱动了整个采集-评估用例。

```
Web 世界：  浏览器(人) ──发起──> 应用 ──发起──> 数据库
            驱动侧 actor 是"人"，数据库被动应答 → 被驱动侧

IoT 世界：  时钟(定时器) ──发起──> 应用 ──发起──> Modbus 设备
            驱动侧 actor 是"时钟"，设备被动应答 → 被驱动侧
            而时钟自己，是驱动侧 actor
```

结论：**Modbus 在六边形上被拆成两半**——`PollingScheduler`（采集定时器）在**驱动侧**（actor 是时钟，调用 `PollDevicesUseCase`）；`ModbusDeviceAdapter`（协议访问）在**被驱动侧**（实现 `DeviceSnapshotReader`/`ControlValueWriter`）。

对照验证：若设备换成 MQTT 直连上报（设备主动推送），actor 变成设备本身——适配器整体移到驱动侧。**同一个业务动作，发起方不同，侧别就不同。**

### 5.3 精妙推论：轮询频率必须是内核的知识

如果轮询周期写死在 `PollingScheduler`（`@Scheduled(fixedRate=1000)`）：回忆 10 课"高温告警触发后加密采集（1s→500ms）"的需求——频率决策是**业务规则**（跟告警级别、设备重要性挂钩），写死在适配器里 = 业务规则泄漏到驱动侧。正解是**哑定时器 + 内核频率表**：

```java
// 驱动侧适配器：哑的，只知道"每 tick 问一次内核现在该干什么"
@Component
public class PollingScheduler {

    private final PollingPlanPort pollingPlan;   // 被驱动端口：问内核要频率表
    private final PollDevicesUseCase pollDevices;

    @Scheduled(fixedRate = 100)                  // 最小分辨率 100ms，仅此而已
    public void tick() {
        for (Long deviceId : pollingPlan.dueDevices(now())) {
            pollDevices.poll(deviceId);          // 到期的设备，交给用例
        }
    }
}
```

```java
// 内核：频率是领域知识，可随告警动态调整
public class PollingPlan {
    private final Map<Long, Duration> rates = new ConcurrentHashMap<>();

    public void increaseRate(Long deviceId) { rates.put(deviceId, Duration.ofMillis(500)); }
    public void restoreRate(Long deviceId)  { rates.put(deviceId, Duration.ofSeconds(1)); }
    public boolean isDue(Long deviceId, Instant now) { /* 按当前频率判断是否到期 */ }
}
```

**加密采集之所以在 10 课成环，正是因为轮询调度（业务知识）被错放在采集模块里当成了"技术细节"**。六边形把它归位到内核，环从根上消失。

### 5.4 南北向流量全图

```
   [RestConfigAdapter]     [MqttControlAdapter]    [KafkaAlarmSink]
        REST 配置页            平台下发指令              告警上报
            │ 调用                 │ 调用                  ▲ 实现
            ▼                     ▼                        │
  RuleConfigUseCase    ◄─驱动端口─ ControlUseCase   AlarmSink 被驱动端口─┘
  ┌────────────────────────────────────────────────────────────┐
  │                        应 用 内 核                          │
  │   应用层：用例 + 全部端口定义   领域层：AlarmRule/PollingPlan │
  │                  箭头全部指向内核 ▲▲▲                        │
  └────────────────────────────────────────────────────────────┘
      ▲ 实现                                  ▲ 调用
  DeviceSnapshotReader/ControlValueWriter   [PollingScheduler]
            │                                │ 调用 PollDevicesUseCase
      [ModbusDeviceAdapter]                  │（驱动侧：时钟是 actor）
```

读图口诀：**北向左侧是"人和平台"（REST/MQTT 指令），北向右侧是"上报出口"（Kafka），南向右侧是"设备访问"（Modbus），南向左上角还挂着一个特殊 actor——时钟。**

### 5.5 四个适配器的实现骨架

**REST 适配器**：`@RestController`，DTO→命令、结果→VO，纯翻译。
**MQTT 指令适配器**：`@MqttListener` 收报文，`CtrlCmdParser.parse` 协议解析后交用例。

**Modbus 适配器（衔接 09 课 OCP 注册表）**：

```java
@Component
public class ModbusDeviceAdapter implements DeviceSnapshotReader, ControlValueWriter {

    private final ModbusClient client;                 // SDK 止步于此
    private final PointTableStore pointTables;         // deviceId → 从站/地址映射
    private final ParserRegistry parsers;              // 09 课：型号解析注册表

    public DeviceSnapshot read(Long deviceId) {
        PointTable table = pointTables.of(deviceId);
        byte[] raw = client.readHoldingRegisters(
            table.slaveId(), table.startAddr(), table.quantity());
        return parsers.parse(table.model(), raw);      // 新型号 = 新增 Parser，零修改
    }
}
```

两个前三课构件在此会师：**点表**（4.4 的翻译材料）+ **ParserRegistry**（09 课 OCP 扩展点）——六边形适配器正是它们理所应当的住处。

**Kafka 告警出口**（09 课 DIP 原班人马）：`KafkaAlarmSink implements AlarmSink`，topic/序列化/分区键全在适配器里。

### 5.6 适配器的验收：三条共性纪律

| 纪律 | 检查法 |
|---|---|
| **薄** | 只做协议翻译/格式转换；出现 if 业务条件 = 泄漏 |
| **可独立替换** | 删掉 Kafka 适配器换 SMS 适配器，内核与用例测试零改动 |
| **可独立测试** | 驱动适配器 mock 端口即测；被驱动适配器 mock SDK 即测 |

**六边形把"架构"变成了"可单测的日常代码"**：内核纯 Java，全项目 90% 的测试不需要容器、数据库、网络——对照病灶 3（规则不可测），结构性翻案。

## 6. 存量迁移——贫血三层的六边形改造

### 6.1 迁移的总策略：不重写，做映射

| 三层 | 六边形去处 | 迁移动作 |
|---|---|---|
| `controller/` | 驱动适配器 | **改**（挂在内核外） |
| `service/` | **拆成两半** | 编排部分 → 应用层用例；业务规则 → 领域层 |
| `mapper/` + ORM 实体 | 被驱动适配器 | `AlarmRuleMapper` + Entity → `MyBatisRuleRepository` + DO |
| `entity/`（贫血数据袋） | **领域模型（内核）** | 补行为：`AlarmRule` 学会 `triggeredBy()` |

**Service 是唯一需要动刀拆分的层**：它同时背着编排和规则两种职责——09 课 SRP 的迁移版：一个类里的两条变化轴，各自回各自的家。

### 6.2 六步迁移法（每步独立可提交）

**第 1 步：Mapper 上提接口（被驱动端口就位）**——不改逻辑，在 Mapper 前垫端口：`AlarmRecordRepository`（`existsActiveAlarm`/`save`），`MyBatisAlarmRecordRepository` 包一层。验收：Service 改依赖接口，`mvn test` 绿。

**第 2 步：业务规则下沉领域（贫血→充血）**——`triggeredBy(value)`、`windowSatisfied(count)`、`levelFor(value)` 搬进 `AlarmRule`。验收：纯内存领域单测（毫秒级）。

**第 2.5 步：窗口判断的翻译归位**——"数记录数"是 SQL 实现细节，业务语义是"持续超限 N 分钟"：

```java
// 被驱动端口说业务语言
public interface OverrunCounter {
    int countMinutes(Long deviceId, Double threshold, Duration window);
}

// 适配器翻译成 SQL
public class MyBatisOverrunCounter implements OverrunCounter {
    public int countMinutes(Long deviceId, Double threshold, Duration window) {
        return mapper.countRecentOverrun(deviceId, threshold, (int) window.toMinutes());
    }
}
```

**第 3 步：通知出口端口化**——`AlarmSink` 端口 + `KafkaAlarmSink` 实现，`AlarmService` 不再 import `NotifyService`——病灶 2（Service 互调成网）的第一根线被剪断。

**第 4 步：Service 瘦身为用例**——只剩编排：加载规则 → `rule.triggeredBy()` → `rule.windowSatisfied(overrunCounter...)` → 去重 → 落库 → `alarmSink.send()`。同样的流程，规则各回各家；mock 三个端口即可单测。

**第 5 步：Controller 改为驱动适配器**——名字从 Controller 改为 Adapter，只做 DTO/VO 翻译。

**第 6 步：包结构归位**——`application/`（用例 + `port/` 端口定义）、`domain/`（充血模型）、`infrastructure/`（MyBatis/Kafka 适配器 + DO）。验收：内核包 grep 不到 kafka/mybatis/modbus。

### 6.3 迁移的节奏与守护

| 节奏 | 说明 |
|---|---|
| **一个 Service 一次** | 每次只迁移一个垂直切片，不动无关代码 |
| **每步独立可提交** | 六步 = 六个 PR，每步测试全绿，随时可停 |
| **借需求迁移** | 改到哪迁到哪，不搞运动式重构 |
| **ArchUnit 冻结防回潮** | 新六边形区域先上分层规则，旧区域冻结存量 |

两个坑：**不要一口气全量抽 Repository**（只抽当前用例消费的方法——ISP 端口按消费者裁剪）；**ORM 实体别急着删**（改名 `AlarmRuleDO` 挪进 infrastructure，改名成本 5 分钟，删错的成本是一个下午）。

### 6.4 何时停止：完成判据

| 判据 | 检查法 |
|---|---|
| 核心规则已归位 | 最常变的 3–5 条业务规则，改动只涉及领域层 |
| 端口验收通过 | 命名检验（内核无技术词）+ 端口清单齐全 |
| 架构测试就位 | ArchUnit 规则全绿，存量冻结 |

**迁移的终点不是"形状像六边形"，是"变化被隔离"。**

## 7. 守卫层次分明——ArchUnit 分层规则与包结构对应

### 7.1 六边形要靠规则活着，不靠自觉

最大的风险不是"迁移不完整"，而是**腐化**：三个月后某人在用例里直接 `@Autowired KafkaTemplate`，六边形悄悄破洞——没人报错。**有层次 ≠ 层次分明，分明 = 被强制执行。**

### 7.2 分层规则集（可直接抄）

```java
@AnalyzeClasses(packages = "com.example.gateway")
public class HexagonTest {

    // 规则1：领域层不依赖任何东西（纯度铁律）
    @ArchTest
    static final ArchRule domain_is_pure =
        noClasses().that().resideInAPackage("..gateway.domain..")
            .should().dependOnClassesThat()
            .resideInAnyPackage("..gateway.application..",
                                "..gateway.infrastructure..", "..gateway.adapter..");

    // 规则2：应用层不依赖适配器/基础设施（箭头向内执法）
    @ArchTest
    static final ArchRule application_depends_inward =
        noClasses().that().resideInAPackage("..gateway.application..")
            .should().dependOnClassesThat()
            .resideInAnyPackage("..gateway.infrastructure..", "..gateway.adapter..");
    // 允许依赖 domain —— 分层只禁反向

    // 规则3：内核不依赖任何技术框架（命名检验的自动化）—— 最有效，第一天就上
    @ArchTest
    static final ArchRule 核心不依赖技术框架 =
        noClasses().that().resideInAnyPackage("..gateway.domain..", "..gateway.application..")
            .should().dependOnClassesThat()
            .resideInAnyPackage("org.springframework..", "org.apache.kafka..",
                                "org.apache.ibatis..", "net.wimpi.modbus..");

    // 规则4：端口实现必须住在适配器包（防"内核里直接 new 实现类"）
    @ArchTest
    static final ArchRule 端口的实现必须在适配器包 =
        classes().that().implementInterface(AlarmSink.class)   // 具体端口逐个声明
            .should().resideInAPackage("..infrastructure..");
    // 实用兜底：适配器包内实现端口 的类必须以 Adapter/Repository/Sink 结尾

    // 规则5：分层依赖无环（ADP 执法）
    @ArchTest
    static final ArchRule 分层切片无环 =
        slices().matching("com.example.gateway.(*)..")
            .should().beFreeOfCycles();
}
```

| 规则 | 守护 |
|---|---|
| domain 纯净 | 领域规则的唯一家不被污染 |
| application 向内 | 箭头全部指向内核（DIP 空间化） |
| 内核无技术框架 | 4.4 命名检验的自动化，**最有效** |
| 端口实现在适配器 | 防"内核里直接 new 实现类" |
| 分层无环 | ADP 底线 |

### 7.3 六边形与 11 课包结构的对应（最后一公里）

```
gateway-alarm 模块内部：
com.example.gateway.alarm
├── application/          ← 应用层：用例 + 端口定义
│   ├── EvaluateAlarmUseCase.java      ← 11 课的"门面"就是用例
│   └── port/                          ← 11 课的 api 契约区就是端口
├── domain/               ← 领域层：AlarmRule（充血）、AlarmRecord
├── infrastructure/       ← 被驱动适配器（11 课的 internal 实现区）
└── adapter/              ← 驱动适配器（REST/MQTT/定时器）
```

| 六边形构件 | 包结构（11 课） | 模块结构（10 课） |
|---|---|---|
| 端口 | `application/port/`（api 契约区） | domain-core 模块的接口 |
| 应用层用例 | `application/` 的门面类 | 各业务模块的 facade |
| 领域层 | `domain/` 包 | domain-core 模块的模型 |
| 适配器 | `infrastructure/` + `adapter/`（internal 实现区） | infrastructure 模块 |

**六边形不是在 11 课结构之外另起炉灶，而是给它补上"用例 + 端口"这一层语义**——api 包重命名为 port、门面类重命名为 UseCase，六边形即成，四课贯通。

### 7.4 存量项目：按层冻结，逐步收紧

```
第 1 周：上"domain 纯净"规则（存量违规先冻结）
第 2 周：上"内核无框架"规则 —— 最有效，最先全绿
第 3 周：上"application 向内"规则
第 N 周：port 归位规则，配合垂直切片迁移逐步解冻
```

原则：**每条规则上线时存量必须已被冻结或已为零**——只对新代码零容忍，团队才不会因"满屏红"废弃架构测试。

## 8. 落地检查清单与全课收束

### 8.1 六边形落地七步操作手册

```
第一步：列 actor 清单（谁发起）→ 得到驱动/被驱动端口清单
第二步：端口定义进内核 application/port/，命名技术中立，方法说业务语言
第三步：适配器薄翻译 —— 驱动侧调端口，被驱动侧实现端口（点表+注册表住这）
第四步：定时器哑化 —— @Scheduled 只留最小分辨率，频率表进内核
第五步：存量按垂直切片六步迁移 —— 一个 Service 一次，六个 PR 各自全绿
第六步：ArchUnit 五规则 + 按层冻结 —— "内核无框架"第一天就上
第七步：验收 —— 内核 grep 无技术词 · 适配器可整替 · 核心规则毫秒级单测
```

### 8.2 评审现场速查表

| 场景 | 检查项 |
|---|---|
| 新建接口 | 是端口还是内部接口？消费者/actor 是谁？放 application/port 了吗？ |
| 接口/类名出现 Kafka/Modbus/MyBatis | 且在内核里 = 泄漏，改名或挪到适配器 |
| Service 方法里出现 if 业务条件 | 规则下沉领域层，Service 只留编排 |
| `@Scheduled` 里写轮询频率 | 频率决策是业务知识 → 内核频率表 |
| Controller 里组装业务数据 | 适配器只做协议翻译，业务动作交用例 |
| 引入新技术 | 只新增适配器？要动内核 = 端口设计有问题 |
| 两个 Service 要互调 | 内核调端口，或发领域事件（10 课手法三） |

### 8.3 一句话记住本课

> **六边形 = 09 课 DIP 的空间化：业务居心，箭头向内；端口说业务语言，适配器只做翻译——在 IoT 里，时钟也是 actor。**

"引入架构后仍层次分明"的三个可执行判据：

1. **侧别判据**：谁发起，谁就是驱动侧——Modbus 拆成定时器（左）+ 协议访问（右）
2. **语言判据**：内核代码里出现技术名词 = 层次已被污染，ArchUnit 当场报红
3. **变化判据**：业务变只动内核、技术变只换适配器——做不到，形状再像也是三层换皮
