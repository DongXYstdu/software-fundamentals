### 二、分析执行计划：EXPLAIN 详解

使用 `EXPLAIN` ?`EXPLAIN ANALYZE`（MySQL 8.0+）查?SQL 执行计划?

```sql
EXPLAIN SELECT * FROM orders WHERE user_id = 100 AND status = 'PAID';
```

**关键字段解读**?

| 字段 | 含义 | 关注?|
|---|---|---|
| `type` | 访问类型（效率从高到低） | `system` > `const` > `eq_ref` > `ref` > `range` > `index` > `ALL`（全表扫描，需优化?|
| `key` | 实际使用的索?| 是否命中预期索引 |
| `key_len` | 使用的索引长?| 越短越好，判断联合索引使用情?|
| `rows` | 预估扫描行数 | 越少越好 |
| `Extra` | 额外信息 | `Using filesort`（文件排序）、`Using temporary`（临时表）需要关?|

**type 类型效率对比**?

![](https://aka.doubaocdn.com/s/XudE1wZNoJ)

- **`system/const`**：最高效，主键或唯一索引查询，最多返回一行数据?
- **`eq_ref`**：唯一索引关联查询，每个索引键值对应一行?
- **`ref`**：非唯一索引查询，可能返回多行?
- **`range`**：索引范围扫描，?`BETWEEN`、`>`、`<`、`IN` 等操作?
- **`index`**：遍历整个索引树，比 `ALL` 稍好（索引比数据文件小）?
- **`ALL`**：全表扫描，**性能最差，需要重点关注优?*?

### 三、索引优化：最常见的调优手?

#### 1. 索引创建原则

```sql
-- 为高频查询条件创建索?
CREATE INDEX idx_user_status ON orders(user_id, status);

-- 联合索引遵循"最左前缀原则"
-- 索引 (a, b, c) 可支持：a | a,b | a,b,c 的查?
-- 无法支持：b | c | b,c 的查询（缺少最左列?
```

#### 2. 索引失效场景

![](https://aka.doubaocdn.com/s/jzX21wZNoJ)

- **函数/计算**：索引列经过函数处理后，B+ 树的有序性被破坏，无法利用索引?
- **隐式转换**：MySQL 会将字符串转数字进行比较，相当于对列做了函数操作?
- **LIKE 前缀通配**：`%xxx` 无法利用 B+ 树的有序性，只能全扫描?
- **OR 条件**：只要有一个条件列没有索引，整体就会退化为全表扫描?
- **最左前缀**：联合索引按照定义顺序构建，跳过前面的列无法利用索引?
- **否定条件**：优化器可能认为返回数据量过大，直接全表扫描更高效?

### 四、SQL 语句优化技?

#### 1. 避免 SELECT *

```sql
-- ?不推荐：查询所有列，增?IO 和网络开销
SELECT * FROM orders WHERE user_id = 100;

-- ?推荐：只查询需要的?
SELECT order_id, amount, status FROM orders WHERE user_id = 100;
```

#### 2. 优化分页查询

```sql
-- ?深分页性能差：需要扫描前 100000 ?
SELECT * FROM orders LIMIT 100000, 10;

-- ?方案一：基于游标分页（需要连?ID?
SELECT * FROM orders WHERE id > 100000 LIMIT 10;

-- ?方案二：延迟关联（先?ID，再关联?
SELECT o.* FROM orders o
INNER JOIN (SELECT id FROM orders LIMIT 100000, 10) t
ON o.id = t.id;
```

#### 3. 优化 COUNT 查询

```sql
-- ?COUNT(*) 扫描全表
SELECT COUNT(*) FROM orders WHERE status = 'PAID';

-- ?维护计数表（适合高频统计场景?
CREATE TABLE order_stats (status VARCHAR(20), count INT);
-- 业务变更时同步更新计?
```

#### 4. 优化 ORDER BY

```sql
-- ?filesort：排序字段未走索?
SELECT * FROM orders WHERE user_id = 100 ORDER BY create_time;

-- ?创建联合索引，覆?WHERE + ORDER BY
CREATE INDEX idx_user_time ON orders(user_id, create_time);
```

### 五、表结构优化

#### 1. 选择合适的数据类型

## 面试高频追问

1. **联合索引?最左前缀原则"是什么？为什么这样设计？**

   联合索引按照定义顺序构建 B+ 树，先按第一列排序，第一列相同再按第二列排序，以此类推。查询时必须从最左列开始匹配才能利用索引的有序性?

2. **什么情况下应该创建索引？什么情况下不应该？**

   应创建：高频查询?WHERE 条件、JOIN 关联列、ORDER BY/GROUP BY 列、区分度高（基数大）的字段?

   不应创建：区分度低（如性别、状态只有几个值）、频繁更新的列、数据量小的表?

3. **如何优化大批量数据导入？**

   临时关闭索引（`ALTER TABLE ... DISABLE KEYS`）、使用批?INSERT（一条语句插入多行）、关闭唯一性检查、增?`innodb_buffer_pool_size`?
