INDEX idx_a_b_c (a, b, c)

-- ✅ 能走索引
WHERE a = 1
WHERE a = 1 AND b = 2
WHERE a = 1 AND b = 2 AND c = 3

-- ❌ 不能走索引
WHERE b = 2              -- 缺少最左列 a
WHERE c = 3              -- 缺少 a 和 b
WHERE b = 2 AND c = 3    -- 缺少最左列 a</code></pre> <p><strong>为什么要遵守</strong> ：联合索引的 B+ 树是按照定义顺序构建的，先按第一列排序，第一列相同再按第二列排序，以此类推。跳过前面的列就无法利用索引的有序性。</p> <p><strong>一句话总结</strong> ：联合索引像字典排序，必须从左边开始连续匹配，跳过前面的列就像在字典里直接翻 "中间的字"，无法利用有序性。</p> <H2>深度解析</H2> <H3>一、联合索引的 B+ 树结构</H3>   <p>上图展示了联合索引在 B+ 树中的存储结构。核心要点：</p> <ul> <li> <p><strong>全局有序 vs 局部有序</strong> ：只有第一列 <code>a</code> 是全局有序的，后面的列只在前面列相同的情况下才有有序性。</p> </li> <li> <p><strong>字典类比</strong> ：想象一本字典，先按 "首字母" 排序，首字母相同再按 "第二个字母" 排序。如果你跳过首字母直接查第二个字母，字典的有序性就失效了。</p> </li> <li> <p><strong>二分查找的前提</strong> ：B+ 树利用二分查找快速定位，前提是数据有序。跳过前面的列，后面的列无序，二分查找就失效了。</p> </li> </ul> <H3>二、最左前缀匹配规则详解</H3>   <p>上图总结了最左前缀匹配的核心规则。具体说明：</p> <ul> <li> <p><strong>规则一：必须从最左列开始</strong> 。 <code>WHERE b = 2</code> 缺少最左列 <code>a</code> ，无法利用索引的有序性，只能全表扫描。</p> </li> <li> <p><strong>规则二：中间不能跳过</strong> 。 <code>WHERE a = 1 AND c = 3</code> 跳过了 <code>b</code> ，只能使用 <code>a</code> 列的索引， <code>c</code> 无法走索引。</p> </li> <li> <p><strong>规则三：范围查询会 "断后"</strong> 。一旦出现范围查询（ <code>&gt;</code> 、 <code>&lt;</code> 、 <code>BETWEEN</code> 、 <code>LIKE 'x%'</code> ），该列之后的索引列无法被使用。</p> </li> </ul> <H3>三、范围查询 "断后" 问题</H3> <pre><code class="language-sql" data-lang="sql">-- 索引：INDEX idx_a_b_c (a, b, c)

-- ✅ 三个列都能走索引
WHERE a = 1 AND b = 2 AND c = 3

-- ⚠️ 只能使用 a, b，c 无法走索引
WHERE a = 1 AND b &gt; 2 AND c = 3
--            ↑ 范围查询，后面的 c "断了"

-- ✅ 范围查询放在最后，三个列都能利用索引
WHERE a = 1 AND b = 2 AND c &gt; 3</code></pre> <p><strong>原因分析</strong> ：</p>   <p>上图解释了范围查询 "断后" 的底层原因。核心问题：</p> <ul> <li> <p>范围查询筛选出的数据跨越了多个 "组"，后面的列在这些组内分别有序，但整体无序。</p> </li> <li> <p>无法利用 B+ 树的二分查找特性，只能逐条扫描。</p> </li> </ul> <H3>四、最左前缀的实际应用</H3> <pre><code class="language-sql" data-lang="sql">-- 场景：订单查询，常见查询条件组合

-- 查询模式分析
-- 1. 按用户查订单：WHERE user_id = ?
-- 2. 按用户+状态查：WHERE user_id = ? AND status = ?
-- 3. 按用户+时间范围查：WHERE user_id = ? AND create_time BETWEEN ? AND ?

-- ❌ 错误的索引设计
INDEX idx_status_user_time (status, user_id, create_time)
-- status 区分度低，放在最左边浪费

-- ✅ 正确的索引设计
INDEX idx_user_status_time (user_id, status, create_time)
-- user_id 区分度高，放在最左边
-- 等值条件在前，范围条件在后</code></pre> <p><strong>设计原则</strong> ：</p> <table> <thead> <tr> <th>原则</th> <th>说明</th> <th>示例</th> </tr> </thead> <tbody> <tr> <td>区分度高的列放前面</td> <td>提高索引过滤效果</td> <td><code>user_id</code> 比 <code>status</code> 区分度高</td> </tr> <tr> <td>等值条件放前面</td> <td>保证后面列能走索引</td> <td><code>WHERE a = 1 AND b &gt; 2</code> ， <code>a</code> 放前面</td> </tr> <tr> <td>范围条件放后面</td> <td>避免 "断后" 问题</td> <td><code>create_time</code> 放在联合索引最后</td> </tr> <tr> <td>覆盖常用查询</td> <td>一索引多查询</td> <td>一个 <code>(a,b,c)</code> 可支持 <code>a</code> 、 <code>a,b</code> 、 <code>a,b,c</code></td> </tr> </tbody> </table> <H3>五、特殊情况：跳过索引列</H3> <pre><code class="language-sql" data-lang="sql">-- 索引：INDEX idx_a_b_c (a, b, c)

-- MySQL 5.6+ 的索引下推优化
WHERE a = 1 AND c = 3

-- 没有 ICP：存储引擎返回所有 a=1 的记录，Server 层过滤 c=3
-- 有 ICP：存储引擎直接过滤 a=1 AND c=3，减少回表

-- EXPLAIN 结果
-- Extra: Using index condition（表示使用了索引下推）</code></pre> <p><strong>注意</strong> ：虽然 MySQL 5.6+ 有索引下推优化，但这只是在存储引擎层过滤数据，减少回表次数，并不是真正 "走索引"。 <code>c = 3</code> 仍然无法利用索引的有序性快速定位。</p> <H3>六、常见误区</H3>   <p>上图总结了最左前缀原则的常见误区。关键澄清：</p> <ul> <li> <p><strong>条件顺序无关</strong> ：MySQL 优化器会自动重排 <code>WHERE</code> 条件，程序员不需要关心书写顺序。</p> </li> <li> <p><strong>SELECT 列不影响最左前缀</strong> ：只影响是否使用覆盖索引（ <code>Using index</code> ）。</p> </li> <li> <p><strong>OR 条件的陷阱</strong> ： <code>OR</code> 条件通常导致全表扫描，因为无法保证所有条件都能走索引。</p> </li> <li> <p><strong>范围条件也适用</strong> ：只是后面的列无法走索引，本身还是能用到索引的。</p> </li> </ul> <H2>面试高频追问</H2> <ol> <li> <p><strong>联合索引 (a, b, c)，WHERE a = 1 AND c = 3 能走索引吗？</strong></p> <ul> <li>只能走 <code>a</code> 列的索引， <code>c</code> 无法走索引。但 MySQL 5.6+ 会使用索引下推（ICP）在存储引擎层过滤 <code>c = 3</code> ，减少回表次数。</li> </ul> </li> <li> <p><strong>如何判断 SQL 是否走对了联合索引？</strong></p> <ul> <li>使用 <code>EXPLAIN</code> 查看 <code>key</code> （使用的索引名）、 <code>key_len</code> （索引长度）。 <code>key_len</code> 可以判断使用了联合索引的几列。</li> </ul> </li> <li> <p><strong>联合索引列顺序如何设计？</strong></p> <ul> <li>区分度高的列放前面、等值条件列放前面、范围条件列放后面、考虑查询频率和覆盖索引需求。</li> </ul> </li> </ol> <H2>常见面试变体</H2> <ul> <li>"为什么联合索引不遵循最左前缀就无法走索引？"</li> <li>"范围查询为什么会导致后面的索引列失效？"</li> <li>"索引下推是什么？和最左前缀有什么关系？"</li> </ul> <H2>记忆口诀</H2> <p><strong>最左前缀三原则</strong> ：必须从左始、中间不可跳、范围会断后</p> <p><strong>索引设计三要素</strong> ：区分度高在前、等值在前范围后、覆盖常用查询模式</p> <H2>总结</H2> <p>最左前缀匹配原则是联合索引的核心使用规则，其根本原因是联合索引的 B+ 树按照定义顺序构建，先按第一列排序，第一列相同再按第二列排序。因此只有从最左列开始连续匹配，才能利用索引的有序性。实际应用中，应将区分度高的列、等值条件列放在前面，范围条件列放在后面，并通过 <code>EXPLAIN</code> 的 <code>key_len</code> 验证索引使用情况。</p> </div></main>
