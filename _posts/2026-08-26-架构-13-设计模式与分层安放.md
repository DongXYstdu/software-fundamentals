# 设计模式与分层安放（L7 结构软实力 · 收官课）
## 1. 模式为什么会破坏层次分明——反例解剖

### 1.1 一个"教科书式正确、工程上灾难"的代码

这段代码用了正宗的策略模式（GoF 23 之一）、注解齐全、命名规范——**每一步都符合模式书籍的描述，但它把六边形拖垮了**。场景：告警级别映射规则要支持多套策略（按超限倍数、按持续时间、按设备类型）。

```java
// 适配器包里定义的策略接口 —— 注意位置！
package com.example.gateway.infrastructure.strategy;

public interface LevelMappingStrategy {
    String mapLevel(AlarmRule rule, DeviceSnapshot snapshot);   // 参数是领域对象
}
```

```java
// 策略实现A：按超限倍数 —— 在适配器包里操作领域对象
package com.example.gateway.infrastructure.strategy;

@Component
public class OverrunRatioStrategy implements LevelMappingStrategy {

    @Autowired
    private AlarmRecordRepository repo;      // ← 引用内核端口（先记下，单看合法）

    @Override
    public String mapLevel(AlarmRule rule, DeviceSnapshot snapshot) {
        // 业务规则：超限 1.2 倍以上 = CRITICAL
        double ratio = snapshot.value() / rule.threshold();
        if (ratio >= 1.2) return "CRITICAL";
        if (ratio >= 1.0) return "WARNING";
        return "INFO";
    }
}
```

```java
// 用例里的调用处
package com.example.gateway.application;

@Service
public class EvaluateAlarmUseCase {

    @Autowired
    private List<LevelMappingStrategy> strategies;   // ← 内核 → 适配器，方向反了！

    public void evaluate(Long deviceId) {
        // ...
        AlarmRecord record = AlarmRecord.create(deviceId, rule, value);
        for (LevelMappingStrategy s : strategies) {   // 遍历策略
            String level = s.mapLevel(rule, snapshot);
            if (level != null) { record.setLevel(level); break; }
        }
    }
}
```

### 1.2 病理切片：箭头打结的三个节点

**病灶 1：内核反向依赖适配器（12 课规则 2 当场击穿）**

```
EvaluateAlarmUseCase（application）
        │ @Autowired List<LevelMappingStrategy>
        ▼
LevelMappingStrategy（infrastructure.strategy）   ← 依赖方向反了！
```

**病灶 2：策略实现引用内核端口（伪装的合法）**

```
OverrunRatioStrategy（infrastructure）
        │ @Autowired AlarmRecordRepository
        ▼
AlarmRecordRepository（application.port）   ← 单看合法，合起来灾难
```

单看这条箭头合法（适配器实现端口），但结合病灶 1——**内核和适配器互相依赖，六边形边界整体失守**。两条各自"说得通"的箭头合起来是灾难：**每个开发者都觉得自己的调用合理，没人看到全局打结**。

**病灶 3：业务规则住进了适配器（12 课规则 3 击穿）**

`if (ratio >= 1.2) return "CRITICAL"` 是**告警级别映射规则**——它属于内核。现在它躺在 infrastructure 包里，意味着：**换掉 Modbus 适配器、换掉 Kafka，这条规则跟着陪葬重写**。

### 1.3 三个病灶的合成后果

```
   ┌─ application ──────────────────┐      ┌─ infrastructure ─────────┐
   │  EvaluateAlarmUseCase           │      │  OverrunRatioStrategy    │
   │      │                          │      │      │                    │
   │      │ @Autowired 策略列表       │      │      │ @Autowired 仓储    │
   │      └─────────────────────────┼──①──▶│      │                    │
   │                                  │      │      │                    │
   │  AlarmRecordRepository（port）    │◀────┼──────┘                    │
   │                                  │  ②   │  LevelMappingStrategy    │
   │                                  │      │  （业务规则住在适配器）③  │
   └──────────────────────────────────┘      └──────────────────────────┘

   ① 内核→适配器（违规）  ② 适配器→内核（伪装合法）  ③ 业务规则错位
   = application ↔ infrastructure 互相依赖 = 六边形边界整体失守
```

**合成后果链条**：业务规则泄漏到适配器（③）→ 策略接口被迫放适配器（因为实现在这）→ 用例为了用策略反向 import 适配器（①）→ 边界失守 → ArchUnit 报红时团队选择"删规则保进度" → **层次分明彻底死亡，模式成了遮羞布**。

值得强调：这段代码**每一个局部都符合设计模式教材**。破坏不来自"模式用错了语法"，而来自**模式不知道自己该住哪**。**设计模式书籍从不回答"接口放哪个包"——但架构里，位置就是一切。**

### 1.4 病根：三个缺失的问题

| 缺失的问题 | 对应的前课知识 |
|---|---|
| **这个模式解决的变化轴是什么？**（映射规则会变——业务轴，不是技术轴） | 09 课 SRP/OCP：变化轴决定归属 |
| **这个模式属于六边形哪一层？**（业务规则 → 领域层） | 12 课：领域层是业务规则唯一的家 |
| **谁负责组装？**（组装是组合根的职责） | 12 课组合根、10 课装配纪律 |

## 2. 安放坐标系——二维定位法

![模式安放坐标系]({{ site.baseurl }}/assets/svg/13-01-模式安放坐标系.svg)

### 2.1 从三问到坐标系

```
模式 X 应该住在哪？
   ├─ 第一问：它解决什么变化？（09 课）───────────── 决定 X 轴：变化轴
   │     业务轴（规则/流程会变） or 技术轴（协议/中间件会变）
   ├─ 第二问：它的主干逻辑属于哪个层？（12 课）──── 决定 Y 轴：架构层
   │     领域层 / 应用层 / 适配器层 / 组合根
   └─ 第三问：谁负责组装？（10/12 课）─────────── 决定组装点
         多实现由组合根注入，业务代码只声明依赖
```

三问顺序有讲究：**先定变化轴，再定架构层**——同一模式在不同变化轴上会落在不同层（策略既可住领域层【规则族】也可住适配器层【协议族】）。跳过第一问直接选层，是第 1 段反例的原始病因。

### 2.2 横轴：变化轴（09 课 SRP 的模式版）

| 变化轴类型 | 特征 | 网关实例 |
|---|---|---|
| **业务轴** | 规则/流程/策略会变，需求方是业务/运维 | 告警级别映射规则、轮询频率策略、数据清洗流程 |
| **技术轴** | 协议/中间件/实现选型会变，需求方是架构/运维 | 寄存器解析算法、消息重试策略、序列化格式 |

判据一句话：**业务轴问"什么算违规"（领域专家改口），技术轴问"怎么实现"（工程师换方案）**。

### 2.3 纵轴：架构层（12 课的骨架）

| 层 | 对模式的承载力 |
|---|---|
| **领域层** | 业务规则模式的家：策略（规则族）、值对象、工厂方法、规格 |
| **应用层** | 流程编排模式的家：责任链、模板方法、事件发布 |
| **适配器层** | 技术翻译模式的家：适配器模式、装饰器（技术横切）、注册表工厂 |
| **组合根** | 组装模式的家：简单工厂、DI 装配、条件装配 |

### 2.4 二维定位法：交集定层

```
                Y 轴：架构层（12 课）
                组合根 ──────────── 装配区：DI 装配、简单工厂、条件装配
                适配器层 ─────────── 技术翻译区：适配器、装饰器、注册表
                应用层 ───────────── 流程编排区：责任链、模板方法、事件发布
                领域层 ───────────── 业务规则区：策略（规则族）、值对象、工厂方法
                  │
                  └──────────────────────────▶ X 轴：变化轴（09 课）
                          业务轴                   技术轴
```

| 象限 | 变化轴 × 架构层 | 典型模式 | 检验问题 |
|---|---|---|---|
| **左下** | 业务轴 × 领域层 | 策略（规则族）、值对象 | 规则改口时，只动这个包吗？ |
| **左上** | 业务轴 × 应用层 | 责任链、事件发布 | 流程加一步时，只动应用层吗？ |
| **右下** | 技术轴 × 领域层 | **⚠ 概念污染禁区** | 领域模型里不该有技术模式！ |
| **右上** | 技术轴 × 适配器层 | 适配器、装饰器、注册表 | 换协议时，只动适配器包吗？ |

**第一个红线：技术轴模式永远不进领域层（右下禁区）。**

### 2.5 三个补充规则

**规则 A：双轴模式的主轴优先。** 按主变化轴定位——问"这个具体场景里，哪条轴先变"。告警级别映射：业务先变 → 策略住领域层。寄存器解析：技术先变（换型号）→ 策略住适配器层（09 课 `ParserRegistry` 就此正名：技术轴的策略+注册表）。

**规则 B：跨层协作经端口。** 模式骨架跨层时（领域层策略需要读历史数据），**跨层引用必须经端口**（12 课铁律）。第 1 段反例的策略接口引用了 `AlarmRecordRepository` 端口——这本身合法，但接口定义在适配器导致内核反向依赖；正解是接口住领域层、按需注入端口。

**规则 C：组装永远在组合根。** 无论模式住哪层，**多实现的选择、创建、注入一律在组合根**完成。业务代码（任何层）只声明依赖接口，不 new 实现、不 import 实现类。**这条规则独立于坐标系——它是所有模式的公共守则。**

### 2.6 坐标系在网关的完整应用

| 模式 | 第一问：变化轴 | 第二问：层 | 落位 | 前课出处 |
|---|---|---|---|---|
| 级别映射策略族 | 业务轴（映射规则改口） | 领域层 | **左下** | 12 课 `levelFor` 演进 |
| 轮询频率策略（`PollingPlan`） | 业务轴（加密采集） | 领域层 | **左下** | 12 课哑定时器 |
| 采集-清洗-评估管道 | 业务轴（清洗步骤增删） | 应用层 | **左上** | 责任链 |
| 告警事件发布 | 业务轴（响应者会增） | 应用层 | **左上** | 10 课手法三 |
| 寄存器解析（`ParserRegistry`） | 技术轴（新型号接入） | 适配器层 | **右上** | 09 课 OCP 注册表 |
| 重试/熔断装饰 | 技术轴（中间件不稳） | 适配器层 | **右上** | 装饰器 |
| 适配器模式本尊 | 技术轴（协议翻译） | 适配器层 | **右上** | 12 课端口适配器 |
| Spring `@Configuration` 装配 | 组装 | 组合根 | 轴外 | 10 课组合根 |

**坐标系的意义不是分类游戏，是让"模式放哪"从争论变成查表。**

## 3. 领域层模式——策略（规则族）、值对象、工厂方法

### 3.1 领域层的模式准入门槛

领域层是"业务规则唯一的家"（12 课），准入门槛最严：**模式必须为业务规则服务，且不携带任何技术依赖**。三个领域层常客——策略（规则族）、值对象、工厂方法——共同特征：隔离的都是业务变化，且全是纯 Java。

### 3.2 策略（规则族）：第 1 段反例的正面重写

```java
package com.example.gateway.domain.alarm;   // ← 领域层，纯 Java

// 策略接口：业务语言，住领域层（第 1 段反例的最大修正点）
public interface LevelMappingStrategy {
    boolean supports(AlarmRule rule);
    AlarmLevel map(AlarmRule rule, DeviceSnapshot snapshot);
}

// 实现A：按超限倍数 —— 规则本体回到领域层
public class OverrunRatioStrategy implements LevelMappingStrategy {
    public boolean supports(AlarmRule rule) {
        return rule.levelPolicy() == LevelPolicy.OVERRUN_RATIO;
    }
    public AlarmLevel map(AlarmRule rule, DeviceSnapshot snapshot) {
        double ratio = snapshot.valueOf(rule.tag()) / rule.threshold();
        if (ratio >= 1.2) return AlarmLevel.CRITICAL;
        if (ratio >= 1.0) return AlarmLevel.WARNING;
        return AlarmLevel.INFO;
    }
}

// 领域服务：策略的使用者也在领域层，遍历选择
public class LevelMapper {
    private final List<LevelMappingStrategy> strategies;

    public LevelMapper(List<LevelMappingStrategy> strategies) {   // 组合根注入
        this.strategies = strategies;
    }

    public AlarmLevel mapOf(AlarmRule rule, DeviceSnapshot snapshot) {
        return strategies.stream()
                .filter(s -> s.supports(rule))
                .findFirst()
                .orElseThrow(() -> new IllegalStateException(
                        "无级别映射策略: " + rule.levelPolicy()))
                .map(rule, snapshot);
    }
}
```

**与反例的三点修正对照**：

| 反例（1.1） | 正例 | 修正依据 |
|---|---|---|
| 接口住 infrastructure.strategy | 接口住 domain.alarm | 变化轴是业务轴 → 领域层 |
| 用例 `@Autowired List<策略>` | 用例依赖领域服务 `LevelMapper` | 跨层引用经端口（规则 B） |
| 策略实现 `@Autowired` 仓储 | 策略纯 Java，无依赖 | 领域层准入门槛 |

**为什么这个策略模式不破坏层次**：箭头全部朝内，无一条穿透边界；换掉 Kafka/Modbus 策略纹丝不动；新增"按设备类型映射"策略——只加一个类，`LevelMapper` 零修改（OCP 兑现）。**模式与架构在此互相成就：架构给模式安放位置，模式给架构隔离变化。**

### 3.3 值对象：领域层的"隐形模式"

值对象（Value Object，DDD 战术模式）是使用频率最高却最少被识别为"模式"的构件：

> **用类型固化概念的定义，隔离"表示形式"的变化。**

```java
// 阶段1：裸 double —— 概念不存在，魔法数字遍布
// 阶段2：字段命名 —— 有名字但无行为，贫血前兆
private Double threshold;

// 阶段3：值对象 —— 概念有了定义和行为
public final class Threshold {
    private final double value;
    private final ThresholdUnit unit;

    public Threshold(double value, ThresholdUnit unit) {
        if (value < 0) throw new IllegalArgumentException("阈值必须非负");
        this.value = value; this.unit = unit;
    }

    public OverrunRatio ratioAgainst(DeviceSnapshot snapshot) {
        return new OverrunRatio(snapshot.value / value);
    }
}
```

**值对象隔离的变化轴**：`OverrunRatio` 的内部表示从 double 换 BigDecimal、告警级别从 String 换枚举——调用方零改动。**它就是 ISP"最小依赖"的对象版**：调用方依赖概念，不依赖表示。

网关值对象候选清单（可自查）：`Threshold`、`OverrunRatio`、`AlarmLevel`、`SlidingWindow`、`DeviceTag`。**判据：业务上"它是什么"（概念）与"它怎么存"（表示）能分开的名词，都值得值对象化**。

### 3.4 工厂方法：创建一致性收口

```java
public class AlarmRecord {
    private AlarmStatus status;         // private，外界改不了

    // 唯一合法创建路径：状态、去重键、时间戳全部由领域决定
    public static AlarmRecord create(AlarmRule rule, DeviceSnapshot snapshot, AlarmLevel level) {
        AlarmRecord record = new AlarmRecord();
        record.deviceId = snapshot.deviceId();
        record.ruleId = rule.id();
        record.level = level;                  // 类型是 AlarmLevel，不是 String
        record.status = AlarmStatus.ACTIVE;    // 创建即激活，不可能忘
        record.dedupKey = rule.dedupKeyWith(snapshot);
        record.raisedAt = Instant.now();
        return record;
    }
}
```

**判断信号**：构造一个对象时需要**执行业务规则**（生成去重键、设默认状态、校验组合合法性）——这些规则收口到 `create`。与值对象互补：**值对象约束"是什么"，工厂方法约束"怎么生"**。

### 3.5 领域层模式的红线

| 红线 | 判据 | 违者下场 |
|---|---|---|
| 红线 1：策略接口住领域层，实现在领域层，组装在组合根 | 接口所在包是 domain？ | 第 1 段反例重演 |
| 红线 2：领域模式纯 Java | import 了 Spring/Kafka/MyBatis？ | 12 课规则 3 报红 |
| 红线 3：技术轴模式禁入（右下禁区） | 策略隔离的是协议/重试/序列化？ | 概念污染，领域层变技术垃圾场 |

## 4. 应用层模式——责任链、模板方法 vs 组合、事件发布

### 4.1 应用层的模式准入门槛

应用层是"用例编排的家"——薄、只做流程组织。准入的模式必须是**流程编排工具**：隔离的变化轴是"**流程本身会变**"（步骤增删、顺序调整、响应者增减）。

### 4.2 责任链：数据处理管道

网关南向数据的天然形态是**管道**：原始帧 → 解析 → 清洗（去抖、滤波）→ 单位换算 → 告警评估。

```java
public interface FrameHandler {
    FrameContext handle(FrameContext ctx);    // 纯业务语言，无技术词
}

public class FramePipeline {
    private final List<FrameHandler> handlers;

    public FramePipeline(List<FrameHandler> handlers) {   // 组合根注入顺序
        this.handlers = handlers;
    }

    public FrameContext process(FrameContext ctx) {
        for (FrameHandler h : handlers) {
            ctx = h.handle(ctx);
        }
        return ctx;
    }
}

// 某个清洗步骤：只管自己那一步（注意：这是"流程决策"，不是"业务规则"）
public class DebounceHandler implements FrameHandler {
    public FrameContext handle(FrameContext ctx) { /* 去抖：同一测点 2 秒内重复值丢弃 */ ... }
}
```

**责任链在应用层成立的关键**：`FrameHandler` 隔离的变化轴是**清洗流程会变**——加一个步骤 = 加一个实现类 + 组合根调整顺序，管道本体零修改（OCP）。**与策略的本质区别**：策略是"多选一"，责任链是"依次全过"——**选一个用策略，串起来用责任链**。

**关键辨析**：`DebounceHandler` 里的 if 判断会不会违反"适配器不含业务规则"？不违反——**去抖是流程决策（这一帧要不要继续走），规则本体（什么算重复）可以下沉领域层**。分界线是**判断的对象**：判断"数据"归领域，判断"走向"归应用。

### 4.3 模板方法 vs 组合：继承与注入的正面对决（对比小节）

**场景**：采集流程骨架固定（连接 → 读 → 解析 → 断连清理），不同协议步骤实现不同。

**写法 A：模板方法（继承）**

```java
public abstract class AbstractPollingTask {

    public final DeviceSnapshot poll(DeviceConfig config) {   // 模板方法锁死流程
        connect(config);
        try {
            byte[] raw = read(config);
            return decode(raw);
        } finally {
            cleanup();
        }
    }

    protected abstract void connect(DeviceConfig config);   // 子类填空
    protected abstract byte[] read(DeviceConfig config);
    protected abstract DeviceSnapshot decode(byte[] raw);
    protected void cleanup() { /* 默认实现 */ }
}
```

**写法 B：组合（注入）**

```java
public class PollingOrchestrator {
    private final ConnectionFactory conn;     // 三个步骤抽象成接口
    private final RawReader reader;
    private final FrameDecoder decoder;

    public PollingOrchestrator(ConnectionFactory conn, RawReader reader, FrameDecoder decoder) {
        this.conn = conn; this.reader = reader; this.decoder = decoder;
    }

    public DeviceSnapshot poll(DeviceConfig config) {
        try (Connection c = conn.open(config)) {
            byte[] raw = reader.read(c, config);
            return decoder.decode(raw);
        }
    }
}
```

**正面对决表**：

| 维度 | 模板方法（继承） | 组合（注入） |
|---|---|---|
| 骨架复用方式 | extends 父类 | 持有三个接口 |
| 新协议接入 | 新建子类（**要读并理解父类**） | 新建三个实现类（**只看接口契约**） |
| 步骤级替换 | 不行——骨架焊死在父类 | 行——Reader 单独换 |
| 运行时换行为 | 不行（编译期定死） | 行（注入不同实现） |
| LSP 风险 | 有——子类覆写可能破坏契约 | 无——没有继承树 |
| 父类演化 | 父类一动全子类地震 | 编排类与实现类独立演化 |
| 09 课 LSP 结论 | "慎用类继承"的对象 | DIP 的标准形态 |
| **判分** | 适合：骨架稳定 + 填空少 + 无运行时替换 | **默认选择** |

**应用层的裁决**：模板方法不是死罪，但它是**弱选择**——只在"骨架极其稳定、填空类数量少、无运行时替换"时用。GoF"组合优于继承"在应用层的具体化：**能用注入的编排，不用继承的骨架**。12 课 `ModbusDeviceAdapter` 里"点表 + 解析器"的组合结构，就是写法 B 的既成事实。

### 4.4 事件发布：应用层的"广播总线"

```java
@Service
public class EvaluateAlarmUseCase {

    private final DomainEventPublisher publisher;   // 端口：事件出口（被驱动）

    public void evaluate(Long deviceId) {
        // ... 规则评估、告警落库
        publisher.publish(new AlarmTriggeredEvent(deviceId, level, Instant.now()));
        // 发完即忘：谁订阅、怎么响应，用例不关心（OCP 响应者无限扩展）
    }
}
```

**一个事件，三个住址**：发布在应用层（用例编排）、定义在领域层（契约模型 `AlarmTriggeredEvent`）、响应在适配器层（各自按职责归位）——12 课"同一技术横跨两侧"在模式上的重演。

### 4.5 应用层模式的红线

| 红线 | 判据 |
|---|---|
| 红线 1：处理器/步骤接口住应用层，不外溢 | `FrameHandler` 出现在 domain 或 infrastructure 包 = 越界 |
| 红线 2：链/编排器不含业务规则 | 管道类里出现"级别裁决" → 下沉领域层 |
| 红线 3：模板方法慎用，运行时替换场景禁用 | 有"动态换实现"需求还用继承 = 自缚手脚 |
| 红线 4：事件契约（领域事件类）住领域层 | 事件字段出现 Kafka 消息格式 = 契约被污染 |

## 5. 适配器层模式——适配器、装饰器、注册表工厂

### 5.1 适配器层的模式准入门槛

适配器层是"技术翻译的家"。准入的模式必须为**技术轴**服务。三主角构成适配器内部三层职责分工：

> **适配器负责"翻得对"，装饰器负责"翻得稳"，注册表负责"翻哪种"。**

### 5.2 适配器模式：本层命名是座金山

适配器层的名字就是"适配器模式"（GoF Adapter）——**这里的"适配器"是字面意义的模式，不是隐喻**。`ModbusDeviceAdapter` 就是原型：SDK 的 `readHoldingRegisters(slaveId, addr, qty)` → 内核契约的 `read(deviceId)`。

```java
public class ModbusDeviceAdapter implements DeviceSnapshotReader {

    private final ModbusClient sdk;              // 被适配的"旧接口"
    private final PointTableStore pointTables;   // 翻译材料：deviceId → 地址

    public DeviceSnapshot read(Long deviceId) {
        PointTable t = pointTables.of(deviceId);
        byte[] raw = sdk.readHoldingRegisters(          // SDK 原生方法
                t.slaveId(), t.startAddr(), t.quantity());
        return t.decode(raw);                           // 原始字节 → 业务快照
    }
}
```

**正确性验证**：换 SDK 只换这个适配器，契约/内核/用例测试全零改动；新协议 = 新增实现 + 组合根注册（OCP）；适配器内允许协议细节（寄存器、地址、点表），因为**它就是协议细节的家**。

### 5.3 装饰器：技术横切，不碰翻译逻辑

```java
public class RetryingSnapshotReader implements DeviceSnapshotReader {   // 实现同一个端口

    private final DeviceSnapshotReader delegate;    // 被装饰的真实适配器
    private final RetryPolicy policy;

    public RetryingSnapshotReader(DeviceSnapshotReader delegate, RetryPolicy policy) {
        this.delegate = delegate; this.policy = policy;
    }

    public DeviceSnapshot read(Long deviceId) {
        int attempts = 0;
        while (true) {
            try {
                return delegate.read(deviceId);
            } catch (ModbusTimeoutException e) {      // 协议异常：只在这里识别
                if (++attempts >= policy.maxAttempts()) throw e;
                sleep(policy.backoff(attempts));
            }
        }
    }
}
```

两条关键纪律：
1. **实现同一个端口**——调用方完全无感；**装饰器 vs 继承：继承是"换一个类"，装饰器是"包一层"**，运行时可组合（重试+熔断+日志层层包，顺序可调）
2. **技术异常识别在装饰器，不在适配器本体**——适配器保持"一次翻译，抛错向上"的纯粹

组合根装配（规则 C）：`new RetryingSnapshotReader(new LoggingSnapshotReader(raw), retryPolicy())`——组合根决定包装顺序。

### 5.4 注册表工厂：`ParserRegistry` 的正名

09 课的 `ParserRegistry` 一直没明确模式身份——本课正名：**工厂模式（Factory）与策略路由的结合体，住适配器层**。为什么不在领域层？坐标系规则 A：**它隔离的是"新型号接入"（技术轴），不是"规则改口"（业务轴）**——寄存器布局是协议知识。

```java
@Component
public class ParserRegistry {
    private final Map<String, ModelParser> parsers;   // 型号 → 解析策略

    public ParserRegistry(List<ModelParser> parserList) {
        this.parsers = parserList.stream()
            .collect(Collectors.toMap(ModelParser::supportedModel, p -> p));
    }

    public ModelParser of(String model) {              // 工厂职责：按型号选解析器
        ModelParser p = parsers.get(model);
        if (p == null) throw new UnsupportedModelException(model);
        return p;
    }
}
```

**"工厂方法"与"注册表工厂"在坐标系上的区别**（3.4 与 5.4 必须分清）：

| | 工厂方法（3.4） | 注册表工厂（5.4） |
|---|---|---|
| 住哪层 | 领域层 | 适配器层 |
| 隔离的变化 | 创建一致性的业务约束 | 技术多实现的选型路由 |
| 创建什么 | 领域聚合（`AlarmRecord`） | 技术策略（`ModelParser`） |
| 判定 | "怎么生"是业务规则 → 领域 | "选哪个实现"是技术路由 → 适配器 |

**同样的"工厂"单词，变化轴不同，住址就不同——这正是坐标系存在的意义。**

### 5.5 适配器层模式的红线

| 红线 | 判据 |
|---|---|
| 红线 1：业务规则不得进入适配器层模式 | 装饰器/适配器/注册表里出现"级别映射"→ 泄漏（病灶 3 重演） |
| 红线 2：装饰器只包技术能力，不改翻译逻辑 | 装饰器里出现业务判断 = 职责错位 |
| 红线 3：技术异常识别在装饰器 | 适配器本体捕获并处理协议异常 = 职责混淆 |
| 红线 4：端口实现可以在适配器层，但端口定义不得 | 端口在 infrastructure 定义 = 12 课 4.3 违规 |

## 6. 组合根模式——为什么工厂不进内核

### 6.1 一个看似合理的"工厂"放错了地方

```java
package com.example.gateway.domain.alarm;   // ← 领域层

// ⚠ 看似无害：工厂方法住领域层
public class AlarmFactory {
    public AlarmSink createSink() {
        KafkaAlarmSink sink = new KafkaAlarmSink();          // ← new 技术实现
        sink.setTopic("iot-alarm");
        sink.setBootstrapServers(env.getProperty("kafka.bootstrap"));   // ← 读配置
        return sink;
    }
}
```

这个工厂**不该进领域层**——它创建的是技术实现（Kafka），读取的是环境配置。它本质是**组装逻辑**，组装逻辑的家是组合根。

### 6.2 "new 是知识，组装是策略"

**罪一：`new` 是知识。** `new KafkaAlarmSink()` 把"告警出口是 Kafka"这个**技术选型知识**写死在领域层。

**罪二：`env.getProperty` 是知识。** 读配置 = 知道 Kafka 地址、topic——**环境知识**住进领域层，领域层无法脱离运行环境独立测试。

**罪三：选择策略被固化。** "加个短信通道、按级别路由"的选型策略本该由组合根自由装配表达，现在被 `createSink()` 焊死成"只造 Kafka"。

> **`new` 是知识，组装是策略。领域层/应用层只声明依赖（接口），组合根负责把实现装配起来。**

三条推论：
1. 任何层出现 `new 技术实现类` + `读环境配置` = 组装逻辑泄漏，应上移组合根
2. 组合根是**全工程唯一允许"new 实现 + 读配置"的地方**
3. 想换出口/换库/换协议：**只改组合根，业务层零改动**（OCP 在装配层面兑现）

### 6.3 组合根就是 Spring 的 @Configuration

```java
@Configuration
public class AlarmCompositionRoot {          // 组合根：gateway-app 模块

    // 1. 实现类 → 端口：new 都发生在这里
    @Bean
    public AlarmSink alarmSink(KafkaProperties props) {
        return new KafkaAlarmSink(props.getBootstrapServers(), "iot-alarm");
    }

    // 2. 装饰器叠加（5.3 的装配顺序）
    @Bean
    public DeviceSnapshotReader snapshotReader(ModbusDeviceAdapter raw) {
        return new RetryingSnapshotReader(new LoggingSnapshotReader(raw), retryPolicy());
    }

    // 3. 注册表收集：Spring 自动注入所有实现
    @Bean
    public ParserRegistry parserRegistry(List<ModelParser> parsers) {
        return new ParserRegistry(parsers);
    }

    // 4. 条件装配：同一端口按环境选实现（本地内存库、现场 MySQL）
    @Bean
    @ConditionalOnProperty(name = "repo.mode", havingValue = "memory")
    public AlarmRecordRepository inMemoryRepo() { return new InMemoryAlarmRecordRepository(); }

    @Bean
    @ConditionalOnProperty(name = "repo.mode", havingValue = "mysql")
    public AlarmRecordRepository myBatisRepo() { return new MyBatisAlarmRecordRepository(); }
}
```

**组合根不是"设计模式"，是"装配边界"**——它是全工程唯一的新知识集中营，业务层永远不认识实现类。

### 6.4 条件装配的用武之地：网关三场景

| 场景 | 装配方式 | 说明 |
|---|---|---|
| 本地开发 vs 现场生产 | `@ConditionalOnProperty` 内存库/MySQL | 本地无 DB 也能起服务 |
| 协议按型号路由 | 注册表收集 `List<ModelParser>` | 09 课 OCP 实现机制 |
| 告警出口按级别 | 组合根决定 `AlarmSink` 装配策略 | 6.2 罪三的正解 |

**一个值得点破的细节**：为什么 `@Autowired List<AlarmSink>` 不算"组合根被绕开"？——`@Autowired` 只是**声明依赖**（我要一组实现），**选哪个、配哪个**仍是组合根的 `@Bean` 决定。**声明依赖在业务层，选择实现在组合根**——这个分工是判断"组合根是否被绕过"的分界线。

### 6.5 组合根模式的红线

| 红线 | 判据 |
|---|---|
| 红线 1：`new` 技术实现 + 读配置只出现在组合根 | 其他层出现 `new Kafka...` 或 `@Value("${kafka...}")` = 泄漏 |
| 红线 2：业务层不 import 实现类 | 用例里 `import KafkaAlarmSink` = 12 课规则 4 违规 |
| 红线 3：条件装配只选实现，不改行为 | 组合根里写业务判断 = 规则泄漏 |
| 红线 4：组合根不参与业务逻辑 | `@Configuration` 类出现规则计算 = 组合根失格 |

## 7. 红线与守卫——过度设计信号与模式层次检验

### 7.1 本段的结构：第 7 段是"刹车片"

第 3–6 段是"油门"（各层模式），本段是"刹车片"：**模式用多了、用早了、用偏了，同样破坏层次分明**。模式不是越多越好，过度设计比欠设计更隐蔽——它顶着"专业"的名义。本段给两套工具：**事前**的过度设计信号、**事后**的层次检验三问。

### 7.2 三个过度设计信号（09 课"第二次变化才抽象"的完整版）

**信号 1：为"想象中的扩展"建接口**

接口实现类数量 == 1？→ 问自己"第二个实现候选是否存在且已可见"。**抽象的价值 = 未来变化的概率 × 未来改动的成本**——概率为零的抽象，成本全落在今天。

**信号 2：模式化的"骨架"在追新**

处理环节 < 3 个且未来无明确增删计划 → 用一个 `for` 循环，别上责任链。**模式的骨架成本必须被真实增长的步骤数摊销**。

**信号 3：策略族的"差异化"只有名字**

策略实现之间只有参数不同、没有算法不同 → 用**数据驱动**（规则表/配置化阈值），别用策略。**策略隔离的是"算法族"，不是"参数集"**——参数用配置，算法才用策略。

三条信号合一：**模式是为"已发生的第二次变化"服务的，不是为"想象中的第 N 次变化"预演的**。

### 7.3 模式层次检验三问（事后守卫）

```
Q1 位置问：这个模式的接口定义在哪个包？
   ├─ 领域层 / 应用层端口区 → 继续 Q2
   └─ infrastructure / adapter 的业务接口 → ❌ 第 1 段反例，上移或重定变化轴

Q2 依赖问：这个模式引用了哪些跨层类型？
   ├─ 只引用本层 + 端口（接口）→ 继续 Q3
   └─ import 了实现类 / 技术类 → ❌ 12 课规则 3

Q3 组装问：谁在 new 这个模式的实现？
   ├─ 组合根（@Configuration）→ ✅ 通过
   └─ 业务代码里 new 实现 → ❌ 组合根被绕过
```

**任何一问不过，先回坐标系重定位，再回代码**——检验的是"位置+依赖+组装"三个维度，不是模式语法本身。

### 7.4 实操演示：三问抓第 1 段反例

| 问 | 第 1 段反例的答案 | 判定 |
|---|---|---|
| Q1 位置问 | `LevelMappingStrategy` 定义在 `infrastructure.strategy` | ❌ 违规 |
| Q2 依赖问 | 用例 `import List<LevelMappingStrategy>`（跨层 + 实现层类型） | ❌ 违规 |
| Q3 组装问 | 用例 `@Autowired List<策略>` 直接持有并遍历 | ❌ 违规 |

**三问全红——即使不看病理切片，三问也能独立抓出问题**。再看正例（3.2 `LevelMapper`）：接口住领域层 ✓、只引用本层类型 ✓、组合根注入 ✓——三问全绿，严格对照。

```
 └───────────────┬─────────────────────┘
                 │ 精装修（架构→模式）
                 ▼
 ┌─────────────────────────────────────┐
 │  13 设计模式与分层安放（精装修）        │
 │  · 安放坐标系：变化轴 × 架构层          │
 │  · 各层模式归位 + 组合根装配            │
 └─────────────────────────────────────┘
```

**五个词记住五课**：尺子 → 分割线 → 结构单元 → 建筑 → 精装修。

### 8.4 回答你最初的问题（贯穿全程的主线）

| 诉求 | 回答 | 所在课 |
|---|---|---|
| 模块怎么划分 | 纵向按业务能力切，边界与变化轴平行；两问法识别能力 | 10 |
| 分包如何健壮 | by-feature + api/internal + package-private + common 四门禁 | 11 |
| 层次分明是什么 | 业务有唯一的家 + 依赖单向可预期 + 变化隔离在所属层（被强制执行） | 12 |
| 引入模式后仍分明 | 模式住进坐标系（变化轴 × 架构层），组装在组合根，三问检验 | 13 |

**一句话总纲**：

> **先找到变化轴（09），沿轴切模块（10），包内摆契约与实现（11），把技术推到外围（12），让模式住进各自的层（13）——层次分明不是结果，是每一层都守住了自己的"家"。**

### 8.5 系列的落地检查清单

| 检查项 | 判据 | 课 |
|---|---|---|
| 新增一个需求，改动落在几个模块/包？ | ≤2，理想是 1 | 10/11 |
| 依赖图有环吗？ | 无环（Enforcer + ArchUnit） | 10 |
| 内核里 grep 得到技术词吗？ | 无（kafka/modbus/mybatis） | 12 |
| 新模式接口定义在哪层？ | 按变化轴归位（三问） | 13 |
| 谁在 new 实现类？ | 只在组合根 | 13 |
| 业务规则变，动哪层？ | 只动领域层 | 12 |
| 技术选型变，动哪层？ | 只动适配器 + 组合根 | 12/13 |

### 8.6 系列收官三句记忆锚点

1. **五课递进**：尺子（09 判断标准）→ 分割线（10 模块）→ 结构单元（11 包）→ 建筑（12 架构）→ 精装修（13 模式）——每一课解决"上一课的落地形式"
2. **坐标系是模式时代的"层次分明"**：变化轴 × 架构层，让模式放哪从争论变成查表；组装永远在组合根
3. **验收总纲**：层次分明的最终检验——业务变只动内核、技术变只换适配器、加需求只改一个家
