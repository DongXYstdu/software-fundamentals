## HTTP/1.1 协议的性能问题

我们得先要了解下 HTTP/1.1 协议存在的性能问题，因?HTTP/2 协议就是把这些性能问题逐个攻破了?

现在的站点相比以前变化太多了，比如：

- *消息的大小变大了*，从?KB 大小的消息，到几 MB 大小的消息；
- *页面资源变多?，从每个页面不到 10 个的资源，到每页?100 多个资源?
- *内容形式变多样了*，从单纯到文本内容，到图片、视频、音频等内容?
- *实时性要求变高了*，对页面的实时性要求的应用越来越多?

这些变化带来的最大性能问题就是 **HTTP/1.1 的高延迟**，延迟高必然影响的就是用户体验。主要原因如下几个：

- *延迟难以下降*，虽然现在网络的「带宽」相比以前变多了，但是延迟降到一定幅度后，就很难再下降了，说白了就是到达了延迟的下限?
- *并发连接有限*，谷歌浏览器最大并发连接数?6 个，而且每一个连接都要经?TCP ?TLS 握手耗时，以?TCP 慢启动过程给流量带来的影响；
- *队头阻塞问题*，同一连接只能在完成一?HTTP 事务（请求和响应）后，才能处理下一个事务；
- *HTTP 头部巨大且重?，由?HTTP 协议是无状态的，每一个请求都得携?HTTP 头部，特别是对于有携?Cookie 的头部，?Cookie 的大小通常很大?
- *不支持服务器推送消?，因此当客户端需要获取通知时，只能通过定时器不断地拉取消息，这无疑浪费大量了带宽和服务器资源?

为了解决 HTTP/1.1 性能问题，具体的优化手段你可以看这篇文章「HTTP/1.1 如何优化？」，这里我举例几个常见的优化手段?

- 将多张小图合并成一张大图供浏览?JavaScript 来切割使用，这样可以将多个请求合并成一个请求，但是带来了新的问题，当某张小图片更新了，那么需要重新请求大图片，浪费了大量的网络带宽；
- 将图片的二进制数据通过 Base64 编码后，把编码数据嵌入到 HTML ?CSS 文件中，以此来减少网络请求次数；
- 将多个体积较小的 JavaScript 文件使用 Webpack 等工具打包成一个体积更大的 JavaScript 文件，以一个请求替代了很多个请求，但是带来的问题，当某?js 文件变化了，需要重新请求同一个包里的所?js 文件?
- 将同一个页面的资源分散到不同域名，提升并发连接上限，因为浏览器通常对同一域名?HTTP 连接最大只能是 6 个；

尽管?HTTP/1.1 协议的优化手段如此之多，但是效果还是不尽人意，因为这些手段都是对 HTTP/1.1 协议?外部"做优化，**而一些关键的地方是没办法优化的，比如请求-响应模型、头部巨大且重复、并发连接耗时、服务器不能主动推送等，要改变这些必须重新设计 HTTP 协议，于?HTTP/2 就出来了?*

## 兼容 HTTP/1.1

HTTP/2 出来的目的是为了改善 HTTP 的性能。协议升级有一个很重要的地方，就是?*兼容**老版本的协议，否则新协议推广起来就相当困难，所?HTTP/2 做到了兼?HTTP/1.1?

那么，HTTP/2 是怎么做的呢？

第一点，HTTP/2 没有?URI 里引入新的协议名，仍然用「http://」表示明文协议，用「https://」表示加密协议，于是只需要浏览器和服务器在背后自动升级协议，这样可以让用户意识不到协议的升级，很好的实现了协议的平滑升级?

第二点，只在应用层做了改变，还是基于 TCP 协议传输，应用层方面为了保持功能上的兼容，HTTP/2 ?HTTP 分解成了「语义」和「语法」两个部分，「语义」层不做改动，与 HTTP/1.1 完全一致，比如请求方法、状态码、头字段等规则保留不变?

但是，HTTP/2 在「语法」层面做了很多改造，基本改变?HTTP 报文的传输格式?

## 头部压缩

HTTP 协议的报文是由「Header + Body」构成的，对?Body 部分，HTTP/1.1 协议可以使用头字段「Content-Encoding」指?Body 的压缩方式，比如?gzip 压缩，这样可以节约带宽，但报文中的另外一部分 Header，是没有针对它的优化手段?

HTTP/1.1 报文?Header 部分存在的问题：

- 含很多固定的字段，比?Cookie、User Agent、Accept 等，这些字段加起来也高达几百字节甚至上千字节，所以有必要**压缩**?
- 大量的请求和响应的报文里有很多字段值都是重复的，这样会使得大量带宽被这些冗余的数据占用了，所以有必须?*避免重复?*?
- 字段?ASCII 编码的，虽然易于人类观察，但效率低，所以有必要改成**二进制编?*?

HTTP/2 ?Header 部分做了大改造，把以上的问题都解决了?

HTTP/2 没使用常见的 gzip 压缩方式来压缩头部，而是开发了 **HPACK** 算法，HPACK 算法主要包含三个组成部分?

- 静态字典；
- 动态字典；
- Huffman 编码（压缩算法）?

客户端和服务器两端都会建立和维护?*字典**」，用长度较小的索引号表示重复的字符串，再用 Huffman 编码压缩数据?*可达?50%~90% 的高压缩?*?

### 静态表编码

HTTP/2 为高频出现在头部的字符串和字段建立了一?*静态表**，它是写入到 HTTP/2 框架里的，不会变化的，静态表里共?`61` 组，如下图：

你可能注意到，表中有?Index 没有对应?Header Value，这是因为这?Value 并不是固定的而是变化的，这些 Value 都会经过 Huffman 编码后，才会发送出去?

这么说有点抽象，我们来看个具体的例子，下面这?`server` 头部字段，在 HTTP/1.1 的形式如下：


### 动态表编码

静态表只包含了 61 种高频出现在头部的字符串，不在静态表范围内的头部字符串就要自行构?*动态表**，它?Index ?`62` 起步，会在编码解码的时候随时更新?

比如，第一次发送时头部中的「`User-Agent`」字段数据有上百个字节，经过 Huffman 编码发送出去后，客户端和服务器双方都会更新自己的动态表，添加一个新?Index ?62?*那么在下一次发送的时候，就不用重复发这个字段的数据了，只用发 1 个字节的 Index 号就好了，因为双方都可以根据自己的动态表获取到字段的数据**?

所以，使得动态表生效有一个前提：**必须同一个连接上，重复传输完全相同的 HTTP 头部**。如果消息字段在 1 个连接上只发送了 1 次，或者重复传输时，字段总是略有变化，动态表就无法被充分利用了?

因此，随着在同一 HTTP/2 连接上发送的报文越来越多，客户端和服务器双方的「字典」积累的越来越多，理论上最终每个头部字段都会变?1 个字节的 Index，这样便避免了大量的冗余数据的传输，大大节约了带宽?

理想很美好，现实很骨感。动态表越大，占用的内存也就越大，如果占用了太多内存，是会影响服务器性能的，因此 Web 服务器都会提供类?`http2_max_requests` 的配置，用于限制一个连接上能够传输的请求数量，避免动态表无限增大，请求数量到达上限后，就会关?HTTP/2 连接来释放内存?

综上，HTTP/2 头部的编码通过「静态表、动态表、Huffman 编码」共同完成的?

## 并发传输

知道?HTTP/2 的帧结构后，我们再来看看它是如何实现**并发传输**的?

## 服务器主动推送资?

HTTP/2 还在一定程度上改善了传统的「请?- 应答」工作模式，服务不再是被动地响应，也可以**主动**向客户端发送消息?

## 总结

HTTP/2 协议相比 HTTP/1.1 改进了很多，主要通过以下技术来提升性能?

- **头部压缩**：通过 HPACK 算法（静态表、动态表、Huffman 编码）压缩头部，减少冗余数据传输?
- **二进制帧**：将文本格式改为二进制格式，提高传输效率和解析效率；
- **并发传输**：通过 Stream 实现多路复用，解决了 HTTP 层面的队头阻塞问题；
- **服务器推?*：服务器可以主动推送资源，减少客户端的等待时间?

?HTTP/2 仍然存在 TCP 层面的队头阻塞问题，这个问题将在 HTTP/3 中解决?
