## 为什么需要哈希表？

在数据处理中，**查找**是最常见的操作之一。让我们对比一下各种数据结构的查找效率：

| 数据结构 | 平均查找 | 最坏查找 | 适用场景 |
|---------|---------|---------|---------|
| 无序数组 | $O(n)$ | $O(n)$ | 数据量小 |
| 有序数组（二分） | $O(\log n)$ | $O(\log n)$ | 静态数据，插入慢 |
| 链表 | $O(n)$ | $O(n)$ | - |
| 平衡二叉树 | $O(\log n)$ | $O(\log n)$ | 动态数据 |
| **哈希表** | **$O(1)$** | $O(n)$ | **键值对查找** |

哈希表（Hash Table，也叫散列表）通过**键 → 数组索引**的映射，实现了近乎"一步到位"的查找。它是现代编程语言中使用最广泛的数据结构之一（Python 的 `dict`、Java 的 `HashMap`、Go 的 `map`…）。

---

## 核心思想：散列函数

哈希表的核心是一个**散列函数（Hash Function）**，它把任意长度的输入（键）映射成一个固定长度的整数（数组索引）。

```
  key = "dongxiangyang"
         │
         ▼  hash(key)
         │
    index = 42  ← 数组下标
         │
         ▼
  ┌──┬──┬──┬──┬──┬──┬──┐
  │  │  │  │  │  │●│  │  │  ← 存放在 table[42]
  └──┴──┴──┴──┴──┴──┴──┴──┘
    0  1  2  3  4  42 ... N-1
```

一个好的散列函数应该满足：

1. **一致性**：相同的 key 永远得到相同的 hash 值
2. **高效性**：计算速度快
3. **均匀性**：哈希值在输出空间中均匀分布
4. **抗冲突**：不同的 key 尽量得到不同的 hash 值

### 常见的散列函数

| 方法 | 原理 | 适用场景 |
|------|------|---------|
| **除留余数法** | `hash(key) = key % p` (p 通常取质数) | 简单，整数 key |
| **乘法哈希** | `hash(key) = floor((key × A mod 1) × M)` | 分布更均匀 |
| **DJB2** | `hash = hash × 33 + char` | 字符串，速度快 |
| **MurmurHash** | 复杂的位运算混合 | 通用，速度快分布好 |
| **SHA-256** | 密码学哈希 | 需要防篡改时 |

以 **DJB2** 为例（处理字符串）：

```c
unsigned long hash(unsigned char *str) {
    unsigned long hash = 5381;  // 魔术初始值
    int c;
    while ((c = *str++))
        hash = ((hash << 5) + hash) + c;  // hash * 33 + c
    return hash;
}
```

为什么是 `33` 和 `5381`？这是 Dan Bernstein 经过大量测试后选出的"魔术数"，实际效果很好。

## 不可避免的问题：哈希冲突

无论散列函数设计得多好，**冲突（Collision）** 都是不可避免的——把无限的 key 空间映射到有限的数组索引，必然有两个不同的 key 落到同一个位置。

```
"apple"   ──hash──►  index = 7
"orange"  ──hash──►  index = 7   ←  冲突！
```

解决冲突主要有两类方法：**链地址法** 和 **开放寻址法**。

---

## 方案一：链地址法（Chaining）

数组的每个位置挂一个链表（或红黑树），冲突的元素放进同一个链表。

```mermaid
graph TD
    subgraph 哈希表
        I0[0] --> L0[null]
        I1[1] --> L1["banana" → null]
        I2[2] --> L2["apple" → "orange" → null]
        I3[3] --> L3[null]
        I4[4] --> L4["dog" → null]
    end
    L2 -- "hash(apple)=2" --- A["apple"]
    L2 -- "hash(orange)=2" --- B["orange"]
```

### 查找过程

1. 计算 `hash(key)` 得到索引 `i`
2. 遍历 `table[i]` 处的链表
3. 逐个比较 key，找到则返回，否则返回空

### 时间复杂度分析

- **最好情况**（无冲突）：$O(1)$
- **最坏情况**（全部冲突）：$O(n)$，退化成链表
- **平均情况**：取决于**装载因子（Load Factor）**
  - 装载因子 $\alpha = \frac{n}{m}$（n 个元素，m 个槽位）
  - 平均查找长度 ≈ $1 + \alpha$（一次哈希 + 链表遍历 $\alpha$ 个节点）

> 当 $\alpha > 0.75$ 时，链地址法的性能明显下降，需要**扩容（Rehashing）**——把数组容量翻倍，重新哈希所有元素。
{: .prompt-tip }

**Java `HashMap` 的实现**就是链地址法 + 链表过长时转红黑树（链表长度 > 8 且容量 ≥ 64 时），最坏情况从 $O(n)$ 降到 $O(\log n)$。

## 方案二：开放寻址法（Open Addressing）

冲突发生时，**在数组内部寻找下一个空槽**。不需要额外的链表结构，所有元素都存在数组里。

### 线性探测（Linear Probing）

最简单的开放寻址：冲突时依次探查下一个位置。

```
探查序列: h(key), h(key)+1, h(key)+2, ... (mod m)

插入 "apple"  hash=2 → 位置 2 空 → 放入 [2]
插入 "orange" hash=2 → 位置 2 占用 → 尝试 [3] → 空 → 放入 [3]
插入 "grape"  hash=2 → 位置 2 占用 → [3] 占用 → [4] 空 → 放入 [4]

  ┌──┬──┬──┬─────┬──────┬──────┬──┐
  │  │  │apple│orange│grape│  │  │...
  └──┴──┴──┴─────┴──────┴──────┴──┘
    0  1  2    3      4      5  6
```

**线性探测的问题**：容易产生**一次群集（Primary Clustering）**——冲突元素聚集成连续的块，越往后查找越慢。

### 二次探测（Quadratic Probing）

探查步长随次数增长：`h(key), h(key)+1², h(key)+2², h(key)+3², ...`

缓解了一次群集，但会产生**二次群集**（相同 hash 值的元素探查序列相同）。

### 双重散列（Double Hashing）

使用两个不同的散列函数：`h1(key), h1(key)+h2(key), h1(key)+2×h2(key), ...`

探查步长由第二个散列函数决定，分布更均匀，是理论上最好的开放寻址方案。

> **Python `dict` 采用伪随机探测**，是开放寻址法的一种变体。
{: .prompt-info }

### 删除的困难

开放寻址法的**删除操作很麻烦**：如果直接把槽位置空，后续查找可能"断链"——后面的元素虽然哈希值也对应前面的位置，但因为冲突被放在了后面，删除中间元素后它们就再也找不到了。

解决方案：使用**墓碑标记（Tombstone）**——删除时不置空，而是标记为"已删除"。查找时跳过墓碑，插入时可重用墓碑位置。

## 链地址法 vs 开放寻址法

| 维度 | 链地址法 | 开放寻址法 |
|------|---------|-----------|
| **空间** | 需要额外指针/节点 | 数组紧凑，CPU 缓存友好 |
| **删除** | 简单，直接删除节点 | 困难，需墓碑标记 |
| **装载因子** | 可 > 1（链表可无限延长） | 必须 < 1（数组填满就无法插入） |
| **最坏性能** | 链表过长时 $O(n)$ | 探测失败时 $O(m)$ |
| **现代实现** | Java HashMap, C++ `std::unordered_map` | Python `dict`, Go `map` (1.21+ 改用混合) |

## 扩容与 Rehashing

当装载因子超过阈值（通常 0.75），哈希表需要**扩容**：

1. 申请一个**更大的数组**（通常 2 倍）
2. 遍历旧数组的每个元素，**重新计算哈希值**后插入新数组
3. 释放旧数组

```mermaid
flowchart LR
    A[旧表 size=4<br/>α=0.75] -->|扩容| B[新表 size=8]
    A --> C["apple → 2"]
    A --> D["orange → 2(链表)"]
    C --> E[重新哈希<br/>apple → 5]
    D --> F[重新哈希<br/>orange → 1]
    E --> G[新表[5] = apple]
    F --> H[新表[1] = orange]
```

### 渐进式 Rehashing

一次性把所有元素重新哈希在元素很多时会造成**长时间卡顿**。Redis 的 `dict` 采用**渐进式 rehash**：

- 同时维护新旧两个哈希表
- 每次 CRUD 操作时，顺便搬运几个元素
- 后台也会主动搬运
- 直到旧表为空，切换到新表

这样把一次大开销**摊还**到多次操作中，避免了单次操作的延迟尖刺。

## 一个简化的 C++ 实现

下面是一个基于链地址法的简化哈希表，帮助理解核心逻辑：

```cpp
template <typename K, typename V>
class HashTable {
private:
    vector<list<pair<K, V>>> table;  // 链表数组
    int size;                        // 元素数量
    int capacity;                    // 桶数量
    const double MAX_LOAD_FACTOR = 0.75;

    int hash(const K& key) const {
        return std::hash<K>{}(key) % capacity;
    }

    void rehash() {  // 扩容
        int new_capacity = capacity * 2;
        vector<list<pair<K, V>>> new_table(new_capacity);
        for (auto& bucket : table)
            for (auto& kv : bucket) {
                int idx = std::hash<K>{}(kv.first) % new_capacity;
                new_table[idx].push_back(kv);
            }
        table = move(new_table);
        capacity = new_capacity;
    }

public:
    HashTable(int cap = 16) : size(0), capacity(cap), table(cap) {}

    V& operator[](const K& key) {
        int idx = hash(key);
        for (auto& kv : table[idx])
            if (kv.first == key) return kv.second;
        // 未找到，插入新元素
        table[idx].emplace_back(key, V());
        if (++size > capacity * MAX_LOAD_FACTOR) rehash();
        return table[idx].back().second;
    }

    bool get(const K& key, V& val) {
        int idx = hash(key);
        for (auto& kv : table[idx])
            if (kv.first == key) { val = kv.second; return true; }
        return false;
    }
};
```

## 常见面试问题

**Q1：为什么哈希表的数组大小通常取质数？**

> 使用质数可以让除留余数法得到更均匀的分布。但现代实现（如 Java HashMap）不用质数，而是用 2 的幂配合位运算（`hash & (length - 1)`），速度更快但需要更好的哈希函数。

**Q2：什么是 HashMap 的 Fail-Fast？**

> Java HashMap 在迭代过程中如果检测到结构被修改（增删元素），会立即抛出 `ConcurrentModificationException`，防止迭代器读到不一致的状态。通过 `modCount` 实现。

**Q3：为什么 Python dict 不用链表？**

> Python 选择开放寻址法的原因：1) 数组更紧凑，对 CPU 缓存更友好；2) Python 对象本身已含指针间接，再加一层链表指针开销更大；3) 现代 CPU 的分支预测让线性探测的实际性能非常好。

**Q4：如何设计一个良好的哈希函数？**

> 关键是扩散（diffusion）和混淆（confusion）——输入的每一位都应该影响输出的每一位；key 中的细微变化会导致完全不同的输出。MurmurHash、XXHash、SipHash 都是现代工程中常用的高性能哈希。

## 小结

| 概念 | 要点 |
|------|------|
| **散列函数** | 把 key 映射到数组索引，要求均匀分布 |
| **哈希冲突** | 不可避免，通过链地址法或开放寻址法解决 |
| **装载因子** | $\alpha = n/m$，超过阈值需要扩容 |
| **扩容（Rehashing）** | 数组翻倍 + 重新哈希；渐进式避免卡顿 |
| **实际实现** | Java HashMap（链地址 + 红黑树）；Python dict（开放寻址） |

理解哈希表的原理不仅有助于用好它，更能在遇到性能问题时精准定位——比如"为什么这个 HashMap 的 get 突然变慢了？"可能就是装载因子过高导致链表过长，或者哈希函数不够均匀造成的。
