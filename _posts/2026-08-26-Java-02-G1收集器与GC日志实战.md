# G1 收集器原理与 GC 日志实战
## 1. G1 Region 模型

![02-01 G1 Region 模型]({{ site.baseurl }}/assets/svg/02-01-G1Region模型.svg)

- 堆被切分为约 **2048 个等大 Region**（1~32MB，2 的幂）
- "分代"降级为 Region 的**临时标签**：Eden / Survivor / Old 动态变化，回收后变空闲可复用
- 回收单位是 Region 而非整代：每次挑"垃圾占比最高、回收最划算"的格子做复制式回收
- **Humongous**：单个对象 ≥ 1/2 Region，跳过分代直接占老年代连续 Region，不参与正常回收节奏

```
┌────┬────┬────┬────┬────┬────┬────┬────┐
│Eden│Eden│ S0 │Old │Old │Old │Old │Old │   每格 = 1 Region
│    │    │    │    │    │    │    │    │   (1~32MB · 2 的幂)
├────┼────┼────┼────┼────┼────┼────┼────┤
│Eden│Eden│ S1 │Old │Old │Old │Old │Old │   ~2048 个格子
├────┼────┼────┼────┼────┼────┼────┼────┤       │
│Eden│Eden│Old │Old │Old │Old │Old │Old │       │ 角色 = 临时标签
├────┼────┼────┼────┼────┼────┼────┼────┤       │ 回收后变空闲
│Old │Old │Old │Old │Old │Old │Old │Old │       ▼
├────┼────┼────┼────┼────┼────┼────┼────┤
│ H  │ H  │ H  │空  │空  │空  │空  │空  │   H = Humongous 连续格
└────┴────┴────┴────┴────┴────┴────┴────┘   (大对象直入老年代)
```

**参数纪律**：G1 下**不要**手动设 `-Xmn` / `SurvivorRatio`——G1 按停顿目标动态调整新生代格子数，手动设等于抢方向盘。

## 2. 并发标记四阶段

![02-02 G1 并发标记四阶段]({{ site.baseurl }}/assets/svg/02-02-G1并发标记四阶段.svg)

```
1 初始标记 ──> 2 并发标记 ──> 3 最终标记 ──> 4 筛选回收
 STW·极短      不 STW·最久     STW·极短       STW·主要停顿
 标GC Roots    沿引用图遍历     清空SATB缓冲    按收益选Region
 直达老对象    SATB记录变化    处理并发残余    复制存活·整理
```

- **Young GC** = 只做阶段 4 的新生代部分（高频、几 ms）
- **Mixed GC** = 老年代占用到 **IHOP 阈值（默认 45% 堆）** 启动并发标记周期，之后连做几次 Mixed GC 把老年代高收益 Region 一起清
- **SATB**（Snapshot-At-The-Beginning）：并发标记开始拍快照；期间旧引用被删仍当活——宁可多标不可漏标，漏标会回收活对象
- 停顿预算 `MaxGCPauseMillis` 由历史停顿数据预测，G1 据此决定每次回收多少 Region

### G1 三大退化坑

| 现象 | 根因 |
|---|---|
| 停顿目标设太小反而更卡 | 预算小 → 每次回收少量 Region → 赶不上分配 → 堆渐满 → 退化 Full GC（单线程串行，秒级） |
| `to-space exhausted` | 复制回收需要目的地空格子；老年代预留不足无处可拷 |
| `Pause Full (G1 Compaction Pause)` | 并发标记跟不上分配洪峰，放弃并发模型退回串行整理 |

## 3. GC 日志解剖

![02-03 GC 日志解剖]({{ site.baseurl }}/assets/svg/02-03-GC日志解剖.svg)

```
[gc] GC(4821) Pause Young (Normal) (G1 Evacuation Pause) 987M->89M(1024M) 12.345ms
 └标签┘└─序号─┘└─────停顿类型─────┘ └────触发原因────┘ └──堆占用变化──┘ └─停顿─┘
```

| 字段 | 含义 | 看点 |
|---|---|---|
| `[gc]` | `-Xlog:gc*` 输出类别 | 日志体系入口 |
| `GC(4821)` | JVM 内 GC 序号 | 增速 = GC 频率 = 分配速率 |
| `Pause Young (Normal)` | 停顿类型 | Young / Mixed / Full；Normal / Prepare Mixed / Initial Mark |
| `(G1 Evacuation Pause)` | 触发原因 | Evacuation = 复制存活对象 |
| `987M->89M(1024M)` | 回收前->后（总堆） | 差值 = 释放量；后值不降 = 泄漏嫌疑 |
| `12.345ms` | STW 停顿 | 对 MaxGCPauseMillis 的答卷 |

### 读日志心法
1. 先扫 `Pause Full` / `to-space exhausted` —— 有没有事故
2. 再看 Young GC `前->后` 差值 —— 回收效果
3. 再看停顿 ms 与频率 —— 健康度
4. 拿不准拖进 GCeasy 自动出报告

### 三个异常信号

```
Pause Full (G1 Compaction Pause)   → 退化串行整理：并发标记跟不上分配
to-space exhausted                  → 复制目标不足：加大堆或调低停顿目标
Humongous Allocation 频繁           → 大对象多：控批量大小或增大 G1HeapRegionSize
```

## 4. Metaspace 泄漏——Spring Boot 专属陷阱

- Metaspace 存**类元数据**（本地内存，JDK 8 起取代永久代）
- 泄漏特征：`jstat -gcmetacapacity` 已用值持续涨、Full GC 后不回落 → 最终 `OutOfMemoryError: Metaspace`

| 触发源 | 机制 | 关联 |
|---|---|---|
| CGLIB 动态代理 | Spring AOP 每个增强类生成一个代理类 | @Transactional、租户/日志切面正常只生成一次；**运行时反复 new 代理才是问题** |
| 反射 inflation | 反射 ≥15 次后生成字节码加速类 | 框架内部行为，正常 |
| 脚本/规则引擎 | Groovy、Aviator 每次编译产生新类 | 计算点表达式引擎留意表达式无限增长 |
| Arthas 增强 | watch/trace 每次生成内联类 | **排查完关掉增强会话，否则类累积** |

防线：
- `-XX:MaxMetaspaceSize` 必设——宁可它先报错，别吃光机器内存
- 排查：`jcmd <pid> GC.class_stats -all` / Arthas `sc -d` 看类加载器持有量

## 5. 生产场景对照

| 场景 | 对应知识点 |
|---|---|
| yudao 重度 AOP（事务/租户/日志切面） | CGLIB 代理类常驻 Metaspace，MaxMetaspaceSize 必设 |
| TDengine 批量写入大 SQL | 超半 Region 即 Humongous 直入老年代，批量大小要控 |
| 大屏时序接口大 JSON 响应 | 同上，响应体字符串是大对象 |
| 网关消息队列溢出突发分配 | 分配速率飙升 → 并发标记跟不上 → 退化 Full GC |
