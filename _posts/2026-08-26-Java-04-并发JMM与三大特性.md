# 并发编程（一）：JMM 与三大特性
## 1. JMM 内存模型抽象

![04-01 JMM 内存模型抽象]({{ site.baseurl }}/assets/svg/04-01-JMM内存模型抽象.svg)

JMM（Java Memory Model）在硬件内存模型之上定义统一语义，让"一次编写处处运行"成立。

```
┌─────────────── 主内存 Main Memory ───────────────┐
│  共享变量：堆中实例字段 · 静态字段                  │
└──┬───────────────┬────────────────┬──────────┘
   │ read·load     │ store·write     │ read·load   store·write
   ▼               ▲                 ▼             ▲
┌──────────────────────┐         ┌──────────────────────┐
│ 线程 A 工作内存       │         │ 线程 B 工作内存       │
│ 副本在寄存器/L1 cache │         │ 副本在寄存器/L1 cache │
│ A 改了变量未必立刻同步 │         │ B 未必看到 A 的修改    │
└──────────────────────┘         └──────────────────────┘
        │                                  │
   use / assign 操作副本            use / assign 操作副本
```

**JMM 全部问题之源**：工作内存副本何时与主内存同步。不加同步原语，写线程的修改可能长时间对读线程不可见。

## 2. 三大特性

- **原子性**：操作不可分割。基本类型读写基本原子；但 `i++` 是"读-改-写"三步，不原子
- **可见性**：一个线程的修改何时对另一线程可见。普通变量依赖何时写回主内存
- **有序性**：编译器/CPU 会重排序优化（as-if-serial 对单线程无害，多线程有害）

## 3. 三大特性 × 三大工具矩阵

![04-02 三大特性与三大工具矩阵]({{ site.baseurl }}/assets/svg/04-02-三大特性与三大工具矩阵.svg)

| 特性 | synchronized | volatile | final |
|---|---|---|---|
| 原子性 | ✓ | ✗（i++ 救不了） | — |
| 可见性 | ✓ | ✓ | ✓（构造期） |
| 有序性 | ✓ | ✓（禁重排） | ✓ |

- **synchronized 全包**：原子+可见+有序，代价是阻塞
- **volatile 取一半**：可见+有序，不阻塞；但**不保证复合操作原子性**
- **final 仅构造期安全发布**：构造完 final 字段，构造结束后别的线程读到的一定完整——不可变对象天然线程安全的根

### 三个最常见认知错位

1. `i++` 不原子——三步之间可被插队，volatile 也救不了，统计必须用 `AtomicInteger`（CAS）或 synchronized
2. volatile 不轻量但够用——状态开关、轮询配置项（单读单写）合适；带条件判断的复合操作别指望它
3. final 是"构造期安全发布"——不可变对象天然线程安全

## 4. 双重检查单例：为什么必须 volatile

![04-03 双重检查单例与 volatile]({{ site.baseurl }}/assets/svg/04-03-双重检查单例与volatile.svg)

```java
public static Singleton getInstance() {
    if (instance == null) {              // 第一次检查（无锁）
        synchronized (Singleton.class) {
            if (instance == null) {      // 第二次检查
                instance = new Singleton();  // ⚠ 雷在这里
            }
        }
    }
    return instance;
}
```

`new Singleton()` 实际三步：
1. 分配内存（malloc）
2. 调构造函数初始化对象
3. 把引用赋给 instance（store）

**CPU/编译器允许重排序为 1 → 3 → 2**：此时 instance 已非空但对象未初始化。线程 B 第一次检查看到 instance≠null，直接返回 → 拿到半初始化对象 → 脏值 / NPE。

**解药**：`private static volatile Singleton instance;`
- 禁止 1 → 3 → 2 重排序（store 前对象必须已初始化）
- 保证可见性（B 立刻看到完整对象）
- JDK 5+ volatile 才有此语义，故 JDK 5 前双重检查根本不安全

**一句话**：volatile 的真正杀手锏不是"保证可见"，是禁止 new 的重排序。

## 5. 生产场景对照

| 场景 | JMM 视角 |
|---|---|
| 网关轮询线程写点位值、业务线程读 | 共享变量可见性——不加同步原语，读线程可能长时间看不到写 |
| 空压机多步控制序列状态字段 | 有序性——状态标志位加 volatile 防重排序错乱 |
| Modbus FIFO / 计数器 | 用 `LinkedBlockingQueue` / `AtomicInteger`（内部 volatile+AQS），别手搓 |
| 设备最新值 Redis 缓存 | ⚠ 跨进程一致性，**不是 JMM 范畴**，要用缓存更新策略/TTL |
