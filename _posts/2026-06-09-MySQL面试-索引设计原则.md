，更想考察你是否具备在生产环境中设计合理索引的能力，能否平衡查询性能与写入成本。</p> </li> <li> <p><strong>原理理解</strong> ：是否理解 B+ 树结构、最左前缀原则、索引下推等底层原理，而非只会死记硬背几条规则。</p> </li> <li> <p><strong>权衡意识</strong> ：索引不是越多越好，考察你是否懂得在查询性能、存储空间、写入性能之间做取舍。</p> </li> </ol> <H2>核心答案</H2> <p>设计索引应遵循以下 <strong>7 大核心原则</strong> ：</p> <table> <thead> <tr> <th>原则</th> <th>核心要点</th> <th>关键词</th> </tr> </thead> <tbody> <tr> <td>选择合适的列</td> <td>WHERE、JOIN、ORDER BY、GROUP BY 列优先</td> <td>高频查询列</td> </tr> <tr> <td>区分度高优先</td> <td>选择性 = 唯一值/总行数，越高越好</td> <td>基数大、离散度高</td> </tr> <tr> <td>最左前缀原则</td> <td>联合索引按顺序匹配，从左到右连续使用</td> <td>范围查询断后</td> </tr> <tr> <td>覆盖索引</td> <td>索引包含查询所需全部字段，避免回表</td> <td><code>SELECT</code> 列也在索引中</td> </tr> <tr> <td>控制索引数量</td> <td>单表索引不超过 5 个，单个索引字段不超过 5 个</td> <td>写入成本、空间占用</td> </tr> <tr> <td>前缀索引</td> <td>长字符串只索引前 N 个字符，节省空间</td> <td>牺牲部分选择性</td> </tr> <tr> <td>索引下推</td> <td>MySQL 5.6+ 特性，在索引层过滤减少回表</td> <td><code>Using index condition</code></td> </tr> </tbody> </table> <p><strong>一句话总结</strong> ：索引设计要 "选对列、区分度高、遵循最左前缀、善用覆盖索引、控制数量"。</p> <H2>深度解析</H2> <H3>一、选择合适的列建立索引</H3>   <p>上图总结了适合与不适合建立索引的列。具体说明如下：</p> <p><strong>✅ 适合建索引的场景</strong> ：</p> <ul> <li> <p><strong>WHERE 条件列</strong> ：查询条件中频繁出现的列，能大幅减少扫描行数。</p> </li> <li> <p><strong>JOIN 关联列</strong> ：外键关联列，能加速多表关联查询。</p> </li> <li> <p><strong>ORDER BY / GROUP BY 列</strong> ：排序和分组操作非常消耗性能，索引可以利用 B+ 树的有序性直接获取结果。</p> </li> <li> <p><strong>高基数列</strong> ：唯一值越多，索引的过滤效果越好。</p> </li> </ul> <p><strong>❌ 不适合建索引的场景</strong> ：</p> <ul> <li> <p><strong>区分度低的列</strong> ：如性别（只有 "男/女"）、状态（只有 "启用/禁用"），索引过滤效果差，优化器可能直接选择全表扫描。</p> </li> <li> <p><strong>频繁更新的列</strong> ：每次更新都会导致索引重建，增加写入成本。</p> </li> <li> <p><strong>小表</strong> ：数据量小于 1000 行时，全表扫描可能比走索引更快。</p> </li> </ul> <H3>二、区分度（选择性）原则</H3> <p><strong>区分度 = 唯一值数量 / 总行数</strong> ，值越接近 1 越好。</p> <pre><code class="language-sql" data-lang="sql">-- 查看列的区分度
SELECT
    COUNT(DISTINCT user_id) / COUNT(*) AS user_id_selectivity,
    COUNT(DISTINCT status) / COUNT(*) AS status_selectivity
FROM orders;

-- 结果示例：
-- user_id_selectivity: 0.85  ✅ 区分度高，适合建索引
-- status_selectivity: 0.01   ❌ 区分度低，不适合单独建索引</code></pre> <p><strong>联合索引的列顺序</strong> ：区分度高的列放前面。</p> <pre><code class="language-sql" data-lang="sql">-- 假设 status 只有 3 个值，user_id 有 10 万个值
-- ❌ 错误：区分度低的列在前
CREATE INDEX idx_wrong ON orders(status, user_id);

-- ✅ 正确：区分度高的列在前
CREATE INDEX idx_right ON orders(user_id, status);</code></pre> <H3>三、最左前缀原则</H3> <p>联合索引按照定义顺序构建 B+ 树，查询时必须从最左列开始连续匹配。</p>   <p>上图展示了最左前缀原则的应用场景。关键点说明：</p> <ul> <li> <p><strong>从左到右连续匹配</strong> ：必须从索引的第一列开始，中间不能跳过任何一列。</p> </li> <li> <p><strong>范围查询会"断后"</strong> ：一旦出现范围查询（ <code>&gt;</code> 、 <code>&lt;</code> 、 <code>BETWEEN</code> 、 <code>LIKE</code> 前缀模糊），该列之后的索引列无法被使用。</p> </li> <li> <p><strong>优化建议</strong> ：把范围查询列放在联合索引的最后。</p> </li> </ul> <pre><code class="language-sql" data-lang="sql">-- 场景：经常查询某用户的已支付订单
-- ✅ 推荐：等值条件在前，范围条件在后
CREATE INDEX idx_user_status_time ON orders(user_id, status, create_time);

-- 查询能完整利用索引
SELECT * FROM orders
WHERE user_id = 100 AND status = 'PAID' AND create_time &gt; '2024-01-01';</code></pre> <H3>四、覆盖索引</H3> <p>如果索引包含了查询所需的所有字段，MySQL 可以直接从索引中获取数据， <strong>无需回表</strong> 查询聚簇索引。</p> <pre><code class="language-sql" data-lang="sql">-- 假设有索引：INDEX(user_id, status)

-- ❌ 需要回表：SELECT 中有索引不包含的字段
SELECT user_id, status, amount FROM orders WHERE user_id = 100;

-- ✅ 覆盖索引：SELECT 字段都在索引中
SELECT user_id, status FROM orders WHERE user_id = 100;

-- ✅ 更好的方案：创建包含 amount 的联合索引
CREATE INDEX idx_covering ON orders(user_id, status, amount);</code></pre> <p><strong>EXPLAIN 中显示 <code>Using index</code> 表示使用了覆盖索引</strong> 。</p> <H3>五、控制索引数量</H3> <p>索引不是越多越好，每个索引都有成本：</p>   <p>上图分析了索引带来的各项成本。具体说明：</p> <ul> <li> <p><strong>空间成本</strong> ：每个索引都是一棵独立的 B+ 树，会占用额外的磁盘空间。联合索引字段越多，空间占用越大。</p> </li> <li> <p><strong>时间成本（写入时）</strong> ：</p> <ul> <li><code>INSERT</code> 操作需要同时更新所有索引</li> <li><code>UPDATE</code> 操作如果修改了索引列，需要先删除旧的索引项，再插入新的索引项</li> <li><code>DELETE</code> 操作需要从所有索引中删除对应的数据</li> </ul> </li> <li> <p><strong>优化器成本</strong> ：索引越多，MySQL 优化器在生成执行计划时需要考虑的选项越多，可能导致选择时间变长，甚至选错索引。</p> </li> </ul> <p><strong>经验法则</strong> ：</p> <ul> <li>单表索引数量： <strong>不超过 5 个</strong></li> <li>单个索引字段数： <strong>不超过 5 个</strong></li> <li>定期审查：删除 unused 索引</li> </ul> <pre><code class="language-sql" data-lang="sql">-- 查看索引使用情况（MySQL 5.7+）
SELECT * FROM sys.schema_unused_indexes
WHERE object_schema = 'your_database';</code></pre> <H3>六、前缀索引</H3> <p>对于 <code>VARCHAR</code> 、 <code>TEXT</code> 等长字符串列，可以使用前缀索引只索引前 N 个字符，节省空间。</p> <pre><code class="language-sql" data-lang="sql">-- 创建前缀索引，只索引 email 前 10 个字符
CREATE INDEX idx_email_prefix ON users(email(10));

-- 查询时正常使用
SELECT * FROM users WHERE email = 'test@example.com';</code></pre> <p><strong>权衡</strong> ：</p> <ul> <li>✅ 节省索引空间</li> <li>❌ 可能降低区分度（前 N 个字符相同的情况）</li> <li>❌ 无法用于覆盖索引（必须回表验证完整值）</li> </ul> <p><strong>如何确定前缀长度</strong> ：</p> <pre><code class="language-sql" data-lang="sql">-- 计算不同前缀长度的区分度
SELECT
    COUNT(DISTINCT LEFT(email, 5)) / COUNT(*) AS prefix_5,
    COUNT(DISTINCT LEFT(email, 10)) / COUNT(*) AS prefix_10,
    COUNT(DISTINCT LEFT(email, 15)) / COUNT(*) AS prefix_15,
    COUNT(DISTINCT email) / COUNT(*) AS full_column
FROM users;

-- 选择区分度接近完整列的最短前缀</code></pre> <H3>七、索引下推（Index Condition Pushdown，ICP）</H3> <p>MySQL 5.6+ 引入的优化特性，将部分 WHERE 条件的过滤下推到存储引擎层，减少回表次数。</p> <pre><code class="language-sql" data-lang="sql">-- 假设有索引：INDEX(name, age)

-- 无 ICP：存储引擎返回所有 name 匹配的记录，Server 层再过滤 age
-- 有 ICP：存储引擎直接过滤 name AND age，只返回符合条件的记录
SELECT * FROM users WHERE name LIKE '张%' AND age = 25;</code></pre> <p><strong>EXPLAIN 中显示 <code>Using index condition</code> 表示使用了索引下推</strong> 。</p> <H2>面试高频追问</H2> <ol> <li> <p><strong>联合索引的列顺序如何确定？</strong></p> <ul> <li>区分度高的列放前面、等值条件列放前面、范围查询列放后面、考虑排序分组需求。</li> </ul> </li> <li> <p><strong>什么情况下索引会失效？</strong></p> <ul> <li>对索引列使用函数或计算、隐式类型转换、 <code>LIKE</code> 以 <code>%</code> 开头、 <code>OR</code> 条件中有列无索引、联合索引不满足最左前缀、否定条件（<code>!=</code> 、 <code>NOT IN</code> ）等。</li> </ul> </li> <li> <p><strong>主键为什么建议使用自增 ID？</strong></p> <ul> <li>自增 ID 保证新数据顺序插入 B+ 树末尾，避免页分裂，减少碎片，提高写入性能和空间利用率。</li> </ul> </li> </ol> <H2>常见面试变体</H2> <ul> <li>"联合索引 (a, b, c)，WHERE b = 1 AND c = 2 能走索引吗？"</li> <li>"什么情况下应该使用前缀索引？"</li> <li>"索引越多越好吗？为什么？"</li> <li>"覆盖索引是什么？有什么优势？"</li> </ul> <H2>记忆口诀</H2> <p><strong>索引设计七原则</strong> ：选对列、区分高、最左前、覆盖好、控数量、前缀省、下推快</p> <p><strong>联合索引顺序</strong> ：区分度高放前头，等值条件优先走，范围查询放最后</p> <H2>总结</H2> <p>索引设计需要在查询性能和写入成本之间做权衡。核心原则是：选择高频查询且区分度高的列建立索引；联合索引遵循最左前缀原则，区分度高的列放前面；善用覆盖索引避免回表；控制索引数量避免过度索引；长字符串可使用前缀索引节省空间。记住，索引不是越多越好，要根据实际业务场景和查询模式进行设计。</p> </div></main>
