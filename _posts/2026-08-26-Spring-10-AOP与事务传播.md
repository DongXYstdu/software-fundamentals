# AOP 与事务传播
---

## 第 4 段：AOP 实现原理

![AOP 代理与自调用失效]({{ site.baseurl }}/assets/svg/10-01-AOP代理与自调用失效.svg)

### 4.1 两种代理的生成方式

| 维度 | JDK 动态代理 | CGLIB |
|---|---|---|
| 原理 | 基于**接口**：运行时生成实现目标接口的 `$Proxy` 类 | 基于**继承**：运行时生成目标类的**子类** |
| 调用路径 | `$Proxy` → `InvocationHandler` → 目标方法 | 子类重写方法 → `MethodInterceptor` → `super.目标方法` |
| 关系 | 代理与目标是"兄弟"（同接口） | 代理与目标是"父子"（继承） |
| 前提 | 目标类必须实现接口 | 类和方法都不能是 `final` |
| 代理范围 | 只能代理接口方法 | 所有非 final 方法 |

### 4.2 Spring 的选型规则（Boot 2.x 起默认）

```
spring.aop.proxy-target-class = true（默认）→ 一律 CGLIB，哪怕有接口
```

默认 CGLIB 的原因：`@Autowired UserServiceImpl`（注入具体类）时，JDK 代理的 `$Proxy` 不是 `UserServiceImpl` 子类 → 类型不匹配报错。统一 CGLIB 从根上避免。

### 4.3 自调用失效的根因（本段核心）

```
① Controller → 代理对象        （走代理，事务开启 ✓）
② 代理对象 → 目标对象.methodA() （委托，正常）
③ methodA 内部：this.methodB()  （this 是原始对象，绕过代理壳 ✗）
```

**关键一句话**：代理是包在目标对象**外面**的壳；`this.methodB()` 是对象**内部**调用，`this` 永远指向原始对象，碰不到壳 → methodB 的 `@Transactional` **静默失效**（不报错，最危险）。

与代理方式无关——**JDK 和 CGLIB 都失效**，问题不在代理怎么生成，而在"调用有没有穿过代理"。

三种解法（本质都是"让调用重新穿过代理壳"）：

| 解法 | 写法 | 评价 |
|---|---|---|
| ① 拆类 | 把 methodB 移到另一个 Bean，注入后调用 | **首选**，最干净 |
| ② 注入自己 | `@Lazy private UserService self;` → `self.methodB()` | 可行，稍别扭 |
| ③ currentProxy | `((UserService)AopContext.currentProxy()).methodB()`，需 `exposeProxy=true` | 侵入强，不推荐 |

**呼应 09 第 2 段**：`@PostConstruct` 里自调用同理失效——且更彻底，那时代理**还没生成**。

## 第 5 段：事务传播七行为

![事务传播七行为]({{ site.baseurl }}/assets/svg/10-02-事务传播七行为.svg)

### 5.1 七种行为（按"外层有没有事务"两列记忆）

| 行为 | 外层无事务 | 外层有事务 | 记忆标签 |
|---|---|---|---|
| **REQUIRED**（默认） | 新建 | **加入外层，同生共死** | 融入 |
| **REQUIRES_NEW** | 新建 | **挂起外层，新开一条连接** | 独立 |
| **NESTED** | 新建 | **在外层事务内打保存点** | 局部回滚 |
| SUPPORTS | 非事务跑 | 加入外层 | 随大流 |
| NOT_SUPPORTED | 非事务跑 | 挂起外层，非事务跑 | 逃离事务 |
| MANDATORY | 抛异常 | 加入外层 | 断言"必须有" |
| NEVER | 非事务跑 | 抛异常 | 断言"禁止有" |

MANDATORY / NEVER 是"断言型"：保护关键入口（如导出方法标 NEVER，防止被外层大事务包住占用连接过久）。

### 5.2 三强对比（yudao 批处理场景：外层遍历 100 台设备，第 50 台失败）

| | 前 49 台记录 | 特性 | 适用 |
|---|---|---|---|
| REQUIRED | **全没** | 全或无 | 强一致批处理 |
| REQUIRES_NEW | **保留**（已提交） | 独立生死 | 日志/审计留痕 |
| NESTED | 全没（但单台失败只回滚自己） | 局部可回滚、整体同生共死 | 单条失败不连坐 |

**REQUIRES_NEW vs NESTED 本质区别**（面试高频）：
- REQUIRES_NEW：两条连接、两个**真正独立**的事务——"分家"
- NESTED：一条连接、一个事务内的**保存点（savepoint）**——"家里划个房间"

### 5.3 连接数与坑

```
REQUIRED：    外层和内层共用同一个 Connection（一条连接）
REQUIRES_NEW：外层挂起 + 内层新取 = 两条连接
NESTED：      同一条 Connection 上执行 savepoint / rollback(savepoint)
```

REQUIRES_NEW 的坑：批量 + 高并发下占用双连接，可能耗尽连接池或死锁。

### 5.4 前提警告：传播行为建立在代理生效之上

```java
public void importDevices(List<Device> devices) {   // 外层 @Transactional(REQUIRED)
    for (Device d : devices) {
        this.handleOne(d);      // ✗ 自调用！REQUIRES_NEW 根本没机会生效
    }                            //   实际效果 = 全并进外层事务
}
```

## 第 6 段：事务失效全景（8 场景 · 3 层定位）

![事务失效全景]({{ site.baseurl }}/assets/svg/10-03-事务失效全景.svg)

### 6.1 三层排障顺序

| 层 | 排障问题 | 场景 | 共同特征 |
|---|---|---|---|
| 层 1 代理层 | 调用穿过代理了吗？ | ①自调用 ②非 public ③Bean 未受管 ④final | **切面压根没执行**（占一半） |
| 层 2 切面判断 | 异常到达切面了吗？ | ⑤吞异常 ⑥rollbackFor 缺失 | 代理正常，但没看到该回滚的理由 |
| 层 3 环境边界 | 事务真的存在吗？ | ⑦多线程 ⑧MyISAM | 机制正确，边界外失效 |

### 6.2 两个最隐蔽场景

- **⑤ 吞异常**：切面靠**捕获异常**决定回滚，catch 里打日志、做兜底都不影响切面视野——吞掉 = 认为成功。修复：重抛，或 catch 中 `TransactionAspectSupport.currentTransactionStatus().setRollbackOnly()`
- **⑦ 多线程**：事务 Connection 绑定 **ThreadLocal**——事务方法里 `executor.submit()` 的子线程拿到**新连接**，不在同一事务。网关"事务内发 MQ / 异步写日志"最易踩

### 6.3 各场景速查

| # | 场景 | 根因 | 修复 |
|---|---|---|---|
| ① | 自调用 | this = 原始对象 | 拆类 / @Lazy self |
| ② | 非 public 方法 | 代理靠重写，非 public 不参与，静默失效 | 改 public 并拆类 |
| ③ | Bean 未受管 | 手动 new，没过后置钩子，无代理 | 交给容器 |
| ④ | final 方法/类 | CGLIB 靠继承重写，final 禁止 | 去 final（Kotlin 默认 final 注意） |
| ⑤ | 异常被吞 | 切面靠异常触发回滚 | 重抛 / setRollbackOnly() |
| ⑥ | rollbackFor 未配 | 默认只回滚 RuntimeException/Error | `rollbackFor = Exception.class`（yudao 全局规范） |
| ⑦ | 多线程 | Connection 绑定 ThreadLocal | 事务内完成全部逻辑 / 编程式事务 |
| ⑧ | MyISAM | 引擎层无事务 | 换 InnoDB |

## 全课三结论（L2 收束）

1. **一切绕容器**：容器先管 BeanDefinition 蓝图、后造对象——蓝图层是条件装配（回填 08-03）、作用域、依赖排序的根基
2. **代理是分水岭**：生命周期后置钩子生成代理 → 三级缓存为"代理 + 循环依赖"保引用一致 → 自调用绕过代理是一半失效场景的根因（第 5 课 CGLIB 伏笔收口）
3. **事务是切面的应用**：传播行为只在"嵌套调用 + 代理生效"两个前提下才有意义；三强选型看"外层回滚时内层记录要不要留"
