# DDD 落地：限界上下文 / 聚合 / 分层架构（L6 收官课）
## 1. DDD 解决什么问题

业务复杂后最大痛点：**模型混乱**——一个 Order 类背两百字段、Service 几千行 if/else、改个库存动十几个类。

DDD 核心思想：**业务复杂度不会消失，只能用边界把它装进不同盒子**。两套工具：
- 战略设计：拆系统（限界上下文）
- 战术设计：建聚合（一致性边界）

## 2. 战略设计：限界上下文

![08-01 限界上下文与映射]({{ site.baseurl }}/assets/svg/08-01-限界上下文与映射.svg)

一个系统不该有"统一上帝模型"。同一个"商品"概念在不同上下文里就是不同模型：

```
订单上下文 ──C/S──> 商品上下文 ──共享内核──> 库存上下文
商品=快照        商品=完整实体              商品=SKU+数量
│
└── 防腐层（ACL）──> 库存上下文
```

### 三种映射模式
| 模式 | 含义 | 适用 |
|---|---|---|
| C/S 客户-供应商 | 上下游，上游服务下游 | 内部模块协作 |
| 共享内核 | 两边共享一小部分模型（如 SKU） | 强耦合核心概念 |
| **防腐层 ACL** | 翻译层，隔绝对侧模型污染 | **集成外部系统必加** |

### 实战对照
KingSCADA 返回 `Val_xxx` 标签，IoT 内部是 `t_xxx`——典型需要 ACL 的场景：建 `KingScadaAdapter` 把 `Val_xxx` 翻译成 IoT 上下文的 `DeviceTag` 模型，领域层永远只跟 `DeviceTag` 打交道。

## 3. 战术设计：聚合——一致性的边界

![08-02 聚合根与一致性边界]({{ site.baseurl }}/assets/svg/08-02-聚合根与一致性边界.svg)

```
┌──────────────── 订单聚合 ────────────────┐
│                                         │
│      Order 聚合根（外部唯一入口）         │
│         /              \                 │
│        /                \                │
│   OrderItem 实体    Address/Money 值对象  │
│   经 Order.addItem   不可变              │
│   操作                                  │
└─────────────────────────────────────────┘
       ↑
       │ 唯一入口
   外部代码（只持有 Order 引用，禁止直连 OrderItem）
```

### 聚合三条铁律
1. **外部只持有聚合根引用**——改数量要 `order.changeItemQuantity(itemId, qty)`，聚合根守门
2. **事务边界 = 聚合边界**——一次事务只加载/修改/持久化一个聚合
3. **跨聚合协作用领域事件**——`Order` 发布 `OrderPlacedEvent`，`Inventory` 监听扣减，最终一致

### 实战对照
空压机多步安全控制序列（SAFE_STOP）是一个聚合：
- `SafeStopSequence` 聚合根
- `Step` 内部实体
- 外部只能通过 `safeStopSequence.advanceStep()` / `safeStopSequence.abort()` 操作
- 天然保证控制序列的原子性

## 4. 落地：DDD 四层 vs 传统三层

![08-03 DDD 四层与传统三层对比]({{ site.baseurl }}/assets/svg/08-03-DDD四层与传统三层对比.svg)

| 层 | 传统三层（贫血） | DDD 四层（充血） |
|---|---|---|
| 接入 | Controller | Controller |
| 编排 | — | Application（编排·事务·无业务） |
| 业务 | Service（⚠ 业务全在这） | Domain（✓ 业务回到这） |
| 持久化 | DAO/Mapper | Infrastructure（Repository 实现） |
| 模型 | 贫血 Entity（getter/setter） | 充血 Entity（自带行为） |

### 贫血 vs 充血
- **贫血**：业务散在 Service，Entity 是数据袋，改字段改 Service 一堆 if/else
- **充血**：业务回到 Domain，Entity 自带行为；Repository 抽象持久化，可换实现

### yudao 落地提示
yudao 是典型贫血三层（ServiceImpl 几千行常见）。要 DDD 化的渐进路线：
1. 先按上下文拆包（iot-biz 内部按"设备/告警/能耗"分上下文）
2. 把领域逻辑从 ServiceImpl 抽到 Domain 层的聚合方法
3. ServiceImpl 退化成 Application 层，只编排事务
4. Repository 抽象持久化，DO（数据对象）与 Domain Entity 分离
